# 🚨 최우선: 새로 발견한 중대 버그 — **도킹 노드가 절대 실행되지 않습니다**

7번(도킹 파라미터)을 확인하려고 작년 코드를 전수 조사하다가 발견했습니다.

```python
# ship_dock/ship_dock/ship_dock.py 34행
self.declare_parameter("active_wp_mode", 9)     # ← 9번 모드에서 활성화
```
```python
# north_goal_angle.py waypoints — 실제 wp_mode 값들
[..., 7, 3.0],  #WP8 도킹 시작   ← 도킹은 mode 7!
[..., 7, 3.0],  #WP9 도킹        ← mode 7!
```

**`ship_dock`은 `wp_mode == 9`를 기다리는데, 웨이포인트에는 9가 존재하지 않습니다.** 도킹 구간의 실제 모드는 **7**입니다.

게다가 `north_goal_angle`은 mode 7일 때 이렇게 합니다:
```python
if wp_mode == 7:
    self.pub_candidate.publish(Float32(data=CANDIDATE_INVALID))   # 20000 = 폴백
```

**결과: 도킹 구간에서 `ship_dock`은 영원히 잠들어 있고, 배는 그냥 GPS 폴백으로 지나갑니다. 도킹 미션(배점 15%)이 통째로 죽어 있습니다.**

launch에서 파라미터를 안 넘기므로 기본값 9가 그대로 적용됩니다.

**수정:** `active_wp_mode`를 **7**로 바꾸거나, launch에서 명시적으로 넘기세요.

**참고 — 전체 wp_mode 매핑 (검증됨):**

| wp_mode | 웨이포인트 | 담당 노드 | 상태 |
|---|---|---|---|
| 0 | WP0 게이트 시작 | ship_last (=0) | ⚠️ 이름과 안 맞음 |
| 1 | WP1 게이트 끝 | ship_gate (=1) | ✅ |
| 2 | WP2 위치유지 | ship_back (=2) | ✅ |
| 3 | WP3~5 탐색(초록/빨강/하양) | ship_turn (=3) | ✅ |
| 5 | WP6~7 회피 | (없음 — LiDAR 자율회피) | ✅ 의도된 듯 |
| **7** | **WP8~9 도킹** | **ship_dock (=9)** ❌ | **🚨 불일치** |
| 8 | WP10 토너먼트 회피 | (없음) | — |

# 7번. 도킹 파라미터 — **작년 코드는 하드코딩이 맞습니다**

전수 조사 결과입니다.

**비전 노드에는 파라미터가 하나도 없습니다:**
```python
# basic_image_subscriberdock.py 51~52행
self.target_color = "red"        # ← 하드코딩
self.target_shape = "Square"     # ← 하드코딩
```
`color_shape_detector` 패키지 전체에 `declare_parameter`가 **0개**입니다.

**파라미터가 있는 건 미션 노드의 `active_wp_mode`뿐입니다** (그리고 ship_turn의 hold/turn 시간). 이건 "몇 번 모드에서 켜질지"이지 **도킹 표식(색/모양)과는 무관**합니다.

→ 아마 "파라미터로 되어 있다"는 건 이 `active_wp_mode`를 보고 착각하신 것 같습니다. **도킹 표식은 여전히 하드코딩**이고, 제안드린 파라미터화가 필요합니다.

# 11번 vs 10번 — **다른 층위입니다. 둘 다 필요합니다**

같은 것처럼 보이지만, **동작하는 컴퓨터가 다릅니다.**

| | 10번 (ROS 페일세이프) | 11번 (펌웨어 워치독) |
|---|---|---|
| 어디서 도나 | **노트북** (Python 노드) | **아두이노** (C++ 펌웨어) |
| 무엇을 감지 | 센서 값이 오래됐다 (LiDAR/IMU/GPS stale) | `/Motor_run` 명령이 안 온다 |
| 언제 발동 | 센서 고장, 노드 하나 죽음 | **ROS 전체가 죽음, USB 빠짐, 노트북 꺼짐** |

**핵심: ROS가 통째로 죽으면 10번 코드도 같이 죽습니다.** 그때 배를 멈출 수 있는 건 **아두이노밖에 없습니다.** 그래서 11번이 별도로 필요합니다.

**10번 = "센서가 이상하니 내가 멈춘다"**
**11번 = "주인이 죽었으니 내가 멈춘다"**

→ **둘 다 알고리즘에 넣으세요.** 서로를 대체할 수 없습니다.

출발 후 5초에 센서 고장, 전방 14m에 부표 벽이 있는 상황:

| 시나리오 | 페일세이프 | 접촉 | 최종 위치 | 결과 |
|---|---|---|---|---|
| LiDAR 고장 | **OFF** | **2회** | y = 48.0m | 부표벽을 **34m 뚫고 폭주** |
| LiDAR 고장 | **ON** | **0회** | y = 7.9m | 부표벽 **6.1m 앞에서 정지** ✅ |
| IMU 고장 | OFF | 2회 | y = 47.7m | 폭주 |

| 둘 다 | OFF | 2회 | y = 48.0m | 폭주 |
| 둘 다 | **ON** | **0회** | y = 7.9m | 정지 ✅ |

**페일세이프가 없으면 센서가 죽는 순간 마지막 명령으로 부표 벽을 그대로 뚫고 나갑니다.**

**적용한 설계 (3단계):**
- **L1** — 비전만 끊김 → 계속 주행 (미션 포기, 다음 구간으로) ← 지금 하시는 방식
- **L2** — LiDAR/IMU가 **0.5초** 무응답 → **감속(40%) + 직진 유지**
- **L3** — **3초** 무응답 → **정지**
- **미션 타임아웃** — 시스템은 정상인데 미션만 안 풀림 → **다음 좌표로** (전략, 별개)

# 12번. RC 두절 — **판단이 정확하십니다. 그대로 갑니다**

말씀하신 논리가 맞습니다: 자율 미션은 자율로 시작해 자율로 끝나고, RC는 **배에 이상이 있을 때 복귀시키는 용도**입니다. **RC가 끊겼다고 멈추면 경기가 끝나므로** 정지는 답이 아닙니다.

**따라서 최우선 과제는 "RC 신호 없음"과 "자율 선택"을 구분하는 것**입니다. 지금 코드는 이 둘을 **구분하지 못합니다**:

```cpp
// 현재: RC가 없으면 Auto_signal = 0 → 0 < 1500 → 자율
// "RC 없음"인지 "사용자가 자율을 선택"한 건지 알 수 없음
```

**수정 설계:**
```cpp
volatile unsigned long last_rc_ms = 0;   // PulseTimerAuto에서 millis()로 갱신
bool rc_valid = (millis() - last_rc_ms < 500);   // 0.5초 내 펄스 = RC 살아있음

if (!rc_valid) {
    // RC 두절 → 자율 유지 (경기 계속). 단 rc_lost 플래그를 세워둠
    mode = AUTO;
    rc_lost = true;
} else if (Auto_signal >= 1500) {
    mode = MANUAL;    // 사용자가 수동 선택
} else {
    mode = AUTO;      // 사용자가 자율 선택
}
```

**핵심 이점:** RC가 다시 잡히면 `rc_valid`가 즉시 true가 되어 **수동 전환이 정상 작동**합니다. 작년 참사(멀어져서 수동 전환이 안 됨)는 신호가 끊긴 채로 상태가 꼬였기 때문일 가능성이 큽니다.

**안전망은 별도로 유지하세요:** RC 두절 시 자율을 계속하므로, **geofence(9번)** 와 **무선 비상스위치**가 반드시 있어야 배가 경기장 밖으로 나가는 걸 막을 수 있습니다.

# 13번. GPS — **두 가지 용도를 혼동하고 계십니다** (중요)

말씀하신 것: *"GPS 방향(목표) − IMU 방향(뱃머리) = 가야 할 방향"* → **정확합니다.** 그게 `ship_goal_angle`이 하는 일입니다.

**그런데 여기서 쓰는 GPS는 "위치(fix)"입니다. 13번 버그는 그게 아닙니다.**

**GPS가 코드에서 쓰이는 곳은 두 군데인데, 완전히 다릅니다:**

### (A) GPS **위치(fix)** → 목표 방위 계산 ✅ **필수, 유지**
```
north_goal_angle: 현재 GPS 위치 → 목표 WP 좌표 → 목표 방위(bearing)
ship_goal_angle:  목표 방위 − IMU 뱃머리 = 가야 할 방향
```
**이게 말씀하신 그 로직입니다. 당연히 유지해야 합니다.**

### (B) GPS **heading(COG)** → IMU 뱃머리를 **덮어쓰기** ❌ **위험**
```cpp
// iahrs_driver.cpp — 13번 버그는 여기입니다
if (!std::isnan(gps_heading)) {
    yaw_corrected = gps_heading;    // IMU가 잰 뱃머리를 GPS 진행방향으로 바꿔치기!
}
```

**(B)는 "뱃머리 방향" 자체를 GPS 진행방향(COG)으로 대체합니다.** 이건 (A)와 전혀 다른 얘기입니다.

**왜 위험한가:** COG는 **배가 실제로 움직이는 방향**입니다. 뱃머리가 향한 방향이 아닙니다.
- 위치유지·도킹처럼 **느리거나 멈춰 있으면** → COG는 순수 노이즈
- 조류에 옆으로 밀리면 → 뱃머리와 COG가 다름
- 그런데 이 값으로 **IMU를 덮어쓰면** 뱃머리 방향 자체가 엉망이 됩니다

**정리하면:**

| 용도 | 필요한가 | 조치 |
|---|---|---|
| **(A) GPS 위치 → 목표 방위** | ✅ **필수** | **유지.** 단 fix가 2초 이상 끊기면 페일세이프 L2(감속) |
| **(B) GPS heading → IMU 덮어쓰기** | ❌ **불필요** | **끄는 게 안전** (`yaw_corrected = gps_heading` 주석 처리) |

**"GPS가 끊겨도 이전 데이터라도 받아야 한다"는 (A)에 대해서는 맞습니다.** 짧은 끊김(1~2초)은 마지막 위치로 버텨도 됩니다(1.2m/s면 2초에 2.4m 오차). 하지만 그 이상 끊기면 위치가 크게 틀어지므로 **감속하고, 계속 안 오면 정지**해야 합니다.

**(B)는 애초에 지금 토픽 이름이 안 맞아서 작동조차 안 하고 있습니다**(28번). 그러니 **그냥 끄고, 토픽도 연결하지 마세요.** 가장 안전하고 단순합니다.

**여전히 필요한 정보: iAHRS 모델명** (9축이면 지자기로 절대 방위를 내므로 GPS 보정이 완전히 불필요합니다)

# 31·32번. OAK-1 + LiDAR 거리 퓨전 — **가능합니다** ✅

계산 결과 **충분히 실현 가능**하고, 오히려 **RealSense depth보다 물 위에서 더 정확**할 겁니다.

**방식:** 카메라가 "각도 θ에 빨간 부표가 있다" → LiDAR의 `ranges[θ]`를 조회해 거리를 얻음

### ① 각도 정합 정밀도 — 충분함 ✅
- LiDAR 각분해능: **0.225°** (A3, 10Hz)
- 카메라 각도 오차: 약 **±2°**
- 매칭 윈도우 ±3° (= LiDAR 셀 ±13개) 안에서 최소거리 채택 → **문제없음**

### ② 게이트 부표 2개를 구분할 수 있는가 — 여유롭게 가능 ✅

| 거리 | 좌우 부표 각도차 | 판정 |
|---|---|---|
| 2m | 73.7° | ✅ |
| 3m | 53.1° | ✅ |
| 5m | 33.4° | ✅ |
| 8m | 21.2° | ✅ |

매칭 윈도우(±3°)보다 훨씬 크게 벌어져 있어 혼동될 일이 없습니다.

### ③ 유일한 한계 — 도킹 표식 ⚠️
**LiDAR는 2D 평면(수평 한 줄)만 스캔합니다.**
- **부표**: 물에 떠 있어 LiDAR 평면에 걸림 → 거리 획득 ✅
- **도크 구조물**: 평면에 걸리면 거리 획득 ✅
- **도크 표식 판넬**: 물 위 **높은 위치**에 있으면 LiDAR 평면 **밖** → 거리 ❌

**우회책:** 표식은 **카메라로 "어느 도크인지"만 판별**하고, **거리는 그 도크의 구조물을 LiDAR로 측정**합니다. 판별과 측거를 분리하면 됩니다.

### ④ 필요한 작업
- **카메라-LiDAR 외부 캘리브레이션** (상대 위치·각도를 측정해 각도 변환식 만들기)
- **LiDAR 장착 높이**를 부표가 확실히 걸리는 높이로 맞추기 (⚠️ 하드웨어 파트와 협의 필요)
- 새 노드: `/image_bearing`(색·모양·각도) + `/scan` → `/target_distance`

**→ OAK-1으로 진행하셔도 됩니다. 다만 LiDAR 장착 높이를 반드시 부표 높이에 맞추세요.**
