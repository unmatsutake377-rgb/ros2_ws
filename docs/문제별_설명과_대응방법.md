## ⚠️ 먼저 — 1번에 대한 정정

제가 "GPS 방식은 원천 불가"라고 한 건 **과했습니다. 정정합니다.**

준비 기간에 수동 조종으로 돌면서 **직접 GPS 좌표를 찍어두는 것**은 규정 위반이 아닙니다. 규정이 말하는 건 "주최 측이 좌표를 안 알려준다"이지, "GPS를 쓰지 말라"가 아닙니다. 오히려 **"탑재 센서로 직접 인지하라"** 는 요구를 만족합니다(본인 배의 GPS도 탑재 센서니까요).

**다만 세 가지 위험은 남습니다:**

1. **코스가 바뀔 수 있음.** 규정 6.2에 "경기 코스는 대회 당일 공지한다", 2조에 "구역 배치는 변경될 수 있다"고 돼 있습니다. 연습 때 찍은 좌표가 본선에서 틀어질 수 있습니다.
2. **GPS 정밀도.** RTK 없이 일반 GPS는 오차가 m 단위입니다. 게이트 폭이 2~3m인데 GPS 오차가 1~2m면 **좌표만으로는 게이트 중앙을 못 지납니다.** RTK(NTRIP)가 사실상 필수이고, 그래도 최종 정렬은 LiDAR/카메라로 해야 합니다.
3. **도킹·탐색 목표는 당일 공지.** 좌표를 미리 찍어도 **"어느 도크가 목표인지, 어느 색 부표를 도는지"는 당일 결정**됩니다. 이건 좌표로 해결이 안 되고 **반드시 비전**이 필요합니다.

**결론: "GPS로 대략 이동 + 센서로 최종 정렬"의 하이브리드가 정답입니다.** 현재 구조를 버릴 필요는 없고, **센서 기반 미션 수행 레이어를 보강**하면 됩니다. (제 원래 진단보다 훨씬 덜 심각합니다.)

# 🟠 LEVEL 1 — 미션 기능

## 6번. 탐색 orbit 기동이 뭔가?

**규정이 요구하는 것:** 목표 색 부표를 찾아서, **그 부표를 중심으로 원을 그리며 한 바퀴 도는 것**입니다. 방향은 색으로 정해집니다 — **빨강·초록 부표면 시계방향, 흰색이면 반시계방향.**

```
       ⟳ 시계방향 (빨강/초록)
    ┌─────────┐
    │    🔴   │  ← 부표를 중심으로
    │    ↑    │     배가 원을 그리며 한 바퀴
    └─────────┘
        배가 이 원을 따라 돎
```

**지금 코드(`ship_turn`)가 하는 것:** 부표를 발견하면 **좌우로 살짝 비껴서 지나갑니다.** 부표를 스쳐 지나가는 회피 동작이지, 부표 주위를 도는 게 아닙니다. **완전히 다른 동작**이라 새로 만들어야 합니다.

**어떻게 만드나 (개념):**
1. 카메라로 목표 색 부표를 찾는다 → 색상으로 회전 방향 결정 (빨강/초록=CW, 흰색=CCW)
2. 부표까지 거리(depth)와 각도를 잰다
3. 부표에서 반경 R(예: 3m)을 유지하도록 제어 — **거리 오차를 보고 좌/우 추력 차이를 준다**
   - 너무 가까우면 바깥으로, 너무 멀면 안쪽으로
   - 동시에 부표를 항상 옆(90°)에 두도록 조향 → 자연스럽게 원이 그려짐
4. 시작 방위를 기억했다가 360° 돌면 완료

**추가로 필요한 것:** `basic_image_subscriberturn`이 지금 **빨강만 인식**합니다. **초록·흰색 HSV를 추가**해야 합니다(흰색은 채도 낮고 명도 높은 영역).

## 7번. 도킹 표식이 당일 공지 — 어떻게 대응하나?

**문제:** 지금은 코드 안에 `target_color = "red"`, `target_shape = "Square"`가 박혀 있습니다. 당일 "파란 삼각형"이라고 하면 **코드를 고치고 다시 빌드**해야 합니다. 대회장에서 그건 위험합니다.

**대응 방법 3가지 (권장 순서):**

**① ROS 파라미터로 빼기 (가장 권장)**
```python
self.target_color = self.declare_parameter("target_color", "red").value
self.target_shape = self.declare_parameter("target_shape", "Square").value
```
그러면 **빌드 없이 실행할 때 값만 바꾸면** 됩니다:
```bash
ros2 run color_shape_detector basic_image_subscriberdock \
  --ros-args -p target_color:=blue -p target_shape:=Triangle
```
또는 launch 파일에서 인자로 넘기기:
```bash
ros2 launch launch_files launch_files.launch.py target_color:=blue target_shape:=Triangle
```

**② YAML 설정 파일로 빼기**
`dock_target.yaml`에 색/모양을 적어두고, 당일 그 파일만 수정. 코드는 안 건드림.

**③ 런타임 변경 (고급)**
`ros2 param set /image_subscriber_dock target_color blue` — 노드가 켜진 상태로도 바꿀 수 있게. 다만 파라미터 콜백을 구현해야 합니다.

**같이 해결해야 할 것:** 지금 비전 노드는 **모양 인식이 부실**합니다. 삼각형/사각형/원 세 가지를 안정적으로 구분해야 하는데, 현재 HSV·꼭짓점 개수 기준이 거칠어서 오인식이 잦을 겁니다. 그리고 **5색(빨강·초록·파랑·주황·노랑) HSV 범위**를 다 확보하고 대회장 조명에서 재튜닝해야 합니다.

**그리고 도크 3개 중 선택:** 현재는 "표식이 보이면 그쪽으로 간다"인데, 도크 3개가 나란히 있으면 **3개를 모두 인식하고 그중 목표와 일치하는 것을 고르는** 로직이 필요합니다.

## 9번. Geofence(가상경계선)가 뭔가?

**규정:** 장애물 구간에 **노란 점선으로 표시된 가상의 경계선**이 있고, 이걸 **확연히 벗어나면 실격**입니다.

```
  ┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐   ← 가상 경계선 (노란 점선)
  │  🟠  🟠   🟠   🟠   │
  │     🟠   🟠    🟠   │   장애물 구간
  │  🟠    🟠   🟠      │
  └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘
     ↑ 여기를 벗어나면 실격
```

**왜 위험한가:** 배가 장애물을 피하려고 옆으로 크게 돌다가, 경계선 밖으로 나가버릴 수 있습니다. 지금 코드는 **경계선이라는 개념 자체가 없어서** 장애물만 피하면 어디로 가든 상관 안 합니다.

**대응 방법:**
1. 준비 기간에 **경계선 네 모서리의 GPS 좌표를 찍어둔다** (수동 조종으로)
2. 코드에 그 사각형을 넣고, 현재 GPS 위치가 그 안에 있는지 매 순간 확인
3. 경계에 가까워지면(예: 2m 이내) → **그 방향을 '장애물'로 취급**해서 `ship_direction`이 자동으로 피하게 만듦
   - 가장 깔끔한 방법입니다. 경계선을 가상의 벽으로 LiDAR 마스크에 주입하면, 기존 회피 로직이 알아서 처리합니다.
4. 이미 벗어났으면 → 즉시 경계 안쪽 방향으로 복귀

# 🟡 LEVEL 2 — 안전·페일세이프 (10~14번)

## 10번. 소프트웨어 페일세이프가 없다는 게 무슨 뜻?

**페일세이프 = "뭔가 고장 났을 때 안전한 상태로 가는 것"** 입니다.

지금 코드는 이렇습니다. 예를 들어 **GPS가 끊기면?** → `north_goal_angle`은 마지막 위치를 계속 쓰면서 아무 일 없다는 듯 방위를 계산합니다. **IMU가 끊기면?** → 마지막 방위값으로 계속 조향합니다. **LiDAR가 끊기면?** → `motor_control`이 마지막 각도(기본 80°=정면)로 **계속 직진**합니다. **노드가 죽으면?** → 하류 노드가 마지막 명령을 붙잡고 계속 갑니다.

**즉 "고장 = 마지막 명령으로 계속 주행"** 입니다. 배가 멈추지 않습니다.

**있어야 하는 것:** 각 센서/토픽에 **"마지막으로 값이 들어온 시각"** 을 기록하고, 일정 시간(예: 0.5초) 넘게 안 들어오면 → **정지 신호(STOP_HOLD)를 내보내는** 코드입니다. 몇 줄이면 됩니다.

## 11번. 펌웨어 워치독이 없다는 게 무슨 뜻?

**워치독 = "주인이 살아있는지 확인하는 개"** 입니다.

아두이노가 `/Motor_run` 명령을 받아 모터를 돌립니다. 그런데 **노트북이 꺼지거나 USB가 빠지거나 ROS가 죽으면?** 명령이 더 이상 안 옵니다. 지금 펌웨어는 그럴 때 **마지막으로 받은 모터 값을 무한히 유지**합니다. → **배가 전속력으로 계속 달립니다.**

**해결:** 펌웨어에 "마지막 명령 받은 시각"을 저장하고, `timer_callback`에서 **N ms(예: 500ms) 넘게 명령이 없으면 자동으로 중립(1500/1500)** 으로 돌리는 코드를 넣으면 됩니다. 10줄 정도입니다.

```cpp
unsigned long last_cmd_ms = 0;   // 콜백에서 millis()로 갱신
// timer_callback 안에서:
if (millis() - last_cmd_ms > 500) { AutoR = 1500; AutoL = 1500; }
```

## 12번. 무 RC 시 기본 오토파일럿이 왜 위험한가?

펌웨어는 조종기의 Auto 스위치 신호를 보고 모드를 정합니다:
- `Auto_signal < 1500` → **자율운항**
- `Auto_signal >= 1500` → 수동 조종

그런데 **조종기가 꺼져 있거나 신호가 안 잡히면** `Auto_signal`이 **0**으로 남습니다. `0 < 1500`이니까 → **자동으로 자율운항 모드**가 됩니다.

**즉, 조종기가 없거나 신호가 끊기면 배가 자율운항으로 빠집니다.** 그런데 그 상황에서는 사람이 수동으로 뺏어올 수도 없습니다. 11번(워치독 없음)과 겹치면 **완전히 통제 불능**이 됩니다.

**해결:** 유효한 RC 신호가 없으면 → **자율이 아니라 중립(정지)** 으로 가게 바꾸거나, 최소한 "RC 신호가 한 번이라도 잡힌 적이 있어야 자율 허용"으로 조건을 추가합니다.

## 13번. iahrs GPS heading이 stale값에 영구 고정된다?

iahrs 드라이버는 방위(yaw)를 이렇게 정합니다:
- 평소엔 **IMU가 측정한 방위**를 사용
- 그런데 **GPS가 주는 방위(heading)가 유효하면 → 그걸로 덮어씀**

문제는 `gps_heading` 변수가 **한 번 유효한 값을 받으면 절대 초기화(NaN)되지 않는다**는 겁니다.

```cpp
if (!std::isnan(gps_heading)) {
    yaw_corrected = gps_heading;   // GPS 값이 있으면 무조건 이걸로 덮어씀
}
```

**결과:** GPS가 잠깐이라도 방위를 준 뒤 **끊어지면**, 그 **옛날 값(stale)** 이 계속 남아서 **IMU를 영원히 무시**합니다. 배가 아무리 회전해도 방위가 옛날 값에 고정됩니다.

**추가 문제:** GPS의 heading은 **"진행 방향(COG)"** 입니다. 배가 **움직일 때만** 의미가 있고, **정지·저속(위치유지 등)에서는 완전히 부정확**합니다. 선수(뱃머리)가 향한 방향과 다를 수도 있습니다(조류에 밀릴 때).

**해결:**
- GPS 방위에 **타임아웃**을 걸어서, N초 안 들어오면 `gps_heading = NAN`으로 되돌린다
- **속도가 일정 이상일 때만** GPS heading을 신뢰한다 (예: 0.5m/s 이상)
- 아니면 아예 **IMU만 쓰고 GPS 덮어쓰기를 끈다** (가장 단순하고 안전)

## 14번. 미들 스러스터 미제어?

ESC(모터 드라이버)가 **3개** 있습니다 — 오른쪽(R), 왼쪽(L), 그리고 **가운데(M)**.

펌웨어의 자율운항 분기를 보면 `R_signal`과 `L_signal`만 설정하고, **`M_signal`은 건드리지 않습니다.** 수동 조종 분기에서만 설정됩니다.

**결과:** 자율운항 중에 가운데 모터는 **초기값 0** 또는 **마지막 수동 조종값**이 그대로 나갑니다. 제어가 안 됩니다.

**확인 필요:** 실제로 가운데 스러스터가 달려 있나요? 있다면 자율운항에서 어떤 역할이어야 하나요(추가 추력? 횡방향 이동?)? 안 쓸 거면 **명시적으로 중립(1500)** 을 넣어두는 게 안전합니다.

# 🟢 LEVEL 3 — 성능 (15~24번)

## 15번. LiDAR 노이즈 붕괴 — 어떻게 고치나

**현상 (시뮬로 확인됨):** 1.6m 앞 부표를 잘 보고 있다가, **0.3m 거리에 물보라 반사 1점**이 찍히면 → **부표가 통째로 안 보이게 됩니다** (장애물 셀 17개 → 0개).

**원인:** 이 코드 한 줄입니다.
```python
if abs(r - front_min_distance) > self.rear_obstacle_ignore_margin:  # 1.0m
    binary.append(0)   # 무시!
```
"가장 가까운 장애물과 1m 이상 거리 차이 나면 무시한다"는 뜻입니다. 원래 의도는 "먼 배경(벽 등)을 무시하자"였을 텐데, **노이즈가 최근접으로 잡히면 진짜 장애물이 다 걸러집니다.**

**해결 방법 (권장 순서):**

**① 이 로직을 그냥 없앤다 (가장 단순).** `detection_distance(1.8~3m)` 안에 들어온 건 전부 장애물로 본다. 배경 무시는 어차피 탐지거리로 하고 있으므로 이 로직은 중복이자 위험 요소입니다.

**② `front_min_distance`를 노이즈에 강하게 만든다.** 최솟값 대신 **하위 5% 분위수**나 **중앙값 기반**을 쓰면 단일 스파이크에 흔들리지 않습니다.

**③ 시간적 필터를 추가한다 (20번과 함께).** "연속 3프레임에서 계속 보이는 점만 장애물로 인정" → 물보라처럼 순간적인 반사는 자동으로 걸러집니다. **이게 가장 근본적인 해결책입니다.**

## 16번. clearance가 뭔가?

**clearance = 배가 장애물을 지날 때 확보하는 여유 공간**입니다.

코드는 통과 가능한 폭을 이렇게 계산합니다:
```
필요 폭 = half_width × 2 + clearance
       = 0.45 × 2 + 0.15
       = 1.05 m
```
즉 "배 폭 0.9m + 여유 0.15m = 1.05m 이상 뚫려 있으면 지나갈 수 있다"고 판단합니다.

**문제:** 여유 **0.15m는 양쪽 합쳐서 7.5cm씩**입니다. 배가 완벽하게 직진한다면 되겠지만, 실제로는 **조향 오차·관성·조류** 때문에 그 정도는 우습게 벗어납니다.

**시뮬 증거:** 실통과폭 1.1m인 게이트(코드 기준으론 "통과 가능")에서 **실제로 충돌**했습니다.

**해결:** `clearance`를 **0.3~0.5m**로 올리세요. 그러면 필요 폭이 1.2~1.4m가 되어 여유가 생깁니다. 대신 좁은 게이트를 "못 지나간다"고 판단해 후진할 수 있으니, **게이트 구간에서는 조금 낮추는 등 구간별 조정**이 필요할 수 있습니다.

## 17번. 탐지거리 3.0m — LiDAR 스펙상 되나? ✅ **충분히 됩니다**

**RPLIDAR A3 사양:**
- **측정 거리: 최대 25m** (Sensitivity 모드, 현재 설정값)
- 표본 속도: 16,000점/초, 스캔 10Hz
- **각 분해능: 약 0.225°** (한 바퀴에 약 1,600점)

**현재 탐지거리 1.8m는 센서 성능의 7%밖에 안 씁니다.** 3.0m는 물론이고 5m, 10m도 스펙상 전혀 문제없습니다.

**부표가 몇 개 점으로 보이는지 계산:**

| 거리 | 반경 0.2m 부표가 차지하는 각도 | 점 개수 |
|---|---|---|
| 1.8m | 12.7° | 약 56점 |
| **3.0m** | **7.6°** | **약 34점** |
| 5.0m | 4.6° | 약 20점 |
| 10m | 2.3° | 약 10점 |

3m에서도 **34개 점**이면 충분히 안정적으로 탐지됩니다. (코드의 `min_obstacle_cells=3` 조건도 여유롭게 만족)

**진짜 제약은 센서가 아니라 물입니다:**
- 부표는 플라스틱이라 반사율이 낮음 → Sensitivity 모드가 이걸 커버
- **수면 반사·물보라**가 오탐을 만듦 → 15번·20번(시간 필터)으로 대응
- LiDAR 장착 높이가 낮으면 파도를 장애물로 봄 → **가능한 높게** 장착

**결론: 3.0m로 올리세요. 스펙상 여유가 넘칩니다.** 단, 좁은 게이트에서는 오히려 악화됐으니(시뮬), **구간별로 값을 바꾸는 게(게이트 2m / 장애물밭 3~4m) 최선**입니다.

## 18번. 작은 장애물 침식

`suppress_spike_edges` 함수가 **장애물의 가장자리를 깎아냅니다**(침식). 그리고 `smooth_spikes`는 **3셀 이하 장애물을 노이즈로 보고 통째로 지웁니다.**

부표처럼 큰 건 괜찮지만(3m에서 34점), **얇은 기둥·로프·막대**는 몇 점 안 찍혀서 **삭제**됩니다.

**해결:** `max_spike_ratio`(현재 0.01 → 3셀)를 낮추거나, 침식 단계를 없애고 **시간적 필터로 대체**하세요.

## 19번. 침식 후 안전마진이 안 붙는다

`dilate_obstacles`(장애물을 배 폭만큼 부풀리는 함수)에 **`min_obstacle_cells = 3`** 조건이 있습니다. 3셀 미만이면 부풀리지 않습니다.

**문제:** 침식(18번) 후 1~2셀만 남은 장애물은 → **부풀리기가 적용 안 됨** → "장애물은 보이는데 안전 여유는 0" 상태가 됩니다. 오히려 **탐지된 게 더 위험**합니다.

**해결:** 침식을 없애거나, `min_obstacle_cells = 1`로 낮춰서 **작은 것도 반드시 부풀리게** 하세요.

## 20번. 시간적 필터가 없다

**현재:** LiDAR 스캔이 올 때마다 그 **한 장만 보고** 판단합니다. 이전 스캔은 기억 안 합니다.

**문제:** 수면에서 빛이 반사되거나 흡수되면 값이 **깜빡깜빡**합니다. 장애물이 "있다/없다"를 오가면서 조향이 **지터링(덜덜 떨림)** 합니다. 물보라 오탐도 그대로 반영됩니다.

**해결 (개념):** 각 각도별로 **최근 N개 프레임을 기억**하고, "N개 중 M개 이상에서 장애물로 보였을 때만 진짜 장애물로 인정"합니다.
```
예: 최근 3프레임 중 2번 이상 보이면 → 장애물 확정
    순간적인 물보라는 1프레임만 나타나므로 → 자동 제거
```
**15번(노이즈 붕괴)과 18번(작은 장애물 삭제)을 동시에 해결하는 가장 효과적인 방법입니다.**

## 21번. 제어 주기 0.5초가 왜 느린가

`ship_goal_angle`이 **0.5초마다 한 번** 방위 오차를 계산합니다(2Hz). 그런데 IMU는 **100Hz**로 데이터를 줍니다.

**즉 100번 중 2번만 쓰고 98번은 버립니다.**

**결과:** 배가 방향이 틀어져도 **최대 0.5초 뒤에야** 반응합니다. 순항 1.2m/s면 그동안 **0.6m를 잘못된 방향으로** 갑니다. 배가 커지면 관성 때문에 **좌우로 사행(뱀처럼 구불구불)** 하거나 목표를 **오버슈트**합니다.

**해결:** `create_timer(0.5, ...)` → **`create_timer(0.05, ...)`** (20Hz)로 바꾸면 됩니다. 한 줄입니다.

## 22번. 감속 로직이 제거됐다

**예전 버전**은 장애물이나 목표가 가까워지면 **속도를 줄였습니다**:
```python
dist = min(장애물거리, 목표거리)
if dist < 1.5: speed를 낮춤
```

**현재 최종본**은 이 로직이 **통째로 없어졌고**, 그냥 `base_pwm = 1360` 고정 순항입니다. 장애물이 코앞에 있어도 같은 속도로 갑니다.

**왜 문제인가:** 속도가 빠를수록 **회피 반경이 커지고 반응 시간이 짧아집니다.** 접촉 = 30초 패널티인데, 좁은 곳에서 속도를 안 줄이면 부딪힐 확률이 크게 올라갑니다.

**해결:** 장애물 최근접 거리(`/obstacle_distance_array`)를 다시 구독해서, **가까우면 감속**하도록 복구하세요. 시뮬상 접촉이 기록의 65%를 좌우하므로, **감속으로 접촉을 줄이는 게 속도를 유지하는 것보다 훨씬 이득**입니다.

## 23번. mode2_detection_distance가 죽은 코드

```python
self.base_detection_distance = 1.8
self.mode2_detection_distance = 1.8   # ← base와 똑같음!
```
원래 의도는 "도킹(wp_mode 2)에서는 탐지거리를 짧게 해서 도크에 가까이 붙자"였는데, **두 값이 같아서 아무 효과가 없습니다.** 예전 버전엔 0.7이었습니다.

**해결:** 17번과 함께 **구간별 값을 제대로 설정**하세요. 예: 장애물밭 3.0m / 게이트 2.0m / 도킹 0.8m.

## 24번. 신선도(timeout) 체크가 없다

`yaw_error`(방위 오차)와 `candidate_angle`(미션 지시)이 **언제 들어온 값인지 확인하지 않습니다.** 상류 노드가 죽어도 **마지막 값을 영원히 씁니다.**

**해결:** 각 콜백에서 `self.t_yaw = time.time()`으로 시각을 기록하고, 사용할 때 `if time.time() - self.t_yaw > 0.5:` 면 **폴백(정지 또는 직진)** 하도록 합니다. (10번 페일세이프와 같은 작업입니다.)

## 25번. 펌웨어 `It_is_Aship` 오타 — 어떻게 고치나

```cpp
#define It_is_Aship 0   // 주석: A배=0, B배=2
...
if (It_is_Aship == 1) {   // ← 코드는 1을 검사!
    // B배용 다른 PWM 범위
}
```
**주석은 B배를 `2`라고 하는데 코드는 `1`을 검사합니다.** 그래서 `2`를 넣어도 이 분기가 **절대 안 걸립니다** → **B배가 A배의 추력 범위를 그대로 씁니다.**

**해결:** 둘 중 하나로 통일하세요.
```cpp
if (It_is_Aship == 2) { ... }   // 주석에 맞추기
// 또는 #define It_is_Aship 1 로 B배를 1로 정의
```
**두 배 크기가 다르니 이건 반드시 고쳐야 합니다.**

## 30번. udev 포트 의존 — 새 노트북 세팅

`/dev/ttyLiDAR`, `/dev/IMU`, `/dev/ttyGPS`는 **udev 규칙**으로 만들어지는 별명입니다. **새 노트북엔 그 규칙이 없어서 장치를 못 찾습니다.**

**해결:** `/etc/udev/rules.d/99-ssf.rules` 파일을 만들고, 각 장치의 vendor/product ID로 이름을 고정합니다.
```
# 예시 (실제 ID는 lsusb로 확인)
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="ttyLiDAR"
SUBSYSTEM=="tty", ATTRS{idVendor}=="xxxx", ATTRS{idProduct}=="yyyy", SYMLINK+="IMU"
SUBSYSTEM=="tty", ATTRS{idVendor}=="zzzz", ATTRS{idProduct}=="wwww", SYMLINK+="ttyGPS"
```
그다음 `sudo udevadm control --reload-rules && sudo udevadm trigger`.
**이 파일을 저장소에 넣고 세팅 스크립트로 만들어두면** 새 노트북에서도 한 번에 됩니다. 배 2대면 노트북도 2대이므로 **필수**입니다.

## 32번. depth–color 정렬 + 각도 매직넘버

angle = math.degrees(math.atan2(vX - cx, fx))
