# 아이디어 A — "이전 데이터 + 배 속도로 예측해 필터링"

## 평가: **아이디어 자체가 정확합니다** ✅

이건 로보틱스에서 **예측 게이팅(validation gate)** 이라 부르는 표준 기법입니다. 팀이 스스로 이 발상에 도달한 건 좋은 신호입니다.

핵심 논리도 맞습니다. *"이전에 부표를 봤다면, 배가 움직인 만큼 예측한 위치 근처에 있어야 한다. 예측에서 크게 벗어나면 그건 다른 물체(오탐)다."*

## 다만 두 가지를 바꿔야 합니다

### ① "배 속도"가 아니라 **"IMU 각속도"** 를 쓰세요

**문제: 배에 속도계가 없습니다.** 쓸 수 있는 건:
- **GPS 속도(gSpeed)** — 1Hz이고, **저속·정지에서 매우 부정확**합니다. 그런데 게이트를 지날 때가 딱 저속입니다.
- **PWM → 속도 개루프 추정** — 조류·바람·배터리 잔량·부하에 따라 크게 틀어집니다.

**반면 IMU 각속도는 매우 정확합니다** (0.1°/s 수준). 그리고 결정적으로:

> **부표의 방위가 한 프레임 사이에 변할 수 있는 양의 대부분은 '배의 회전' 때문입니다.**
> 배의 '전진'으로 생기는 시차는 부표가 멀면 작고, 가까우면 크지만 그때는 관측도 뚜렷해 매칭이 쉽습니다.

**시뮬로 확인했습니다** (오탐 35% 환경):

| 방식 | 오탐에 속는 비율 |
|---|---|
| 속도 기반 게이팅 (팀 원안) | 8.1% |
| **각속도만 사용** | **8.3%** |

**거의 같습니다.** 속도 추정 오차를 0.8m/s까지 키워도 결과가 안 바뀝니다.

→ **불확실한 속도를 굳이 끌어들일 이유가 없습니다.** 각속도만 쓰면 더 단순하고 더 견고합니다.

### ② 게이팅만 하지 말고 **추적(tracking)** 까지 하세요

게이팅만 하면 문제가 하나 생깁니다. **게이트를 벗어나는 순간 트랙을 버려서 '놓침'이 늘어납니다.**

| 방식 | 정답 추종 | 오탐에 속음 | **놓침** |
|---|---|---|---|
| 현재 (가장 큰 것 선택) | 55.6% | 34.8% | 9.5% |
| 게이팅만 | 73.0% | 8.1% | **18.8%** ← 놓침 2배 |
| **추적기 (게이팅 + 추정)** | **93.3%** | **0.9%** | **5.8%** |

추적기는 **관측이 없어도 예측으로 잠시 버팁니다** (가림·깜빡임 대응). 그래서 놓침도 줄고 오탐도 줄어듭니다.

# 아이디어 B — "IMU에 칼만 필터"

## 평가: **하지 마세요** ❌

**이유: RB-SDA-v1은 IMU가 아니라 AHRS입니다.**

- **IMU** = 원시 자이로·가속도·지자기 데이터를 그대로 줌
- **AHRS** = 그걸 **내부에서 이미 융합해서** roll/pitch/yaw를 계산해 줌

RB-SDA-v1(IntelliThings iAHRS)은 후자입니다. `"e\n"` 명령에 **이미 융합된 오일러각**을 돌려줍니다.

**즉, 칼만 필터가 이미 센서 안에서 돌고 있습니다.** 그 위에 또 필터를 얹으면:
- **얻는 것: 거의 없음** — 원시 자이로 데이터가 없으니 더 나은 융합을 할 수 없습니다
- **잃는 것: 지연** — 이중 필터링은 반응을 느리게 만듭니다. 그런데 우리는 방금 제어 주기를 0.5초 → 0.05초로 줄여 반응성을 확보했습니다. 필터로 다시 느리게 만들면 역효과입니다
- **위험: 발산** — 잘못 튜닝된 칼만 필터는 조용히 발산합니다. 학생 팀이 대회 직전에 디버깅하기 최악의 대상입니다

**칼만 필터가 의미 있으려면** 원시 자이로+가속도+지자기를 직접 받아서 융합해야 하는데, 드라이버가 그걸 주지 않습니다.

## 그럼 칼만은 어디에 쓰나?

**세 군데에서 진짜 가치가 있습니다:**

**1. 부표/표식 추적 ← 이게 바로 아이디어 A입니다** ⭐
이번에 구현했습니다. (아래 참고)

**2. 위치·속도 추정 (GPS + IMU 융합)**
GPS(1Hz, 절대, 노이즈 있음)와 IMU(100Hz, 상대, 드리프트)를 융합하면:
- 100Hz의 부드러운 위치
- **속도 추정** ← 아이러니하게 이게 아이디어 A가 원래 필요로 했던 것
- GPS 끊김 시 몇 초간 추측항법

**하지만 지금은 우선순위가 낮습니다.** 각속도 게이팅으로 이미 해결됐고, 복잡도 대비 이득이 작습니다. **여유가 생기면 그때 하세요.**

**3. LiDAR 부표 추적** (여러 부표를 동시에 추적)
장애물이 많을 때 유용하지만, 지금의 갭-팔로잉으로 충분합니다.

# 실제 구현 결과

**`tracker.py` (알파-베타 필터 + 예측 게이팅)** 를 만들어 `marker_selector` 에 넣었습니다.

## 왜 완전한 칼만이 아니라 알파-베타인가

**알파-베타 필터 = 칼만 필터의 정상상태 근사**입니다.

| | 칼만 필터 | 알파-베타 |
|---|---|---|
| 공분산 행렬 계산 | 필요 | **불필요** |
| 튜닝할 값 | Q, R 행렬 | **α, β 두 개** |
| 발산 위험 | 있음 | **거의 없음** |
| 1차원 방위 추적 성능 | 좋음 | **거의 동일** |

**우리 문제(1차원 방위 추적)에는 완전한 칼만이 과합니다.** 알파-베타로 같은 성능을 훨씬 안전하게 얻습니다.

## 실제 노드로 검증한 결과

`marker_selector` 를 그대로 돌려 측정했습니다 (오탐 35% 환경):

| 설정 | 정답 추종 | **오탐에 속음** | 놓침 |
|---|---|---|---|
| 추적기 OFF (기존) | 54.0% | **36.0%** | 10.0% |
| **추적기 ON (신규)** | **98.7%** | **0.3%** | **1.0%** |

**오탐에 속는 비율이 36% → 0.3%.** 게이트 미션에서 엉뚱한 걸 부표로 보고 돌진하는 일이 사실상 사라집니다.

## 어떻게 동작하나

```
IMU yaw 수신 → 배가 돈 만큼(dpsi) 모든 트랙의 예상 방위를 이동
                              ↓
카메라 관측 수신 → 예측 방위 ±12° 안의 것만 후보로 인정
                → 그중 예측에 '가장 가까운' 것 채택 (가장 큰 것이 아니라!)
                → 알파-베타로 방위·변화율 갱신
                              ↓
              2회 이상 본 트랙만 '확정' (1회짜리 오탐은 여기서 걸림)
```

**핵심 세 가지:**
1. **"가장 큰 것"이 아니라 "예측에 가장 가까운 것"** 을 고릅니다. 가까운 물 반사가 진짜 부표보다 크게 보여도 속지 않습니다.
2. **2회 이상 봐야 확정**합니다. 한 프레임짜리 오탐은 통과하지 못합니다.
3. **관측이 없어도 5프레임까지 예측으로 버팁니다.** 부표가 잠깐 가려져도 트랙을 잃지 않습니다.

## 끄고 켜기

```yaml
marker_selector:
  ros__parameters:
    use_tracker: true         # false 로 하면 기존 방식(가장 큰 것 선택)
    track_gate_deg: 12.0      # ⚠️ 좁히면 오탐↓ 놓침↑ (12°가 시뮬 최적)
    track_confirm_hits: 2     # 2회는 봐야 확정
```

**⚠️ 대회장에서 튜닝하세요.** 카메라 노이즈가 크면 `track_gate_deg` 를 늘리고, 오탐이 많으면 줄이세요.

# 정리 — 팀에게 전할 말

**아이디어 A는 훌륭합니다.** 방향이 정확했고, 실제로 구현하니 오탐이 100배 줄었습니다. 다만:
- **속도 대신 각속도를 쓰세요.** 속도계가 없어서 속도 추정이 부정확한데, 각속도만으로 같은 성능이 나옵니다.
- **게이팅에서 멈추지 말고 추적까지 가세요.** 게이팅만 하면 놓침이 2배로 늘어납니다.

**아이디어 B(IMU 칼만)는 방향이 어긋났습니다.** 센서가 이미 융합을 하고 있어서 얻을 게 없고, 지연만 늘어납니다.

**하지만 팀의 직관은 옳았습니다** — 칼만이 필요하다는 감각 말입니다. **단지 적용할 대상이 IMU가 아니라 부표 추적이었을 뿐입니다.** 그래서 아이디어 A에 칼만(의 경량판인 알파-베타)을 넣었고, 그게 정답이었습니다.
