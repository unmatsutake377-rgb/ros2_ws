## 1. 장비 연결 상태

| 장비 | 포트 | 고정 이름 | 상태 |
|---|---|---|---|
| RPLIDAR A3 | `/dev/ttyUSB0` | **`/dev/ttyLiDAR`** | ✅ health OK, 펌웨어 1.32, Sensitivity 25m, **`/scan` 12Hz** |
| iAHRS IMU | `/dev/ttyUSB1` | **`/dev/IMU`** | ✅ `e` 프로토콜 응답 확인, **100Hz** |

**udev 규칙** `/etc/udev/rules.d/99-ssf.rules` (장비 고유값이라 저장소에 없음):

| 장비 | 판별 기준 | 비고 |
|---|---|---|
| LiDAR | `serial == 0addfc38c7f9f5498e7724af8de7b0cb` | 고유 시리얼 — 확실 |
| IMU | `serial == "0001"` + `product == "CP2102 USB to UART Bridge Controller"` | 🚨 아래 참고 |

🚨 **IMU 시리얼번호가 `0001`(공장 기본값)이라 고유하지 않다.** 지금은 product 문자열이 달라서
(LiDAR `...Bridge` vs IMU `...Bridge Controller`) 구분되지만, **CP2102 모듈을 하나 더 꽂으면
충돌한다.** 그때는 물리 포트 경로(`KERNELS=="3-9.2"`)로 바꿔야 하고, 그러면 **꽂는 자리를
고정해야 하는 제약**이 생긴다.

⚠️ **`dialout` 그룹은 로그아웃만으로 적용되지 않았다.** `systemd --user` 가 로그아웃해도 살아남아
부팅 시점의 그룹 목록을 물고 있기 때문이다. **재부팅해야 적용된다.**

## 2. 🚨 발견한 버그 — 페일세이프 **복구 순간** 노드 사망

### 증상
```
L0 → L1 (WARN)   정상
L1 → L2 (WARN)   정상
L2 → L0 (INFO)   💥 ValueError → ship_direction 사망
```

### 원인
`ship_direction.py` `watchdog_cb` 의 한 줄:
```python
log = self.get_logger().warn if level > prev else self.get_logger().info
log(f"페일세이프 L{prev} → L{level}" + ...)     # ← 같은 소스 위치에서 심각도 2종
```
**rclpy 는 로그 호출을 소스 위치(파일:줄)로 캐싱한다.** 같은 줄이 다른 심각도로 불리면
`ValueError: Logger severity cannot be changed between calls.` 를 던진다.
레벨 상승은 항상 `warn` 이라 안 걸리고, **복구(`info`)에서 처음 걸린다.**

### 실전 영향 (대회를 끝낼 수 있었다)
```
LiDAR 1초 튐 → L1 → LiDAR 복구 → ship_direction 사망
→ /desired_angle 침묵 → motor_control 워치독 0.5s → 모터 중립
→ 아무도 노드를 되살리지 않음 → 배가 물 위에서 영구 정지
```
CLAUDE.md §5 안전장치 4번(**"센서 돌아오면 스스로 풀림"**)이 정반대로 동작하고 있었다.
**고장이 아니라 '회복' 이 배를 죽이는 형태다** — 팀이 가장 두려워한 유형의 최악 버전.

### 왜 못 잡았나
`test_failsafe_logic.py`(27개)는 `SensorWatch` **순수 로직**을 검증한다.
레벨 전이 판정은 처음부터 옳았고, **버그는 ROS 래퍼의 로그 한 줄**에 있었다.
순수 로직 테스트도 시뮬도 닿지 않는 지점 — **실물 구동에서만 나온다.**

### 수정 (`aabb3bc`)
호출 지점을 둘로 분리해 각 줄이 한 가지 심각도만 쓰게 했다. 동작 불변.
저장소 전수 검색 결과 **같은 패턴은 여기 한 곳뿐**이었다.

> 📌 **교훈:** 순수 로직 테스트가 통과해도 ROS 래퍼는 검증되지 않는다.
> 로거를 변수에 담아 재사용하지 말 것.

## 3. 검증한 시나리오

### 3-1. 정상 체인 (8노드)
```
rplidar → /scan → ship_direction → /desired_angle → motor_control → /Motor_run
iahrs → /imu/yaw_raw → yaw_mux → /imu/yaw → ship_goal_angle → /yaw_error ↗
```
GPS 자리(`/north_goal_angle_tp`)만 가짜로 채웠다.

| 토픽 | 실측 주기 | 설계값 |
|---|---|---|
| `/scan` | 12.5 Hz | A3 사양 10Hz |
| `/imu/yaw_raw` | 100.1 Hz | 드라이버 `WallRate(100)` |
| `/imu/yaw` | 50.0 Hz | `period_sec: 0.02` |
| `/yaw_error` | 20.0 Hz | 1단계 0.05s 주기 |
| `/desired_angle` | 10.0 Hz | `control_period_sec: 0.1` |
| `/Motor_run` | 20.0 Hz | motor_control 20Hz |

**전부 설계 주기와 일치.**

### 3-2. ✅ v2.2.2 후진 재탐색 상태기계 — 실물 첫 검증
LiDAR 가 책상 위라 사방 0.37m → "경로 없음" 상태가 계속 유지됐고, 상태기계가 그대로 돌았다.
```
0.51초  PWM 1590/1590 + motor_reverse=True    ← 후진 시작
1.01초  PWM 1500/1500 + motor_reverse=False   ← 0.50초 후 종료  (reverse_duration_sec=0.5)
4.11초  PWM 1590/1590 + motor_reverse=True    ← 3.10초 쿨다운 후 (reverse_cooldown_sec=3.0)
```
**`/motor_reverse` 가 PWM 1500 경계와 완벽히 동기.** N2 후진 게이트가 실물에서 동작한다.

### 3-3. ✅ 페일세이프 — LiDAR 끊김·복구 (수정 후)
```
 3.0초  LiDAR 드라이버 종료
 3.70초 L0 → L1
 5.99초 L1 → L2
13.59초 L0 복구 (재기동 즉시), 노드 생존
/desired_angle 20초간 200회 계속 발행
```
**제어루프 타이머 분리 확인** — LiDAR 9초 끊김 동안에도 발행이 멈추지 않았다(작년엔 0회).

### 3-4. ✅ IMU 끊김 — `/scan` 만 보면 놓치는 경로
```
 3.0초  IMU 드라이버 종료
 3.3초  /imu/yaw 멈춤        ← yaw_mux stale 0.5s → '입을 다뭄'
 3.8초  /yaw_error 멈춤      ← ship_goal_angle 이 침묵 전파
 4.78초 L1                  ← /scan 은 12Hz 멀쩡한데도 잡아냄
 7.08초 L2
14.08초 L0 복구
```
**`/scan` 만 감시했다면 이 고장을 통째로 놓쳤다.** [E] 설계(둘 다 감시, 가장 나쁜 센서가 레벨 결정)가
실물에서 확인됐다. 어느 노드도 "모르는데 아는 척" 하지 않았다.

### 3-5. ✅ motor_control 명령 워치독
```
/desired_angle 마지막 수신 : 3.809초
Motor_run 중립 복귀        : 4.340초
→ 워치독 지연              : 0.531초  (cmd_timeout_sec=0.5 + 발행주기 0.05 한 틱)
```

### 3-6. ✅ 감속 법칙 — 계산식과 실측 일치
거리를 단계 주입하고 PWM 을 관측 (`base_pwm=1360` 전진 기준):

| 거리(m) | 기대 ratio | 실측 PWM | 실측 ratio |
|---|---|---|---|
| 3.0 | 1.000 | 1360 | 1.000 |
| **1.2** | 1.000 | 1360 | 1.000 ← 감속 시작점 |
| 1.0 | 0.950 | 1367 | 0.950 |
| 0.8 | 0.900 | 1374 | 0.900 |
| 0.6 | 0.850 | 1381 | 0.850 |
| 0.3 | 0.775 | 1391 | 0.779 |
| 0.0 | 0.700 | 1402 | 0.700 ← 하한 |

0.3m 의 0.004 차이는 PWM 정수 반올림. **0m 에서도 0.7 로 멈춘다** — 급정지가 아니라 감속만
하는 설계 의도대로다(TTC 폐기와 같은 원칙).

### 3-7. ✅ LiDAR 실물 물체 추적
손을 대고 뗀 구간:
```
 0~3초  0.15~0.23m  방위 97~114°   ← 손
 4~5초  0.26~0.29m  방위  89~90°   ← 떼는 중
 6~11초 0.32~0.35m  방위  88~99°   ← 배경(책상)
```
**거리와 방위가 함께 움직였다** — 노이즈면 방위가 무작위로 튄다. `obst_median_kernel: 5` 가
고립 스파이크를 걸러내고 진짜 물체만 통과시켰다.

### 3-8. ✅ `/imu/mag_heading` (N4) 실물 확인
`yaw_raw` 와 400표본 비교: **평균 차이 0.0015°, 최대 0.012°**.
`zero_yaw_on_boot=false` 라 보정이 안 들어가므로 **설계상 같은 것이 맞다.**
(`mount_offset_deg` 를 잡으면 여기서 갈라진다.)

### 3-9. ✅ healthcheck — 거짓 경보 없음
```
센서: LiDAR/scan ✅  IMU/yaw ✅  GPS/fix …  CAM/image …
heading_status=imu_relative:OK
❌ mode 0,1 → ship_gate : 노드가 떠있지 않음(침묵)
```
`/health_ok=false` 였지만 **전부 실제로 없는 것**을 정확히 짚었다. 늑대소년이 아니다.

## 4-2. GPS (ZED-F9P) 추가 연결 — 설정 불일치 3건 발견·수정

> 같은 날 오후 GPS 를 물렸다. **연습용 배 1척이라 B배(ZED-F9P) 기준으로 통일**한다.
> 순서는 ① udev → ② 관찰 → ③ 설정 → ④ launch 인자화. **추측으로 값을 지어내지 않고
> 전부 실측·코드 추적으로 확정했다.**

### 인식 결과
| 항목 | 값 |
|---|---|
| 모델 | **ZED-F9P** (MON-VER: `MOD=ZED-F9P` / `FWVER=HPG 1.13` / `PROTVER=27.12`) |
| USB ID | `1546:01a9` (u-blox 는 시리얼번호 속성을 안 내놓는다 → VID/PID 로 판별) |
| 고정 이름 | **`/dev/ttyGPS`** |
| 위성계 | GPS + GLONASS + Galileo + **BeiDou** + SBAS + QZSS |
| `/ublox_gps_node/fix` · `fix_velocity` | **각 1.00 Hz** (fix status −1 = 실내라 정상) |

### 🚨 발견 ① launch 가 A배 설정에 하드코딩돼 있었다
`ublox_gps_node-launch.py` 와 `-composed-launch.py` **둘 다** `c94_m8p_rover.yaml`(A배/M8P) 고정.
배가 2척인데 launch 가 한 배에 묶여 있어 **F9P 를 꽂아도 에러 없이 M8P 설정으로 돌았다.**

### 🚨 발견 ② `zed_f9p.yaml` 은 쓸 수 없다 (기지국 설정)
헤더가 `# Configuration Settings for C94-M8P device` 이고 **`tmode3: 1`(Survey-In=기지국)**,
`device: /dev/ttyACM0`. **M8P 파일을 복사해 이름만 바꾼 미완성본**이다. 움직이는 배에 쓰면 안 된다.
→ F9P **rover** 설정이 저장소에 아예 없었다.

### 🚨 발견 ③ NACK 2건의 정체 — UBX-AID
debug 4 로 UBX 바이트를 직접 잡아 확정했다:
```
Setting rate 0x0b, 0x30 → NACK    AidALM.msg  CLASS_ID=11(0x0B) MESSAGE_ID=48(0x30)
Setting rate 0x0b, 0x31 → NACK    AidEPH.msg  CLASS_ID=11(0x0B) MESSAGE_ID=49(0x31)
```
**F9 세대는 UBX-AID 클래스를 지원하지 않는다**(UBX-MGA 로 대체).
`c94_m8p_rover.yaml` 은 `publish.aid.hui` 만 껐고 `alm`·`eph` 는 `publish.all: true` 를
상속해 켜져 있었다(`node.cpp:436-439`). → **`publish.aid.all: false` 한 줄로 셋 다 해결.**

### ⚠️ 발견 ④ `dgnss_mode` 가 적용되지 않는다 (판단 보류)
제품 클래스는 config 가 아니라 **펌웨어 문자열로 결정된다**(`node.cpp:698`):
```
FWVER="HPG 1.13" 은 길이가 정확히 8 → 8>8 거짓 → ref_rov="" → HpPosRecProduct 생성
```
`dgnss_mode` 를 읽는 코드는 **`HpgRovProduct` 에만** 있는데(`hpg_rov_product.cpp:34`) 그게 안 뜬다.
실측 확인: `/navrelposned`·`/navheading`(HpPosRecProduct) + `/navsvin`(상속한 HpgRefProduct).
→ **에러 없이 조용히 무시된다.**

🚨 **이게 RTK 성능에 실제 영향이 있는지는 NTRIP 을 붙여야 안다. 지금은 계정이 없어 검증 불가 →
추측하지 않는다.** 확인법: `/navrelposned` 의 `carrSoln` 플래그(none/float/fixed)를 본다.
fixed 로 안 올라가면 그때 재판단.

### RTCM(NTRIP) 경로 — uart1 은 안 쓰인다
`ntrip_client` → `/rtcm` 토픽 → `UbloxNode::rtcmCallback`(`node.cpp:502`) →
`Gps::sendRtcm`(`gps.cpp:583`) → **연결된 USB 포트로 직접 주입.**
→ `c94_m8p_rover.yaml` 의 `uart1.baudrate: 19200`(M8P 전용) 은 이 구성에서 **미사용**.

|---|---|
| ① | udev 규칙에 GPS 추가 → `/dev/ttyGPS` |
| ② | `save` 블록을 끈 임시본으로만 관찰 (**F9P EEPROM 오염 방지** — 되돌리기 원칙) |

## 4-3. NTRIP 해결 (2026-08-07) — 비밀번호는 계정 비번이 아니다

계정을 새로 발급받고도 `401 Unauthorized` 가 났다. 원인은 **비밀번호**였다.

기관 이용안내(자료실)의 문구:
> Caster Host : www.gnssdata.or.kr, 포트 : 2101, User ID : 로그인 아이디, **비밀번호 : gnss**

**NTRIP 비밀번호는 개인 계정 비밀번호가 아니라 기관이 공개한 고정값 `gnss` 다.**
아이디만 개인값(= 로그인 이메일 **전체**)이다.

| 아이디 | 비밀번호 | 결과 |
|---|---|---|
| 이메일 전체 | 개인 비밀번호 | 401 |
| `@` 앞부분만 | `gnss` | 401 |
| **이메일 전체** | **`gnss`** | **ICY 200 OK** ✅ |

→ 작년 커밋의 `password: "gnss"` 는 **오타가 아니라 원래 맞는 값**이었다.
   작년이 404 였던 건 비밀번호가 아니라 **계정(아이디)이 자동 삭제**됐기 때문이다.
   🚨 **최종접속 기준 50일 미접속 시 계정 자동 삭제** (가입 페이지 명시).
   **대회 전에 한 번 접속해 살아있는지 확인하는 절차가 필요하다.**

### 마운트포인트 선정 — 소스테이블로 계산
캐스터의 source table 은 **인증 없이** 받을 수 있다(`curl --http0.9 http://gnssdata.or.kr:2101/`).
545개 스트림의 기준국 좌표를 WP0(35.1862, 128.5655) 와 대조한 결과:

| 순위 | 기준국 | 거리 |
|---|---|---|
| **1** | **CHWN**(창원) | **12.8 km** ← 채택 (`CHWN-RTCM32`) |
| 2 | GOSG(고성) | 32.7 km |
| 3 | MLYN(밀양) | 37.3 km |

작년의 `DAEG`(대구)는 약 90km 였다. 기준국이 멀수록 RTK 초기화가 느리고 fixed 유지가 불안정하다.

### 검증
- 생 소켓 probe: `ICY 200 OK`
- RTCM 실수신: **10초에 55프레임 / 1081 B/s**
  · 1075·1085·1095·1125 = GPS·GLONASS·Galileo·BeiDou **MSM5** (각 10회)
  · 1006(기준국 좌표), 1033(수신기/안테나), 1230(GLONASS 바이어스)
- ROS 노드: `Connected to http://gnssdata.or.kr:2101/CHWN-RTCM32`, **`/rtcm` 5.5Hz**
- ⚠️ **RTK fixed 도달은 미확인** — 실내라 GPS fix 자체가 없어 보정을 쓸 수가 없다. 야외 필요.

### 진단 방법 (다음에 막히면)
ROS 를 빼고 **생 소켓으로 Basic 인증 GET** 을 쏘면 원인이 바로 갈린다.
NTRIP 버전 3종(없음/1.0/2.0)을 바꿔가며 시험해 **클라이언트 구현·프로토콜 버전·네트워크를 배제**했다.
남은 게 계정뿐이었고, 실제로 그랬다.
※ 별도 NTRIP 클라이언트 프로그램은 **받을 필요 없다.** 우리 `ntrip_client` 노드가 그 역할이고,
  기관이 배포하는 건 클라이언트가 없는 사람용(대개 Windows GUI)이라 배에 못 쓴다.

## 4-4. 카메라(D455) 연결 시도 (2026-08-07) — 🚨 케이블 문제로 미완

**결론: 인식·설정까지는 정상, 영상 프레임이 안 온다. USB 케이블이 원인.**

| 항목 | 결과 |
|---|---|
| 장치 | Intel RealSense D455, S/N 213622300722, FW **5.13.0.55** |
| 스트림 열기 | ✅ 컬러·뎁스 `640x480@30` (USB2.1 에서도 지원 프로파일에 존재) |
| **실제 프레임** | ❌ **0 fps** (`Frames didn't arrived within 5 seconds` 반복) |
| USB 링크 | ⚠️ **`Usb Type Descriptor : 2.1`** — 3.2 여야 정상 |

### 원인 규명 과정
1. 처음엔 허브 2단 경유(`Bus03 → 허브 → 허브 → 카메라`) → 직결로 변경 → **그래도 2.1**
2. USB 3.0 포트 2곳 모두 시도 → **둘 다 2.1**
   · 같은 포트에 **허브를 꽂으면 5000M** 로 붙는다 → **포트는 USB3.0 이 맞다**
3. 커널: `uvcvideo: Non-zero status (-71)` = **EPROTO**, device number 가 **59까지 재열거**
4. 카메라를 손에 들고 있던 변수 제거(고정) → **EPROTO 0건, 재열거 멈춤**
   → 접촉 불량은 해소됐는데 **프레임은 여전히 0**
5. 뎁스를 꺼서 대역폭을 줄여도 **0 프레임** → 대역폭 문제가 아니라 **링크 자체**

→ **케이블이 USB 2.0 전용**이라는 설명만 남는다(정품 아님을 확인).
  USB-C 는 뒤집어 꽂아도 동작하므로 **방향 문제는 아니다.**

### 필요한 것
USB **3.2 Gen1(=3.0, 5Gbps)** C↔A 케이블, **1m 이하**, `SS` 로고 또는 A단자 안쪽 파란색.
"충전 전용" 금지. ⚠️ Intel 정품일 필요 없다 — **RealSense 는 임시 카메라이고 본선은 OAK 다.**

### 🚨 별건으로 잡은 실제 버그 — 카메라 내장 IMU 가 노드를 죽인다
```
Failed to open .../iio:device1/scan_elements/in_anglvel_x_en : Permission denied
→ Error updating the sensors   (rs_node_setup.cpp:511)
```
librealsense 가 D455 의 HID/IIO 센서를 열려다 실패하고, 그 예외가 **센서 설정을 통째로 중단**시킨다.
RealSense udev 규칙이 시스템에 없기 때문이다(`ros-humble-librealsense2` 가 제공하지 않는다).

**케이블과 무관하다** — 좋은 케이블로 바꿔도 그대로 난다.
→ `launch_files.launch.py` 에 **`enable_gyro:False, enable_accel:False`** 추가로 해결.
  udev 규칙을 까지 않은 이유: **우리는 이 IMU 를 쓰지 않는다**(헤딩은 iAHRS·yaw_mux 담당).
  안 쓰는 센서를 위해 시스템에 규칙을 남기는 대신 명시적으로 끈다.
  ※ OAK(PoE)로 바꾸면 USB HID 자체가 없어져 이 줄은 불필요해진다.

### 🚨 화각 불일치 발견 — OAK 로 이월되는 자산
프레임 4장이 왔을 때 `camera_info` 를 읽었다:

| 출처 | 값 |
|---|---|
| `camera_info` | `fx=387.36` → **HFOV 79.12°** |
| `vision.yaml` | `hfov_deg: 71.5` |
| 차이 | **+7.62°** (화면 가장자리 조향각 약 3.8° 오차, `align_tol_deg`=5°) |

`oak_arrival_runbook.md` §5 의 "검산" 절차가 **실제로 불일치를 잡아낸다**는 것이 증명됐다.
⚠️ 프레임 4장에서 읽은 값이라 **확정이 아니다.** 스트리밍 정상화 후 재확인할 것.
→ 런북에 기록 + `hfov_deg` 를 없애고 `camera_info` 직독으로 갈지 **검토 항목**으로 남겼다
  (OAK 실물의 `camera_info` 를 보고 판단 — 지금은 검증할 카메라가 없다).

## 4-5. 카메라 없이 마저 한 검증 (2026-08-07)

카메라 케이블을 기다리는 동안, **장비가 꽂혀 있을 때만 할 수 있는 것** 3가지를 처리했다.

### ① 미션 노드 모드별 동작 — 런타임 검증은 이번이 처음
그동안 `test_mode_gate.py` **정적 검사**만 있었다. `north_goal_angle` 을 내리고 `/wp_mode` 를
직접 발행하며 누가 `/candidate_angle` 을 말하는지 관측했다(각 모드 정착 3초 + 측정 5초).

| wp_mode | 담당(설계) | 실측 |
|---|---|---|
| 0, 1 | `ship_gate` | `INVALID×50` (단일 값) |
| 2 | `ship_back` | `180°×34` + `INVALID×16` |
| 3 | `ship_turn` | `SPIN_RIGHT×50` |
| **5** | **없음(회피)** | **✅ 침묵 0회** |
| 7 | `ship_dock` | `SPIN_RIGHT×47` + `STOP_HOLD×3` |
| **8** | **없음(회피)** | **✅ 침묵 0회** |

**mode 5·8 침묵이 핵심이다.** CLAUDE.md 3-6 이 *"담당 노드가 없는 것이 정상이고, healthcheck 가
이걸 '누락' 으로 경고하면 매 실행마다 늑대소년이 된다"* 고 못박은 항목 — 실물에서 아무도 말하지 않는다.

⚠️ mode 2 의 두 값은 **`ship_back` 한 노드가 내는 것**이다(발행자 충돌 아님).
소스 확인: `REVERSE_REL=180.0`(LiDAR 거리가 너무 가까워 후진) ↔ `CANDIDATE_INVALID`(부표 못 찾음).
카메라가 없어 부표를 못 보니 두 상태를 오가는 것이 정상.
⚠️ 전환 직후 이전 모드의 잔여 메시지가 1~2건 섞인다 → **정착 시간을 주고 측정할 것.**
   (정착 없이 재면 mode 5 에 `SPIN_RIGHT×2` 처럼 나와 충돌로 오해한다)

**보너스:** `/wp_mode` 발행자가 0 이 되자 **미션 노드가 전부 침묵**했다.
"모드를 모르면 비활성"(3-4) 원칙이 검출기뿐 아니라 **미션 노드에도 살아 있다.**

### ② blackbox GPS 컬럼 — 실제 GPS 로 확인
| 컬럼 | 결과 |
|---|---|
| `gps_lat`·`gps_lon` | 187행 (0.0 — fix 없음) |
| **`gps_status`** | **187행, `-1`** ← NO_FIX 가 그대로 기록된다 |
| `gps_vel_x`·`gps_vel_y` | 187행 |
| `gps_dt_max` | `1.0009` (1Hz 간격 정확) |
| `gps_count` | 195행 |

→ **사후에 "그때 fix 가 있었나" 를 정확히 복원할 수 있다.**
   (`wp_mode`·`cam_dt_max` 만 빈칸 — 각각 발행자 정지 상태·카메라 미연결이라 정상)

### ③ `tools/boat_boot.sh` — 첫 실행
🚨 **적용 전 기본값이 전부 위험 쪽이었다:**
```
CPU 거버너      : powersave  (12코어 전부)
USB autosuspend : 2 (켜짐) — 장치 10개가 절전 대상
```
적용 후: 전 코어 `performance` / `usbcore.autosuspend = -1` / 13개 장치 `power/control=on` /
sleep·suspend·hibernate target stop.

**적용 후 장비 정상 확인:** `/scan` 12.9Hz, `/imu/yaw_raw` 100.1Hz, `/fix` 1.0Hz.

> **USB autosuspend 가 기본으로 켜져 있었다는 게 중요하다.** CLAUDE.md 7-3 이 *"시리얼 장치가
> 끊기는 실재 리눅스 이슈"* 라고 한 바로 그 설정이다. 지금까지 시험에서 안 끊긴 건 **운이었을 수 있다.**
> ⚠️ 런타임 설정이라 **재부팅하면 원복**된다 → launch 전에 매번 실행할 것.

※ `pkexec` 로 실행하면 DISPLAY 가 안 넘어가 스크립트가 헤드리스로 판단하고 `xset` 을 건너뛴다.
  화면 절전은 systemd 쪽에서 이미 막으므로 실질 문제는 없다.
