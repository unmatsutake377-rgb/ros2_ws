## 1. 장비 연결 상태

| 장비 | 포트 | 고정 이름 | 상태 |
|---|---|---|---|
| RPLIDAR A3 | `/dev/ttyUSB0` | **`/dev/ttyLiDAR`** | ✅ health OK, 펌웨어 1.32, Sensitivity 25m, **`/scan` 12Hz** |
| iAHRS IMU | `/dev/ttyUSB1` | **`/dev/IMU`** | ✅ `e` 프로토콜 응답 확인, **100Hz** |

**udev 규칙** `/etc/udev/rules.d/99-ssf.rules` (장비 고유값이라 저장소에 없음):

| 장비 | 판별 기준 | 비고 |
|---|---|---|
| LiDAR | `serial == 0addfc38c7f9f5498e7724af8de7b0cb` | 고유 시리얼 — 확실 |
| IMU | `serial == "0001"` + `product == "CP2102 USB to UART Bridge Controller"` | 🚨 아래 참고 |

🚨 **IMU 시리얼번호가 `0001`(공장 기본값)이라 고유하지 않다.** 지금은 product 문자열이 달라서
(LiDAR `...Bridge` vs IMU `...Bridge Controller`) 구분되지만, **CP2102 모듈을 하나 더 꽂으면
충돌한다.** 그때는 물리 포트 경로(`KERNELS=="3-9.2"`)로 바꿔야 하고, 그러면 **꽂는 자리를
고정해야 하는 제약**이 생긴다.

⚠️ **`dialout` 그룹은 로그아웃만으로 적용되지 않았다.** `systemd --user` 가 로그아웃해도 살아남아
부팅 시점의 그룹 목록을 물고 있기 때문이다. **재부팅해야 적용된다.**

## 2. 🚨 발견한 버그 — 페일세이프 **복구 순간** 노드 사망

### 증상
```
L0 → L1 (WARN)   정상
L1 → L2 (WARN)   정상
L2 → L0 (INFO)   💥 ValueError → ship_direction 사망
```

### 원인
`ship_direction.py` `watchdog_cb` 의 한 줄:
```python
log = self.get_logger().warn if level > prev else self.get_logger().info
log(f"페일세이프 L{prev} → L{level}" + ...)     # ← 같은 소스 위치에서 심각도 2종
```
**rclpy 는 로그 호출을 소스 위치(파일:줄)로 캐싱한다.** 같은 줄이 다른 심각도로 불리면
`ValueError: Logger severity cannot be changed between calls.` 를 던진다.
레벨 상승은 항상 `warn` 이라 안 걸리고, **복구(`info`)에서 처음 걸린다.**

### 실전 영향 (대회를 끝낼 수 있었다)
```
LiDAR 1초 튐 → L1 → LiDAR 복구 → ship_direction 사망
→ /desired_angle 침묵 → motor_control 워치독 0.5s → 모터 중립
→ 아무도 노드를 되살리지 않음 → 배가 물 위에서 영구 정지
```
CLAUDE.md §5 안전장치 4번(**"센서 돌아오면 스스로 풀림"**)이 정반대로 동작하고 있었다.
**고장이 아니라 '회복' 이 배를 죽이는 형태다** — 팀이 가장 두려워한 유형의 최악 버전.

### 왜 못 잡았나
`test_failsafe_logic.py`(27개)는 `SensorWatch` **순수 로직**을 검증한다.
레벨 전이 판정은 처음부터 옳았고, **버그는 ROS 래퍼의 로그 한 줄**에 있었다.
순수 로직 테스트도 시뮬도 닿지 않는 지점 — **실물 구동에서만 나온다.**

### 수정 (`aabb3bc`)
호출 지점을 둘로 분리해 각 줄이 한 가지 심각도만 쓰게 했다. 동작 불변.
저장소 전수 검색 결과 **같은 패턴은 여기 한 곳뿐**이었다.

> 📌 **교훈:** 순수 로직 테스트가 통과해도 ROS 래퍼는 검증되지 않는다.
> 로거를 변수에 담아 재사용하지 말 것.

## 3. 검증한 시나리오

### 3-1. 정상 체인 (8노드)
```
rplidar → /scan → ship_direction → /desired_angle → motor_control → /Motor_run
iahrs → /imu/yaw_raw → yaw_mux → /imu/yaw → ship_goal_angle → /yaw_error ↗
```
GPS 자리(`/north_goal_angle_tp`)만 가짜로 채웠다.

| 토픽 | 실측 주기 | 설계값 |
|---|---|---|
| `/scan` | 12.5 Hz | A3 사양 10Hz |
| `/imu/yaw_raw` | 100.1 Hz | 드라이버 `WallRate(100)` |
| `/imu/yaw` | 50.0 Hz | `period_sec: 0.02` |
| `/yaw_error` | 20.0 Hz | 1단계 0.05s 주기 |
| `/desired_angle` | 10.0 Hz | `control_period_sec: 0.1` |
| `/Motor_run` | 20.0 Hz | motor_control 20Hz |

**전부 설계 주기와 일치.**

### 3-2. ✅ v2.2.2 후진 재탐색 상태기계 — 실물 첫 검증
LiDAR 가 책상 위라 사방 0.37m → "경로 없음" 상태가 계속 유지됐고, 상태기계가 그대로 돌았다.
```
0.51초  PWM 1590/1590 + motor_reverse=True    ← 후진 시작
1.01초  PWM 1500/1500 + motor_reverse=False   ← 0.50초 후 종료  (reverse_duration_sec=0.5)
4.11초  PWM 1590/1590 + motor_reverse=True    ← 3.10초 쿨다운 후 (reverse_cooldown_sec=3.0)
```
**`/motor_reverse` 가 PWM 1500 경계와 완벽히 동기.** N2 후진 게이트가 실물에서 동작한다.

### 3-3. ✅ 페일세이프 — LiDAR 끊김·복구 (수정 후)
```
 3.0초  LiDAR 드라이버 종료
 3.70초 L0 → L1
 5.99초 L1 → L2
13.59초 L0 복구 (재기동 즉시), 노드 생존
/desired_angle 20초간 200회 계속 발행
```
**제어루프 타이머 분리 확인** — LiDAR 9초 끊김 동안에도 발행이 멈추지 않았다(작년엔 0회).

### 3-4. ✅ IMU 끊김 — `/scan` 만 보면 놓치는 경로
```
 3.0초  IMU 드라이버 종료
 3.3초  /imu/yaw 멈춤        ← yaw_mux stale 0.5s → '입을 다뭄'
 3.8초  /yaw_error 멈춤      ← ship_goal_angle 이 침묵 전파
 4.78초 L1                  ← /scan 은 12Hz 멀쩡한데도 잡아냄
 7.08초 L2
14.08초 L0 복구
```
**`/scan` 만 감시했다면 이 고장을 통째로 놓쳤다.** [E] 설계(둘 다 감시, 가장 나쁜 센서가 레벨 결정)가
실물에서 확인됐다. 어느 노드도 "모르는데 아는 척" 하지 않았다.

### 3-5. ✅ motor_control 명령 워치독
```
/desired_angle 마지막 수신 : 3.809초
Motor_run 중립 복귀        : 4.340초
→ 워치독 지연              : 0.531초  (cmd_timeout_sec=0.5 + 발행주기 0.05 한 틱)
```

### 3-6. ✅ 감속 법칙 — 계산식과 실측 일치
거리를 단계 주입하고 PWM 을 관측 (`base_pwm=1360` 전진 기준):

| 거리(m) | 기대 ratio | 실측 PWM | 실측 ratio |
|---|---|---|---|
| 3.0 | 1.000 | 1360 | 1.000 |
| **1.2** | 1.000 | 1360 | 1.000 ← 감속 시작점 |
| 1.0 | 0.950 | 1367 | 0.950 |
| 0.8 | 0.900 | 1374 | 0.900 |
| 0.6 | 0.850 | 1381 | 0.850 |
| 0.3 | 0.775 | 1391 | 0.779 |
| 0.0 | 0.700 | 1402 | 0.700 ← 하한 |

0.3m 의 0.004 차이는 PWM 정수 반올림. **0m 에서도 0.7 로 멈춘다** — 급정지가 아니라 감속만
하는 설계 의도대로다(TTC 폐기와 같은 원칙).

### 3-7. ✅ LiDAR 실물 물체 추적
손을 대고 뗀 구간:
```
 0~3초  0.15~0.23m  방위 97~114°   ← 손
 4~5초  0.26~0.29m  방위  89~90°   ← 떼는 중
 6~11초 0.32~0.35m  방위  88~99°   ← 배경(책상)
```
**거리와 방위가 함께 움직였다** — 노이즈면 방위가 무작위로 튄다. `obst_median_kernel: 5` 가
고립 스파이크를 걸러내고 진짜 물체만 통과시켰다.

### 3-8. ✅ `/imu/mag_heading` (N4) 실물 확인
`yaw_raw` 와 400표본 비교: **평균 차이 0.0015°, 최대 0.012°**.
`zero_yaw_on_boot=false` 라 보정이 안 들어가므로 **설계상 같은 것이 맞다.**
(`mount_offset_deg` 를 잡으면 여기서 갈라진다.)

### 3-9. ✅ healthcheck — 거짓 경보 없음
```
센서: LiDAR/scan ✅  IMU/yaw ✅  GPS/fix …  CAM/image …
heading_status=imu_relative:OK
❌ mode 0,1 → ship_gate : 노드가 떠있지 않음(침묵)
```
`/health_ok=false` 였지만 **전부 실제로 없는 것**을 정확히 짚었다. 늑대소년이 아니다.
