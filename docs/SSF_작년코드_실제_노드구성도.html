기존에 돌던 구성표와 소스 코드가 3곳에서 다릅니다. 이 문서는 ros2_ws (대회 온보드 노트북 최종본) 의 create_subscription / create_publisher 를 전부 파싱해서 만든 것입니다. 코드가 정답입니다.

2. 기존 구성표와 다른 3곳

1 /left_*, /right_* 토픽은 존재하지 않습니다

구성표에는 /left_angle, /left_distance, /right_angle, /right_distance 가 그려져 있지만, 코드 어디에도 없습니다. 실제 게이트 비전은 /red_angle, /red_distance, /green_angle, /green_distance 를 씁니다.

→ 구성표가 구버전입니다. 이대로 작업하면 없는 토픽을 ros2 topic echo 하게 됩니다.

2 motor_control 로 들어가는 선 2개가 실제로는 끊겨 있습니다

구성표는 /obstacle_distance_array 와 /goal_distance 가 motor_control 로 들어가는 것처럼 그렸습니다. 실제 코드는:

self.sub_angle = self.create_subscription(Float32, "/desired_angle", ...)  — 이게 전부입니다.

장애물이 코앞이어도 감속하지 않았던 이유가 이겁니다. /obstacle_distance_array 는 ship_turn 과 ship_back 만 받고 있고, /goal_distance 는 아무도 안 받는 죽은 토픽입니다. 구성표는 '의도'를 그렸는데, 코드가 그 의도를 구현하지 않았습니다.

3 뎁스(depth) 카메라 의존이 구성표에 아예 없습니다 — 가장 위험

비전 노드 3종이 전부 /camera/camera/depth/image_rect_raw 를 구독합니다. 모든 거리값(/image_distance, /red_distance, /green_distance)이 RealSense 의 뎁스에서 나옵니다.

OAK-1 W POE 는 단안(mono) 카메라라 뎁스가 없습니다. (뎁스가 있는 건 OAK-D 계열입니다.) 카메라만 갈아끼우면 ship_gate, ship_dock, ship_turn, ship_back 이 전부 거리를 못 받아 죽습니다.

대응은 둘 중 하나입니다: ① OAK-D 계열(스테레오 뎁스 있음)로 바꾸거나, ② 거리를 LiDAR 에서 가져오도록 코드를 바꾸는 것 — 올해 새 코드가 이미 이 방식입니다 (카메라는 방위각만, 거리는 /scan 에서).

3. 구조적 결함 — /candidate_angle 에 6개 노드가 발행

north_goal_angle, ship_gate, ship_dock, ship_turn, ship_back, ship_last — 여섯 노드가 같은 토픽에 발행합니다.

각 노드가 스스로 /wp_mode 를 보고 "내 차례면 발행" 하는 분산 합의 구조입니다. 그런데 active_wp_mode 가 6개 파일에 흩어져 있어서, 아무도 전체 표를 볼 수 없습니다.

노드active_wp_mode상태
ship_gate0, 1정상
ship_back2정상
ship_turn3정상
ship_dock9 🚨 웨이포인트의 도킹 모드는 7입니다 → 1년 내내 침묵

도킹 미션이 통째로 죽어 있었는데 아무도 몰랐습니다. 배는 멀쩡히 돌아다녔고, 그냥 도킹만 안 했으니까요. 침묵하는 노드는 에러를 내지 않습니다. 이게 이 구조의 근본 위험입니다.

권고: 노드 구조는 그대로 두고, wp_mode → 담당 노드 매핑표를 yaml 한 곳에 모은 뒤, 부팅 시 healthcheck 가 "빠진 모드 / 중복 모드 / 침묵하는 노드" 를 자동 검사하게 하는 것. 노드를 하나도 안 건드리면서 같은 사고를 구조적으로 막습니다.
