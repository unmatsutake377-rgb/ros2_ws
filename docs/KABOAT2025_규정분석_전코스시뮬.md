# KABOAT 2025 경기규정 분석 + 전 코스 시뮬레이션 (최종)

> 경기규정(경기규정-202511-수정.docx) + 임무설명서를 분석하고,
> 실제 경기장 규격(70m×20m)으로 현재 코드 로직을 구동한 결과.

---

## 🚨 1. 규정에서 나온 치명적 발견 — 현재 아키텍처가 원천적으로 불가

**경기규정 5.2:**
> *"각 구성물의 정확한 위치(**GPS 좌표**)는 **공개되지 않으며**, 각 팀은 보트에 탑재된 **센서를 활용하여** 임무 수행에 필요한 상황 인지를 **직접 수행**해야 한다."*

현재 코드 `north_goal_angle`은 **웨이포인트 GPS 좌표를 코드에 하드코딩**해두고 그 좌표로 항법합니다.
**좌표가 공개되지 않으므로 이 방식은 근본적으로 성립하지 않습니다.**

→ GPS는 "대략적인 구간 이동"에만 쓰고, **미션 수행(게이트·부표·도크 인지)은 LiDAR/카메라 기반으로 전면 전환**해야 합니다. 파라미터 조정이 아니라 **아키텍처 수준의 변경**입니다. 이게 올해 최우선 과제입니다.

## 2. 규정에서 확정된 수치

| 항목 | 값 |
|---|---|
| 1경기장 (종합임무) | **70m × 20m** |
| 2경기장 (토너먼트) | **30m × 12m** |
| 제한시간 (종합임무) | **15분 (900초)** |
| 장애물 접촉 패널티 | **1회당 30초** (토너먼트 15초) |
| 위치유지 | 부표 **5m 이내, 5초**, **2회 수행** |
| 보트 크기 | 길이 **L ≥ 1.0m**, 높이 **H ≤ 1m** |
| 전원 | DC 모터 + 축전지, **최대 24V** |
| 도전 횟수 | 종합임무 **5회**, 최고점 채택 |

**미션 순서 (종합임무):** 항로추종 → 위치유지 → 도킹 → 탐색 → 장애물회피
**배점 (75% 중):** 장애물회피 **20%** > 항로추종·도킹·탐색 각 **15%** > 위치유지 **10%** / 토너먼트 원격·자율 각 5%

## 3. 🔧 규정 미충족 하드웨어 (지금 없는 것)

규정 4.2에 필수인데 현재 시스템에 없습니다:

- **상태 표시등 (3색)** — 원격조종=**초록**, 자율운항=**노란색**, 비상정지=**빨강**. 검사 항목(8번)이라 없으면 **경기 참가 불가**.
- **비상스위치 2종** — **버튼식** + **무선식** 둘 다 필수 (검사 9·10번).
- **흘수선 표시** (100~110% 부력)

또 규정상 **"제어명령은 선체 내부 연산장치에서 계산"** 되어야 하고 외부 PC는 모니터링만 가능합니다. (NTRIP 보정 수신은 제어 연산이 아니므로 문제없어 보이나, 주최 측 확인 권장)

## 4. 전 코스 시뮬레이션 결과 (70×20m, 실제 배치)

실제 노드 로직(ship_direction 갭팔로잉 / motor_control / yaw_error)을 그대로 구동.
가정: 배 폭 0.9m(코드값), 순항 1.2m/s.

| 탐지거리 | 게이트폭 | 주행시간 | 접촉 | 패널티 | **최종 기록** | 판정 |
|---|---|---|---|---|---|---|
| 1.8m | 2.0m | 906.8s | 2회 | 60s | 966.8s | ★ **시간초과** |
| 1.8m | 3.0m | 139.8s | 3회 | 90s | **229.8s** | 완주 |
| 1.8m | 4.0m | 139.8s | 3회 | 90s | **229.8s** | 완주 |
| 3.0m | 2.0m | 141.2s | **6회** | 180s | 321.2s | 완주 |
| **3.0m** | **3.0m** | 139.6s | 3회 | 90s | **229.6s** | 완주 |
| 3.0m | 4.0m | 139.6s | 3회 | 90s | **229.6s** | 완주 |

### 핵심 해석

**시간은 문제가 아닙니다.** 전 코스 주행이 약 **140초**인데 제한시간은 900초라 6배 여유입니다.

**진짜 승부는 접촉 패널티입니다.** 접촉 1회 = 30초인데, 순수 주행이 140초이므로:

| 접촉 | 기록 | 순수주행 대비 |
|---|---|---|
| 0회 | 139.6초 | — |
| 1회 | 169.6초 | **+21.5%** |
| 3회 | 229.6초 | **+64.5%** |
| 5회 | 289.6초 | **+107%** |

**접촉 3회면 기록이 거의 2배가 됩니다.** 즉 **속도를 올리는 것보다 "안 부딪히는 것"이 압도적으로 중요**합니다. 지금 코드는 모든 조합에서 **접촉 3회**가 발생합니다.

**좁은 게이트에서 막힙니다.** 게이트 2.0m + 탐지 1.8m 조합은 주행 907초로 시간초과했습니다. 통과폭이 부족하다고 판단해 후진(260)을 반복하며 헤맵니다.

**탐지거리를 무작정 올리면 안 됩니다.** 탐지 3.0m + 게이트 2.0m는 오히려 접촉 6회로 악화됐습니다. 좁은 곳에서 너무 일찍 반응해 사행합니다.

## 5. 미션 ↔ 코드 불일치 (재확인)

| 미션 | 규정 요구 | 현재 코드 | 상태 |
|---|---|---|---|
| **전체** | GPS 좌표 비공개, 센서로 인지 | 웨이포인트 GPS 하드코딩 | ❌ **원천 불가** |
| 항로추종 | 빨강–**초록** 게이트 | `/red_angle` + **`/yellow_angle`**(노랑) | ❌ 색상 불일치 |
| 탐색 | 부표 중심 **원 선회(orbit)**, 빨강·초록=시계 / **흰색**=반시계 | 좌우로 비껴가기, 흰색 인식 없음 | ❌ 동작 자체가 다름 |
| 도킹 | 표식 **당일 공지** (3형상 × 5색) | `red`+`Square` 하드코딩 | ❌ 변경 불가 |
| 위치유지 | 부표 5m 이내 5초, **2회** | GPS 기준 5초 정지, 위치 피드백 없음 | ❌ 표류 |
| 장애물회피 | 가상경계선 이탈 = 실격 | geofence 없음 | ❌ 실격 위험 |

## 6. 우선순위 (배점 가중치 반영)

**1순위 — 아키텍처 (모든 미션의 전제)**
1. **GPS 웨이포인트 의존 제거** → 센서 기반 상황 인지로 전환. 규정상 필수.

**2순위 — 접촉 줄이기 (기록에 직결, 장애물회피 20%로 배점 최대)**
2. `clearance` **0.15m → 0.3~0.5m** (시뮬상 접촉의 주원인)
3. `detection_distance` **1.8m → 3.0m** (단, 좁은 게이트 구간은 별도 값)
4. **구간별 탐지거리 전환** — 게이트/도킹은 짧게, 장애물밭은 길게
5. LiDAR **노이즈 견고성** (앞서 확인한 `rear_obstacle_ignore_margin` 버그 — 물보라 1점에 부표가 사라짐)

**3순위 — 미션 기능 (각 15%)**
6. 탐색 **orbit 기동** 신규 작성 (색상별 회전 방향)
7. 게이트 색상 **노랑 → 초록**
8. 도킹 표식 **파라미터화** (당일 공지 대응)
9. 위치유지 **피드백 제어** (10%)
10. **Geofence** (실격 방지)

**4순위 — 검사 통과 (없으면 출전 불가)**
11. 3색 상태 표시등, 버튼식+무선식 비상스위치, 흘수선 표시
