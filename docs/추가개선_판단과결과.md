# ✅ 구현한 것

## 1. 📼 블랙박스 로거 — **이게 가장 중요합니다**

**왜 최우선인가:** 규정에 **"종합임무는 5회까지 도전 가능, 최고점을 최종 점수로"** 라고 되어 있습니다.

즉 **1회차에 실패해도 원인만 알면 2~5회차에서 고칠 수 있습니다.**
그런데 지금은 **왜 실패했는지 알 방법이 없습니다.**

- 부표를 못 봤나? 봤는데 회피를 못 했나?
- 페일세이프가 걸렸나? 걸렸다면 **어느 센서** 때문에?
- GPS가 튀었나? IMU 방위가 틀어졌나?
- 게이트를 몇 개 통과했나?

**경기 후 CSV 한 장을 엑셀로 열면 전부 나옵니다.**

```
t, wp_mode, lat, lon, goal_bearing, imu_yaw, yaw_error, candidate,
desired_angle, pwm_r, pwm_l, obst_dist, failsafe, dock_ang,
red_ang, green_ang, buoy_ang, gates_passed
```

**rosbag이 아니라 CSV인 이유:** rosbag은 `/scan`(초당 16,000점) 때문에 용량이 폭발하고, 열려면 ROS 환경이 필요합니다. CSV는 **엑셀로 바로 열리고** 15분에 몇 MB입니다.

**부하:** 10Hz × 20컬럼 = 초당 200값. CPU 0.01% 미만.

> **이게 5회 도전이라는 규정을 살릴 수 있는 유일한 방법입니다.**

## 2. 🩺 출발 전 헬스체크

**왜 필요한가:** 심판이 호명하면 **1분 안에 출발**해야 합니다. 그 짧은 시간에 터미널 로그를 뒤져 "GPS 잡혔나? IMU 살아있나?"를 확인할 수 없습니다.

**특히 위험한 상황:** 센서 하나가 죽은 채 출발하면 **페일세이프가 곧바로 걸려 배가 물 위에 멈춰 섭니다.** 경기가 그대로 날아갑니다.

이 노드가 2초마다 한 줄로 알려줍니다:
```
✅ 출발 준비 완료 | LiDAR 342스캔 IMU 680 GPS 34 | 페일세이프 L0
```
또는
```
❌ 출발하지 마시오 — 문제 발견:
   · GPS fix 없음 (하늘이 안 보이거나 안테나 문제)
   · IMU 끊김 (3.2초 전이 마지막)
```

## 3. 🚩 게이트 쌍 제약 + 순차 통과 카운트

### 쌍 제약 — **검증됨** ✅

**문제:** 화면에 **"다음 게이트의 빨강"** 과 **"이번 게이트의 초록"** 이 같이 보이면, 그 둘의 중간으로 가버립니다. **엉뚱한 방향입니다.**

**해결:** 두 부표의 각도차가 게이트로서 말이 되는 범위(5~80°)일 때만 쌍으로 인정합니다.

**실제 노드로 검증:**

| | 결과 |
|---|---|
| 쌍 제약 OFF | 빨강 -75°, 초록 +20° → **중간 -27.5°** (엉뚱한 방향!) |
| **쌍 제약 ON** | 각도차 95°는 같은 게이트가 아니라 판단 → **초록만 사용, +5.0°** ✅ |

### 순차 통과 카운트

규정: *"다수의 게이트를 순차적으로 통과해야 하며, 중간에 게이트를 누락할 경우 패널티"*

지금까지 **몇 개를 통과했는지 세지 않았습니다.** 부표가 옆(±75°)을 넘어 뒤로 가면 통과로 카운트하고 `/gates_passed` 로 발행합니다. 블랙박스에도 기록됩니다.

## 4. ⚠️ TTC 비상 제동 — **정직하게: 효과가 측정되지 않았습니다**

**아이디어:** 거리만 보면 늦습니다. **"몇 초 뒤에 부딪히는가(TTC)"** 를 보고, 못 피할 것 같으면 일단 멈춥니다. (멈추는 비용 1~2초 << 접촉 30초)

**그런데 시뮬에서 추가 이득이 안 나왔습니다:**

| | 접촉 | 최소 여유 |
|---|---|---|
| 비상제동 OFF | 0회 | +0.53m |
| 비상제동 ON | 0회 | +0.59m |

**이유:** 이미 갭-팔로잉 + 감속이 충분히 잘 작동해서, 비상 제동이 발동할 상황 자체가 안 왔습니다.

**그래도 넣은 이유:** 시뮬은 **완벽한 센서**를 가정합니다. 실제로는 LiDAR 노이즈, 반응 지연, 조류 때문에 회피가 실패할 수 있습니다. **비용이 거의 없는 보험**이고, `use_emergency_brake: false` 로 언제든 끌 수 있습니다.

**솔직한 평가: 넣어두되 기대는 하지 마세요.** 문제가 생기면 끄면 됩니다.

# ❌ 일부러 안 한 것 (그리고 그 이유)

## GPS + IMU 위치 칼만 필터

**할 수는 있습니다.** 100Hz 부드러운 위치, 속도 추정, GPS 끊김 시 추측항법을 얻습니다.

**하지만 안 합니다:**
- **속도 추정이 필요했던 이유가 사라졌습니다.** 부표 추적은 각속도만으로 해결됐습니다.
- GPS는 **구간 이동용**일 뿐입니다. 미션 수행은 이미 LiDAR/카메라가 합니다.
- **위험:** 잘못 튜닝된 칼만은 **조용히 발산**합니다. 대회 직전에 디버깅하기 최악입니다.

**여유가 생기면 그때 하세요. 지금은 아닙니다.**

## LiDAR 다중 물체 추적

부표를 하나하나 트랙으로 관리하면 이론적으로 더 좋습니다.

**하지만 안 합니다:**
- 시간 필터(3프레임 중 2회)로 이미 **접촉 0.2회**를 달성했습니다.
- 다중 물체 추적은 **데이터 연관(data association)** 문제가 따라옵니다. 부표가 많으면 트랙이 뒤엉킵니다.
- **개선 여지가 거의 없는 곳에 복잡도를 쏟는 건 손해입니다.**

## 딥러닝 비전 (YOLO 등)

**HSV보다 조명에 강건한 건 사실입니다.** OAK-1은 온보드 AI 가속도 있어서 기술적으로 가능합니다.

**하지만 안 합니다:**
- **학습 데이터가 없습니다.** 실제 부표·도크 사진을 수백~수천 장 찍고 라벨링해야 합니다.
- 배도 아직 안 만들어졌습니다. **데이터를 찍을 대상이 없습니다.**
- 실패하면 **비전이 통째로 날아갑니다.** HSV는 최소한 튜닝하면 동작합니다.

**대안:** HSV를 **대회장 조명에서 제대로 재튜닝**하는 데 시간을 쓰세요. 그게 훨씬 확실합니다.

## MPC 등 고급 제어

현재는 P 제어에 가깝습니다. MPC로 바꾸면 더 부드러운 궤적이 나옵니다.

**하지만 안 합니다:**
- **접촉 문제는 이미 해결됐습니다** (3회 → 0.2회). 개선 여지가 없습니다.
- 배점을 좌우하는 건 **접촉(30초)** 이지 궤적의 우아함이 아닙니다.
- 튜닝 비용이 크고, 배 물리 모델이 정확해야 하는데 **배가 아직 없습니다.**

# 💡 제가 생각하는 '진짜 남은 일'은 코드가 아닙니다

코드는 이제 **할 만큼 했습니다.** 여기서 더 얹는 건 수익체감입니다.

**진짜 병목은 이것들입니다:**

| 우선순위 | 할 일 | 왜 |
|---|---|---|
| **1** | **배를 빨리 만들어서 실측** | 배 폭·순항속도·선회응답 — 모든 파라미터가 여기 묶여 있습니다 |
| **2** | **조향 좌/우 부호 벤치 확인** | 배선이 반대면 **모든 게 무의미**합니다. 가장 흔한 사고 |
| **3** | **HSV를 대회장 조명에서 재튜닝** | 물 위 반사 때문에 실내 값이 절대 안 맞습니다 |
| **4** | **udev + NTRIP 계정 2개 준비** | 노트북 2대. 안 하면 대회장에서 손도 못 댑니다 |
| **5** | **LiDAR 장착 높이 = 부표 높이** | 하드웨어 파트와 협의. 안 맞으면 부표를 못 봅니다 |
| **6** | **IMU를 모터·배터리에서 멀리** | 지자기 간섭 = 방위가 통째로 틀어집니다 |

**소프트웨어는 준비됐습니다. 이제 하드웨어와 실측이 병목입니다.**
