## 6a — `ship_dock` + `north_goal_angle` ⚛ **원자적 한 쌍, 같은 커밋**

```
6a: ship_dock 과 north_goal_angle 을 '같은 커밋에서 함께' 고쳐라.
따로 고치면 없던 버그가 생긴다 (아래 [3] 참고).

[1] 🚨 ship_dock: active_wp_mode 9 → 7
    작년 웨이포인트 표에서 도킹은 mode 7 인데 9 로 선언돼 있었다.
    → 도킹 노드가 1년 내내 침묵했다. 배는 멀쩡히 돌아다녔고 도킹만 안 했다.
    침묵하는 노드는 에러를 내지 않는다. 이게 이 구조의 근본 위험이다.

[2] 🚨 ship_dock: 카메라 뎁스를 쓰지 마라
    OAK-1 W POE 는 RGB 전용, 스테레오 뎁스가 없다 (Luxonis 문서 확인).
    작년 코드는 /camera/camera/depth/image_rect_raw 를 구독했다.
    → /image_distance 를 믿지 마라. /scan(LiDAR)을 구독해서 거리를 구해라.

    ★ 그런데 '표식 방위의 LiDAR 거리' 를 찾지도 마라. 그것도 틀린다.
      도크는 넓은 구조물이라, 비스듬히 접근하면
      표식(중앙) 방위와 LiDAR 최근접점 방위가 최대 15° 어긋난다 (계산으로 확인).
      매칭 윈도우 ±3° 를 한참 벗어난다.

    → 올바른 방법: 전방 섹터(정면 ±15°)의 LiDAR '최소거리' 만 쓴다.
      "그 표식까지 얼마" 가 아니라 "전방에 뭔가 얼마나 가까운가" 만 알면 된다.
      도크에 접근 중이면 전방 최소거리 = 도크까지 거리다.
      각도 정합 문제가 통째로 사라진다.

[3] 🚨 north_goal_angle: wp_mode==7 폴백을 제거해라 (이게 원자적인 이유)
    지금 north_goal_angle 은 0.5초마다 이렇게 한다:
        if wp_mode == 7:
            self.pub_candidate.publish(Float32(data=20000.0))   # = 무시하고 GPS로 가라

    이건 작년 사람들이 '도킹이 안 되는 걸 알고 덮어둔 흔적' 이다.
    ship_dock 이 9 로 잡혀 침묵하니, 배가 멈추지 않게 north 가 대신 폴백을 냈다.

    ship_dock 을 7 로 고치면 → 같은 토픽에 발행자가 둘이 된다.
    도킹 중 조향이 GPS 방위로 튄다 (제어 주기의 2%, 20초에 7회 전환).
    접안 직전 60초에 35° 스파이크가 20번쯤 튄다.

    → if wp_mode == 7:  을  if wp_mode in (5, 8):  로 바꿔라.
      폴백은 '담당 노드가 없는 모드' 에만 남긴다 (5=회피, 8=토너먼트회피).

[4] ship_dock: 정면 접근 (head-on approach) FSM
    비스듬한 접근이 모든 문제의 근원이다 (도형 면적 감소, LiDAR 정합 오차).
    → 표식 발견 → 도크 정면 standoff 지점(3m)으로 먼저 이동
      → 도크를 정면으로 마주보게 선회 정렬 → 그다음 직진 접안
    상태: INIT → SEARCH → ALIGN → APPROACH → CONTACT → BACKOFF → DONE

[5] SPIN 규약 (2단계에서 확정)
    5000 = 우선회, 6000 = 좌선회
    ship_dock 의 SEARCH 에서 sweep 할 때 이 값을 쓴다.
    motor_control 은 이제 진짜 제자리 선회를 한다 (spin_forward_pwm=1500).

[6] north_goal_angle: Geofence 발행
    경기장 밖으로 나가면 실격이다. 지금 방어가 0이다.
    → /geofence_state (Float32MultiArray) 발행: [경계까지 거리(m), 경계 방위(deg)]
      ship_direction 이 이미 이걸 구독해서 '가상 장애물' 로 칠하고 알아서 피한다.
    → 경기장 폴리곤 좌표는 아직 모른다. 파라미터로 빼고 ⚠️ 실측 필요 주석.

[7] 공통
    · time.monotonic() 사용
    · 배 2척(A/B) → 값은 전부 파라미터 + ⚠️ 실측 필요 주석
      (standoff_dist_m, contact_dist_m, front_sector_half_deg, geofence_margin_m ...)
    · 토픽 이름은 바꾸지 마라

끝나면 커밋하고, 두 파일을 다음 경로로 복사해줘:
  cp ~/ros2_ws/src/ship_dock/ship_dock/ship_dock.py \
     ~/ros2_ws/src/north_goal_angle/north_goal_angle/north_goal_angle.py \
     ~/Desktop/"SSF 노드 파일"/검토함/
(복사가 안 되면 그냥 알려줘 — 채팅으로 올린다)
```

## 6b — `ship_gate`

```
6b: ship_gate 를 고쳐라.

[1] 🚨 yellow 폴백 제거
    규정은 '빨강-초록' 게이트다. 작년 코드에 yellow 폴백이 있다.

[2] active_wp_modes: [0, 1]
    작년: ship_gate=1, ship_last=0 (WP0 "게이트 시작" 인데 ship_last 가 잡고 GPS 폴백만 냈다)
    → 게이트 접근 구간(mode 0)부터 비전을 쓰는 편이 정렬 시간을 번다.
      mode 0 도 ship_gate 가 맡는다.

[3] 🚨 게이트 쌍 제약
    화면에 '다음 게이트의 빨강' 과 '이번 게이트의 초록' 이 같이 보이면,
    그 둘의 중간으로 가버린다. 엉뚱한 방향이다.
    → 두 부표의 각도차가 게이트로서 말이 되는 범위일 때만 쌍으로 인정.
      pair_min_sep_deg: 5.0   (이보다 붙어 있으면 같은 게이트 아님)
      pair_max_sep_deg: 80.0  (이보다 벌어져 있으면 같은 게이트 아님)
    → 벗어나면 가까운 쪽 하나만 쓴다.

[4] 순차 통과 카운트
    규정: "다수의 게이트를 순차적으로 통과. 누락하면 패널티"
    지금은 몇 개 통과했는지 세지 않는다.
    → 부표가 ±75° 를 넘어 뒤로 가면 '통과' 로 카운트
    → /gates_passed (Int32) 발행. ★ 이름 주의: /gate_pass_count 아니다.
      (0단계 blackbox 가 /gates_passed 로 구독하고 있다)

[5] 거리는 LiDAR 에서
    /red_distance, /green_distance 는 카메라 뎁스 기반이라 OAK-1 에서 죽는다.
    → 부표는 '점 물체' 라 표식-LiDAR 매칭이 통한다 (도크와 다르다).
      카메라 방위 → 그 방위의 LiDAR 거리. /scan 을 구독해라.

[6] 파라미터: red_on_port (빨강이 좌현인가) — ⚠️ 벤치 검증 필요
```

## 6c — `ship_turn`

```
6c: ship_turn 을 고쳐라. 동작이 완전히 바뀐다.

[1] 🚨 작년은 '비껴 지나가기' 였다. 규정은 '선회(orbit)' 다. 규정 위반이었다.
    → 부표를 중심으로 원을 그리며 도는 orbit 기동으로 재작성.
      부표를 ±90° 에 두고, LiDAR 거리로 반경을 보정한다.

[2] 🚨 흰색 부표 인식이 없다
    규정: 빨강·초록 = 시계방향 / 흰색 = 반시계방향
    작년 코드는 빨강만 봤다.
    → /buoy_color 로 색을 받아 회전 방향을 정한다.

[3] 거리는 LiDAR 에서 (/image_distance 쓰지 마라)

[4] 파라미터: orbit_radius_m (⚠️ 실측 필요), radius_tol_m, approach_dist_m,
             k_radial_deg_per_m, orbit_target_deg(360)

[5] SPIN 규약: 5000=우선회, 6000=좌선회
```

## 6d — `ship_back` + `ship_last` 제거

```
6d: ship_back 을 고치고 ship_last 를 제거해라.

[1] 🚨 ship_back 이 하는 일이 '그냥 5초간 PWM 중립' 이다.
    조류 0.5m/s 면 5초에 2.5m 밀린다. 규정은 '부표 5m 이내 5초 유지' 다.
    → 밀려나서 실패한다.
    → 부표까지 거리를 LiDAR 로 재면서 전진/후진으로 위치를 유지해라.
      hold_dist_m(2.5m) 를 목표로, 벗어나면 되돌린다.
      (충돌 여유 + 5m 이내를 동시에 만족시키는 값)

[2] 🚨 ship_back.py 가 자기를 'ship_turn' 으로 등록한다 (복붙 실수)
        super().__init__('ship_turn')
    작년엔 launch 의 name= 덮어쓰기로 가려져 있었다.
    올해는 yaml 파라미터를 노드 이름으로 찾으므로,
    ship_back 이 ship_turn 의 active_wp_mode(3) 을 받아버린다.
    → super().__init__('ship_back') 으로 고쳐라.
    → 그리고 전 노드의 super().__init__() 이름이 파일명·패키지명과 맞는지 확인해라.

[3] ship_last 제거
    하는 일이 /candidate_angle 에 20000 폴백을 내는 것뿐이다.
    새 north_goal_angle 이 mode 5, 8 에서 폴백을 낸다. 중복이다.
    → 패키지 삭제 + launch 에서 제거.

[4] 파라미터: active_wp_mode(2), keep_radius_m(5.0, 규정), hold_time_sec(5.0, 규정),
             hold_dist_m(⚠️ 실측 필요), dist_tol_m
```
