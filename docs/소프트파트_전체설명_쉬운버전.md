> 회로·기구 등 소프트웨어를 직접 만지지 않는 팀원이 "소프트 파트가 뭘 했고, 배가 어떻게 스스로 움직이는지"를

> 하니까요. 대신 그 용어가 처음 나올 때 **무슨 뜻인지 풀어서** 설명합니다. 비유는 이해를 돕는 용도로만 쓰고,
> 용어 자체를 비유로 바꾸지는 않습니다.
>

## 1. 한 문장 요약

**작년(2025) 대회에 실제로 나갔던 배의 소프트웨어를, 올해 새로 만드는 배 두 척(A배·B배)에 다시 쓰기 위해,
배가 없는 지금 시점에 "확인 가능한 버그부터" 하나씩 고치고 있습니다.**

- 배도 아두이노도 카메라도 아직 없습니다. 배는 약 2주 뒤 완성 예정입니다.
- 그래서 **하드웨어 없이도 검증할 수 있는 것**부터 손봤습니다.
- 지금까지 소프트웨어에서 할 수 있는 수정은 사실상 다 끝났고, 남은 건 배가 떠야 시작됩니다.

## 2. 먼저 알아야 할 기본 용어

이 몇 개만 알면 나머지가 다 읽힙니다.

### ROS2 (Robot Operating System 2)
로봇 소프트웨어를 만드는 **틀(프레임워크)** 입니다. 우리 배의 두뇌가 이 위에서 돌아갑니다.
ROS2의 핵심 아이디어는 "**프로그램을 잘게 쪼개서 서로 메시지를 주고받게 한다**"는 것입니다.

### 노드 (node)
잘게 쪼갠 프로그램 조각 하나하나를 **노드**라고 부릅니다.
예를 들어 "LiDAR에서 거리 데이터를 읽는 노드", "그걸 보고 조향각을 정하는 노드", "모터를 돌리는 노드"가
각각 따로 있습니다. 노드 하나가 고장 나도 나머지는 계속 돕니다.

> 비유: 공장의 작업자 여러 명. 각자 자기 일만 하고, 컨베이어 벨트로 물건을 다음 사람에게 넘깁니다.
> 노드 = 작업자, 벨트 = 아래의 "토픽".

### 토픽 (topic)
노드들이 메시지를 주고받는 **통로(채널)** 입니다. 이름이 붙어 있습니다.
예: `/scan`(LiDAR 거리 데이터가 흐르는 통로), `/imu/yaw`(뱃머리 방향이 흐르는 통로).

- **발행(publish)**: 노드가 토픽에 데이터를 "내보내는" 것. (작업자가 벨트에 물건을 올림)
- **구독(subscribe)**: 노드가 토픽에서 데이터를 "받아 읽는" 것. (다음 작업자가 벨트에서 물건을 집음)

한 토픽에는 **여러 노드가 구독**할 수 있습니다(여러 명이 같은 벨트를 봄). 하지만
**한 토픽에 발행하는 노드는 원칙적으로 하나**여야 합니다. 둘이 같은 통로에 서로 다른 값을 내보내면
받는 쪽이 어느 게 진짜인지 모릅니다. **이게 우리가 반복해서 당한 사고의 핵심입니다(6장 참고).**

### 파라미터 (parameter)
노드의 **설정값**입니다. 코드를 안 고치고도 바깥에서 숫자나 문자를 바꿔 넣을 수 있습니다.
예: "장애물이 이 거리 안에 들어오면 감속 시작" 같은 기준값. 배가 A배냐 B배냐에 따라 크기가 다르니
이런 값들을 코드에 박지 않고 파라미터로 빼둡니다.

### yaml 파일
파라미터를 모아 적어두는 **설정 파일**입니다. `.yaml` 확장자를 씁니다.
카메라를 바꾸거나 배를 바꿀 때, 코드가 아니라 이 파일만 고치면 되게 만드는 게 목표입니다.

### 펌웨어 (firmware) / 아두이노 (Arduino)
**아두이노**는 모터를 실제로 돌리는 작은 컴퓨터(마이크로컨트롤러)입니다.
**펌웨어**는 그 아두이노 안에서 도는 프로그램입니다.
노트북(ROS2)이 "이 세기로 모터를 돌려"라는 숫자를 보내면, 아두이노 펌웨어가 그걸 받아 실제 모터 신호로 바꿉니다.

### LiDAR / IMU / GPS / 카메라 (센서들)
- **LiDAR (라이다)**: 빙 돌면서 레이저로 "사방에 물체가 얼마나 떨어져 있나"를 재는 장치. 우리 배의 주된 "눈"입니다.
- **IMU (관성 측정 장치)**: 뱃머리가 **어느 방향**을 향하는지(yaw), 얼마나 기울었는지를 재는 장치.
- **GPS**: 위치(위도·경도)와 **움직인 방향/속도**를 재는 장치. RTK라는 고정밀 방식을 씁니다.
- **카메라**: 부표(빨강·초록 등)의 **색과 방향**을 알아내는 눈. (거리는 안 씁니다 — 이유는 7장에)

### 미션 / wp_mode / FSM
대회는 여러 **미션**(게이트 통과, 도킹, 부표 돌기, 위치 유지 등)으로 이뤄집니다.
지금 배가 **어느 미션 중인지**를 나타내는 숫자가 `/wp_mode`(웨이포인트 모드)라는 토픽으로 흐릅니다.
이 숫자를 순서대로 바꿔가며 미션을 진행하는 장치를 **FSM(상태 기계, Finite State Machine)** 이라고 부릅니다.
(예: `wp_mode = 1`이면 게이트 미션, `7`이면 도킹 미션.)

## 3. 배가 스스로 움직이는 큰 그림

배의 두뇌는 **"보고 → 판단하고 → 움직인다"** 를 1초에 수십 번 반복합니다.

```
   [보기]              [판단하기]                    [움직이기]
  센서들      →     여러 노드가 협력해서        →     모터
 (LiDAR,           "지금 어느 쪽으로 가야                (아두이노가
  IMU, GPS,         하는지" 계산                          실제로 돌림)
  카메라)
```

조금 더 풀면 이렇습니다:

1. **어디가 목표 방향인가?** — GPS 위치와 목표 웨이포인트로 "정북 기준 목표 방위"를 계산하고,
   IMU가 알려주는 "지금 뱃머리 방향"과 비교해 **얼마나 틀어졌는지(`/yaw_error`)** 를 냅니다.
2. **눈앞에 뭐가 있나?** — 카메라가 부표의 방향을, LiDAR가 거리를 알려줍니다.
   미션 노드가 이걸 종합해 "이번 미션에서 가야 할 방향(`/candidate_angle`)"을 제안합니다.
3. **장애물을 피하면서 종합** — `ship_direction`이 LiDAR로 벽·장애물을 보고, 목표 방향과 합쳐서
   **최종 조향각(`/desired_angle`)** 을 정합니다. 위험하면 **감속하거나 멈추라**고도 합니다.
4. **모터로 변환** — `motor_control`이 조향각을 좌우 모터 세기로 바꿔 아두이노에 보냅니다.

이 전체가 매 순간 돌아가고, 그 옆에서 **blackbox**(모든 걸 기록)와 **healthcheck**(고장 감시)가
지켜봅니다.

## 4. 데이터가 흐르는 전체 지도

화살표는 "데이터가 흐르는 방향"입니다. 괄호 안은 그 통로(토픽) 이름입니다.

```
┌─────────────────────────── 센서(눈) ───────────────────────────┐
│  LiDAR ──(/scan)                                                │
│  IMU 드라이버 ──(/imu/yaw_raw)   ← '보정 안 한 날것' 방향          │
│  GPS ──(/ublox_gps_node/fix, .../fix_velocity)                  │
│  카메라 ──(/camera/.../image_raw)                                │
└────────────────────────────────────────────────────────────────┘
        │              │                 │              │
        │              ▼                 │              ▼
        │        ┌───────────┐           │      ┌──────────────────┐
        │        │  yaw_mux  │           │      │ 비전 검출기 3종    │
        │        │ (방향 정리)│           │      │ gate / turn / dock│
        │        └───────────┘           │      └──────────────────┘
        │              │(/imu/yaw)        │              │
        │              │  ← 진짜 뱃머리    │              │(/red_angle, /green_angle,
        │              │     절대방위      │              │ /image_angle, /image_color)
        │              ▼                  ▼              ▼
        │        ┌──────────────────┐  ┌──────────────────────────┐
        │        │ north_goal_angle │  │ 미션 노드 4종             │
        │        │ (목표방위+지오펜스)│  │ ship_gate / ship_turn /   │
        │        └──────────────────┘  │ ship_dock / ship_back     │
        │           │(/north_goal_     └──────────────────────────┘
        │           │  angle_tp,                    │
        │           │  /geofence_state)             │(/candidate_angle)
        │           ▼                               │  ← "이번 미션에서 갈 방향"
        │     ┌────────────────┐                    │
        │     │ ship_goal_angle│                    │
        │     │ (방향 오차 계산)│                    │
        │     └────────────────┘                    │
        │           │(/yaw_error)                   │
        │           │  ← 목표와 현재 방향의 차이       │
        ▼           ▼                               ▼
      ┌──────────────────────────────────────────────────┐
      │              ship_direction                       │
      │  LiDAR로 장애물 보며 목표방향과 합쳐 최종 조향 결정  │
      │  위험하면 감속/정지 (페일세이프)                    │
      └──────────────────────────────────────────────────┘
              │(/desired_angle, /obstacle_distance_array, /failsafe_level)
              ▼
      ┌──────────────────────────┐
      │      motor_control        │
      │  조향각 → 좌우 모터 세기    │
      └──────────────────────────┘
              │(Motor_run)                    │(/motor_reverse ── 다시 yaw_mux로)
              ▼
      ┌──────────────────────────┐
      │  아두이노 펌웨어 → 모터    │
      └──────────────────────────┘

  ┌─────────── 옆에서 지켜보는 도구 (ssf_tools) ───────────┐
  │  blackbox   : 위 모든 값을 CSV 파일로 기록 (구독만)      │
  │  healthcheck: 센서·노드가 살아있나 감시 → /health_ok    │
  └────────────────────────────────────────────────────────┘
```

> **읽는 법**: 위(센서)에서 아래(모터)로 데이터가 흘러내립니다. 왼쪽 줄(방향 계산)과 오른쪽 줄(미션 판단)이
> `ship_direction`에서 만나 하나의 최종 결정이 됩니다.

## 5. 노드 하나하나가 하는 일

### 센서 드라이버 (눈에서 데이터를 읽어오는 노드들)

| 노드 | 하는 일 | 내보내는 토픽 |
|---|---|---|
| `rplidar_ros` | LiDAR를 돌려 사방 거리 측정 | `/scan` |
| `iahrs_driver` | IMU에서 뱃머리 방향을 읽음 (**날것** 상태로) | `/imu/yaw_raw` |
| `ublox_gps` | GPS 위치·속도 | `/ublox_gps_node/fix`, `.../fix_velocity` |
| `realsense2_camera` | 카메라 영상 | `/camera/.../image_raw` |

### yaw_mux — 뱃머리 방향을 "진짜 방위"로 정리
IMU가 주는 `/imu/yaw_raw`는 그대로 쓸 수 없는 **날것**입니다(자세한 이유는 7장 N1).
`yaw_mux`가 이걸 보정해서 **"진짜 뱃머리 절대방위"** 인 `/imu/yaw`로 내보냅니다.
이 `/imu/yaw`를 여러 노드가 구독해서 방향 판단에 씁니다.

- 이름의 뜻: **mux(멀티플렉서)** = "여러 입력 중 하나를 골라 내보내는 장치".
  뱃머리 방향을 알아내는 방법이 여러 개(IMU 단독 / GPS로 보정 / 듀얼 GPS)라, 그중 하나를 골라 쓰기 때문입니다.

### 비전 검출기 3종 (gate / turn / dock) — 카메라로 부표를 봄
카메라 영상에서 색(빨강·초록·흰색)과 도형을 찾아 **부표가 어느 방향에 있는지(각도)** 를 계산합니다.

- `gate` 검출기 → `/red_angle`, `/green_angle` (게이트 미션의 좌우 부표)
- `turn`·`dock` 검출기 → `/image_angle`, `/image_color`
- **이 노드들은 항상 켜져 있고**, `/wp_mode`를 보고 자기 차례일 때만 일합니다(7장 3-4).

### 미션 노드 4종 (ship_gate / ship_turn / ship_dock / ship_back)
각 **미션의 실제 두뇌**입니다. 카메라가 준 부표 방향 + LiDAR 거리를 종합해서
"이번 미션에서 배가 가야 할 방향"을 `/candidate_angle`로 제안합니다.

| 노드 | 미션 | wp_mode |
|---|---|---|
| `ship_gate` | 게이트(문) 통과 | 0, 1 |
| `ship_back` | 부표 옆 위치 유지(station-keeping) | 2 |
| `ship_turn` | 부표 돌기(orbit) | 3 |
| `ship_dock` | 도킹(접안) | 7 |

### north_goal_angle — 목표 방위 + 경계선(지오펜스)
GPS 위치와 다음 목표 지점으로 **"정북 기준 목표 방위"**(`/north_goal_angle_tp`)를 계산합니다.
또 대회장 **경계선을 넘지 않도록** 가상의 벽(`/geofence_state`)을 만들어 냅니다.

- **지오펜스(geofence)**: "지리적(geo) + 울타리(fence)". 실제 벽은 없지만, 경계 밖으로 나가면 실격이므로
  소프트웨어가 **가상의 LiDAR 벽**을 세워 배가 그쪽으로 못 가게 합니다(7장 6a에서 개선).

### ship_goal_angle — 방향 오차 계산
"목표 방위"(`/north_goal_angle_tp`)와 "지금 뱃머리 방향"(`/imu/yaw`)을 비교해
**얼마나 틀어졌는지(`/yaw_error`)** 를 냅니다. 이 오차가 클수록 더 많이 틀어야 한다는 뜻입니다.

### ship_direction — 최종 조향 결정 (가장 중요한 판단 노드)
지금까지의 모든 걸 종합합니다:
- 목표 방향(`/yaw_error`) + 미션 제안(`/candidate_angle`) + 지오펜스 + **LiDAR로 실제 장애물**
- → **최종 조향각(`/desired_angle`)** 을 정합니다.
- 장애물이 가까우면 **감속** 신호를, 센서가 죽으면 **정지** 신호를 함께 냅니다.

- **페일세이프(failsafe)**: "실패해도 안전하게". 센서가 끊기거나 이상이 생기면
  배를 **자동으로 감속·정지**시키는 안전장치입니다. `/failsafe_level`로 단계를 알립니다(7장 3단계).

### motor_control — 조향각을 모터 세기로 변환
`/desired_angle`(어느 쪽으로 얼마나)을 **좌우 모터 각각의 세기**로 바꿔 `Motor_run` 토픽으로 아두이노에 보냅니다.

- 규약: `Motor_run = 오른쪽세기 × 10000 + 왼쪽세기`. 값 **1500이 중립(정지)**, 1500보다 작으면 전진, 크면 후진.
- 장애물이 가까우면 감속하고, 명령이 끊기면(`/desired_angle`이 안 오면) 중립으로 안전하게 멈춥니다.
- 후진 중인지 여부를 `/motor_reverse`로 알려줍니다(7장 N2 후진 게이트에서 사용).

### 아두이노 펌웨어
노트북이 보낸 `Motor_run` 숫자를 받아 실제 모터 신호로 바꿉니다. 회로팀이 담당합니다.
0.5초 이상 명령이 안 오면 스스로 모터를 멈추는 안전장치(watchdog)가 들어 있습니다.

### ssf_tools — 옆에서 지켜보는 도구 (우리가 새로 만든 패키지)
- **blackbox**: 비행기 블랙박스처럼 **모든 신호를 CSV 파일로 계속 기록**합니다.
  나중에 "왜 그때 이상했나"를 데이터로 되짚기 위한 것입니다. **구독만 하고 아무것도 안 바꿉니다.**
- **healthcheck**: 센서·노드가 살아있는지, 미션마다 담당 노드가 제대로 떠 있는지 **2초마다 점검**하고
  `/health_ok`로 알립니다. 출발 전에 "빨간불"을 미리 잡기 위한 것입니다.

## 6. 이 프로젝트의 근본 위험 — "침묵 실패"

우리가 고친 버그의 **대부분이 같은 유형**입니다. 이걸 이해하면 나머지가 다 이해됩니다.

### 침묵 실패란?
**에러 메시지 하나 없이 조용히 안 돌아가는 고장**입니다.
프로그램이 멈추거나 빨간 글씨가 뜨면 오히려 낫습니다 — 눈에 보이니까요.
침묵 실패는 **아무 일도 안 일어난 것처럼 보이는데 실제로는 그 기능이 죽어 있는** 상태입니다.

### 실제로 있었던 사례들

**① 도킹이 1년간 죽어 있었다.**
도킹 노드(`ship_dock`)가 "내 차례는 `wp_mode`가 **9**일 때"라고 설정돼 있었는데,
실제 도킹 미션의 번호는 **7**이었습니다. 숫자가 안 맞으니 도킹 노드는 **1년 내내 한 번도 안 깨어났습니다.**
그런데 에러는 안 났습니다. 배는 멀쩡히 돌아다녔고, 그냥 도킹만 안 했습니다. 아무도 몰랐습니다.

**② 한 통로에 두 명이 말하기.**
2장에서 "한 토픽에 발행 노드는 하나여야 한다"고 했습니다. 이걸 어기면
두 노드가 같은 통로에 다른 값을 번갈아 내보내고, 받는 쪽은 섞인 값을 받습니다. 역시 에러가 안 납니다.

**③ 아무도 안 듣는 통로에 혼자 말하기.**
경계선(지오펜스)을 만들어 발행하는데, 그걸 **구독하는 노드가 하나도 없으면** 경계 방어가 통째로 없는 겁니다.
발행은 잘 되고 있으니 겉보기엔 정상입니다.

### 그래서 우리의 대응 원칙
- **"모르면 아무 말도 안 한다"**: 값이 확실치 않으면 **틀린 값을 내보내느니 침묵**합니다.
  대신 그 침묵이 **조용하지 않도록** — 왜 멈췄는지 로그를 남기고, healthcheck가 잡게 합니다.
- **healthcheck가 기계적으로 감시**: 사람 기억에 맡기지 않습니다. 사람은 잊어버리니까요.

## 7. 우리가 고친 것 전부 (쉽게)

작업은 **0단계 → 6단계**, 그리고 **V(비전)·N(항법) 트랙**, 마지막 **T8(전원)** 순서로 진행했습니다.
각 항목마다 "무엇이 문제였고, 어떻게 고쳤나"를 한 덩어리로 설명합니다.

### 0단계 — 감시 도구부터 (ssf_tools 신설)
**문제**: 배가 왜 이상한지 되짚을 방법이 없었습니다.
**해결**: `blackbox`(전부 CSV 기록)와 `healthcheck`(고장 감시)를 새로 만들었습니다.
둘 다 **구독만** 하므로 기존 시스템을 건드리지 않습니다 — 관찰자입니다.

### 1단계 — ship_goal_angle (방향 오차)
**문제**: 부팅하자마자 "오차 = 0"이라고 내보냈습니다. 실제로는 아직 아무 데이터도 안 왔는데
"완벽히 정렬됨"이라고 거짓말을 한 셈입니다.
**해결**: 데이터가 오기 전에는 발행하지 않게 했습니다. IMU 신호가 끊기면(stale) 발행을 멈춰
아래 노드가 안전하게 감속하도록 했습니다.

- **stale(스테일)**: "신선하지 않은". 마지막으로 데이터가 온 지 너무 오래됐다는 뜻. 끊긴 것으로 간주합니다.

### 2단계 — motor_control (감속 연결 + 안전장치)
**문제 1**: 장애물이 코앞이어도 **감속이 아예 연결돼 있지 않았습니다.** 감속 정보를 만드는 노드는 있는데,
모터 노드가 그걸 안 듣고 있었습니다(위 6장 사례 ③과 같은 유형).
**해결**: `motor_control`이 장애물 거리 정보를 구독해서 가까우면 감속하게 연결했습니다.

**문제 2**: 명령이 끊겨도 마지막 명령대로 계속 달릴 수 있었습니다.
**해결**: **명령 워치독(watchdog)** 추가 — `/desired_angle`이 0.5초 넘게 안 오면 자동으로 중립(정지).

- **워치독(watchdog)**: "감시견". 정해진 시간 안에 신호가 안 오면 스스로 안전 상태로 만드는 장치.

**참고 — 폐기한 것**: TTC(충돌예상시간) 기반 급정지도 검토했지만, 물보라 같은 노이즈에 과민반응해서
멀쩡한데 급정지하는 부작용이 컸습니다. **측정으로 확인하고 버렸습니다.** 점진적 감속만 남겼습니다.

### 3단계 — ship_direction (제어 루프 분리 + 페일세이프)
**문제**: 조향 계산이 **LiDAR 데이터가 올 때만** 실행됐습니다. LiDAR가 잠깐 끊기면
계산 자체가 멈춰서, 페일세이프(안전 정지)조차 작동을 못 했습니다.
**해결**: 조향 계산을 **일정한 주기로 항상 돌아가는 타이머**로 분리했습니다. 이제 LiDAR가 죽어도
"정지하라"는 신호를 계속 내보냅니다.

**페일세이프 3단계**: 센서 상태에 따라 정상 → 감속 → 정지로 나눴습니다. 별도 감시 타이머가
센서 생존을 독립적으로 확인합니다.

**median 필터(중앙값 필터)**: 물보라가 튀어 거리값 하나가 순간 이상해져도 급감속하지 않도록,
주변 값들의 **중앙값**을 씁니다. 측정 결과 물보라 30% 상황에서 가짜 감속이 **36.8% → 8.9%** 로 줄었습니다.
숫자로 효과를 확인하고 기본 ON으로 채택했습니다.

### 6단계 — 미션 노드 4종
**문제와 해결(요약)**:
- `ship_dock`: 도킹 번호 9 → **7**로 수정(6장 사례 ①). 목표 방위 폴백과 **한 몸으로** 고쳐야 해서 함께 처리.
- 지오펜스: 처음엔 "삼각형 모양으로 앞을 칠하는" 방식이었는데, **코너에서 새는** 허점이 있었습니다.
  경계선을 **가상의 LiDAR 벽**으로 바꿔서 이 허점을 막았습니다(수치로 확인).
- `ship_turn`(부표 돌기), `ship_back`(위치 유지): 카메라 거리 대신 LiDAR 거리를 쓰도록 정리.
  `ship_back`은 작년에 자기 이름을 실수로 `ship_turn`으로 등록해 두 노드가 이름 충돌을 일으키던 것도 고쳤습니다.

### V1 — 카메라에서 "거리 의존" 끊기
**문제**: 작년 비전 노드들은 카메라의 **뎁스(depth, 거리 측정)** 기능에 의존했습니다.
그런데 코드 맨 앞에 "뎁스 데이터가 없으면 그냥 리턴(아무것도 안 함)"이라는 한 줄이 있었습니다.
뎁스가 없는 카메라(OAK 등)를 꽂으면 이 한 줄 때문에 **카메라가 영원히 침묵**합니다(에러 없이).
**해결**: 뎁스 의존을 전부 끊었습니다. **카메라는 방향(각도)만, 거리는 LiDAR가** 담당하도록 역할을 나눴습니다.
각도 계산식은 뎁스가 있든 없든 **똑같은 값이 나온다는 걸 수학적으로 증명**하고 바꿨습니다.

### V2 — CLAUDE.md 문서 정정
**문제**: 작업 지침 문서에 "카메라는 OAK로 **확정**, 기존 비전 파일은 **전부 삭제**"라고 적혀 있었는데,
**OAK는 아직 안 샀고 RealSense가 현역**이었습니다. 그대로 실행했으면 **지금 쓰는 유일한 카메라 경로가 죽을 뻔**했습니다.
**해결**: "카메라 중립화"로 방향을 바꿨습니다 — 지금 카메라로 계속 쓰되, 나중에 카메라를 바꿔도 **설정 파일만 고치면** 되게.

### V3 — 화각(hfov)을 설정값으로 빼기
**문제**: 카메라의 **화각(수평으로 얼마나 넓게 보는지)** 이 숫자로 코드에 **박혀** 있었습니다.
카메라를 광각으로 바꾸면 같은 픽셀이 완전히 다른 각도가 돼서(최대 24° 차이) 모든 계산이 무효가 됩니다.
**해결**: 화각을 `hfov_deg` 설정값으로 빼고, 화면 해상도는 **매 순간 실제 영상에서 읽게** 했습니다.
지금 값은 현재 카메라와 **똑같이 동작**하고(오차 0.004°, 무시할 수준), 카메라를 바꿀 땐 이 값 하나만 고치면 됩니다.

- **화각(hfov, horizontal field of view)**: 카메라가 좌우로 얼마나 넓은 각도를 담는지. 광각일수록 넓습니다.

### V4 — 화면 창 끄기 + 최신 프레임만 쓰기
**문제 1**: 코드에 "화면 창을 띄우는" 명령이 있었습니다. 배는 모니터 없이 원격(SSH)으로 돌리는데,
화면이 없는 환경에서 이 명령은 **노드를 죽입니다.**
**해결**: 화면 창을 `debug_view` 설정값으로 감싸고 기본을 꺼짐(false)으로. 필요할 때만 켭니다.

**문제 2**: 카메라 프레임이 밀리면 **오래된 화면 여러 장이 쌓여** 몇 백 ms 전 장면을 보고 조향할 수 있었습니다.
**해결**: 항상 **최신 한 장만** 쓰도록 설정(sensor QoS, depth=1)했습니다.

- **QoS(Quality of Service)**: 토픽으로 데이터를 주고받는 **품질 규칙**. "밀린 옛날 데이터를 쌓아둘까 버릴까",
  "반드시 도착 보장할까 최신 우선일까" 등을 정합니다. 센서 데이터는 "최신 우선, 옛것 버림"이 맞습니다.

### QoS-B — LiDAR도 최신만 쓰기 + 드라이버 저장소에 포함
**문제 1**: LiDAR 구독도 V4와 같은 "옛날 데이터 쌓임" 문제가 있었습니다(1초치가 쌓임).
**해결**: 미션 노드 5곳 전부 최신만 쓰도록 바꿨습니다. 이렇게 하면 페일세이프의 "끊김 감지"도 더 정직해집니다.

**문제 2(작업 중 발견)**: LiDAR·아두이노 관련 드라이버 4개가 **저장소에 실제 파일이 아니라 "링크"로만** 들어 있어서,
다른 컴퓨터에서 내려받으면 **빈 폴더**로 왔습니다.
**해결**: 파일을 저장소에 직접 담아, 어느 컴퓨터에서든 내려받으면 채워져 오도록 했습니다(검증 완료).

### N1 — 뱃머리 방향(yaw)을 제대로 만들기 (yaw_mux 신설)
**문제**: IMU 드라이버가 내보내던 `/imu/yaw`가 사실 **진짜 방위가 아니었습니다.**
- 부팅 순간의 방향을 "0"으로 잡아버려서 **상대적인 각도**가 됐고,
- GPS가 유효하면 IMU를 무시하고 **GPS의 "이동 방향(COG)"** 으로 덮어썼습니다.
  그런데 COG는 **배가 실제로 간 방향**이지 **뱃머리가 향한 방향**이 아닙니다. 정지 중엔 노이즈로 튑니다.
**해결**: 새 노드 `yaw_mux`를 만들어 **`/imu/yaw`의 유일한 발행자**로 삼았습니다.
IMU 드라이버는 날것(`/imu/yaw_raw`)만 내보내고, `yaw_mux`가 이를 보정해 진짜 방위 `/imu/yaw`를 만듭니다.
값이 불확실하면 발행을 멈춥니다(모르면 침묵).

- **yaw(요)**: 뱃머리가 좌우로 향한 **방위 각도**. (배가 어느 쪽을 바라보는가)
- **COG(Course Over Ground, 대지침로)**: GPS가 재는 **실제 이동 방향**. 뱃머리 방향과 다를 수 있습니다(게걸음).

### N2 — GPS로 뱃머리 방향 보정하기 (옵션 B)
**아이디어**: IMU 방향은 안정적이지만 기준이 없고, GPS 이동 방향(COG)은 기준이 있지만 정지 중엔 노이즈입니다.
**둘을 합쳐서**, 배가 똑바로 갈 때 "IMU와 COG의 차이"를 배워두고, 멈췄을 때도 IMU로 방향을 유지합니다.

- **후진 게이트**: 여기에 함정이 있습니다. 배가 **후진만 계속**하면 COG가 뱃머리와 정확히 **180° 뒤집혀서**,
  방향을 자신만만하게 **정반대로 잘못** 배울 수 있습니다. 그래서 `motor_control`이 후진 중임을 알리면
  (`/motor_reverse`) 그동안엔 학습을 멈추게 했습니다.
- 이 보정이 아직 **믿을 만큼 안 배워졌으면**, 0(정북)을 내보내지 않고 **침묵**합니다.

### V5 — 카메라 토픽을 설정값으로 + 카메라 침묵 감지 + 도착 매뉴얼
**문제/해결**:
- 카메라 영상 토픽 이름을 설정값(`image_topic`)으로 뺐습니다. 카메라를 바꿔도 설정 파일만 고치면 됩니다.
- **카메라 침묵 감지(healthcheck)**: 카메라는 USB가 빠져도 에러 없이 조용히 죽습니다. healthcheck가
  영상이 안 오는 걸 감지하게 했습니다.
- **OAK 도착 매뉴얼**(`docs/oak_arrival_runbook.md`): 나중에 새 카메라가 오면 그날 뭘 해야 하는지
  단계별로 적어뒀습니다(연결·설정·화각 실측·색 재보정·검증 순서). 아직 모르는 값(카메라 IP 등)은 빈칸으로 뒀습니다.

### 3-4 — 미션 전환을 "죽였다 살리기"에서 "항상 켜두기"로
**문제**: 작년엔 미션이 바뀔 때마다 비전 노드를 **프로그램째 껐다 켰습니다(subprocess).**
- 전환할 때마다 카메라가 몇 초씩 멈추고, 좀비 프로세스가 남으면 카메라가 잠기기도 했습니다.
- 게다가 **미션 번호 매핑이 틀려서** 게이트(0번)와 도킹(7번) 미션에서 카메라가 아예 안 켜졌습니다(6장 사례 ①의 나머지 절반).
**해결**: 비전 노드를 **항상 켜두고**, 각자 `/wp_mode`를 보고 **자기 차례일 때만 일하게** 했습니다.
전환 시간이 **몇 초 → 33밀리초 이하**로 줄었습니다.

- 이때 조심할 점: `dock`과 `turn` 검출기가 **둘 다 `/image_angle`을 발행**하므로, 둘이 동시에 켜지면
  "한 통로에 두 명"(6장 사례 ②)이 됩니다. 그래서 미션 번호가 **겹치지 않도록** 하고, 그걸 자동 검사로 못박았습니다.

### T8 — 노트북 전원·발열 관리
**주의**: "전원 관리가 제어 지연의 원인"이라고 **단정할 근거는 없습니다**(측정한 적 없음).
다만 **싸고 무해한 보험**이라 넣었습니다.
- `tools/boat_boot.sh`: 배 띄우기 전에 실행하는 스크립트. CPU를 최고 성능 고정, USB 절전 끄기
  (LiDAR/IMU/GPS 같은 **시리얼 장치가 절전으로 끊기는 실재 문제** 방지), 화면 잠금·절전 끄기.
  **되돌릴 수 있는 설정만** 만지므로 재부팅하면 원상복구됩니다.
- healthcheck가 온도·전원을 **경고 로그로만** 알립니다(`/health_ok`에는 안 넣음 — 온도로 배를 멈추면
  "늑대소년"이 되니까). blackbox는 온도·클럭을 CSV에 기록합니다.

## 8. 우리가 일하는 방식(원칙)

이 프로젝트에서 지킨 규칙들입니다. 다른 파트도 알아두면 협업이 쉽습니다.

1. **한 번에 노드 하나만 고친다.** 문제가 생기면 어느 것 때문인지 바로 알 수 있게.
2. **토픽 이름을 바꾸지 않는다.** 통로 이름을 바꾸면 옛 노드와 새 노드가 못 만납니다. 새 기능은 **통로를 추가**합니다.
3. **하드코딩 금지 — 설정값(파라미터)으로.** 배가 두 척(크기 다름)이라 크기·세기 값은 전부 설정 파일로 뺍니다.
   아직 모르는 실측값은 `# ⚠️ 실측 필요` 표시를 달고 임시값을 넣습니다.
4. **추측하지 않는다.** 코드나 문서가 서로 안 맞으면, 실제 코드를 확인하고 **모르면 물어봅니다.**
5. **측정으로 결정한다.** "이게 좋을 것 같다"가 아니라 시뮬·수치로 확인하고 채택하거나 버립니다.
   (TTC 급정지는 버렸고, median 필터는 채택했습니다.)
6. **순수 로직은 따로 떼어 테스트한다.** 배·ROS 없이도 노트북에서 돌려볼 수 있는 계산 부분을 분리해서,
   지금까지 **총 155개의 자동 테스트**가 항상 통과하는지 확인합니다.
7. **커밋마다 무엇을 왜 바꿨는지 기록한다.** 나중에 누가 봐도 이유를 알 수 있게.

- 카메라 중립화: 거리 의존 제거, 화각·토픽 설정화, 화면 창 안전 처리 (V1~V5)
- 뱃머리 방향 정상화: `yaw_mux` 신설, GPS 보정, 후진 게이트 (N1·N2)
- 미션 전환 방식 개선(항상 켜두기) + 미션 번호 매핑 버그 수정 (3-4)
- 전원·발열 관리 (T8)
- 자동 테스트 155개 전부 통과

### 배가 없어서 아직 못 한 것 (실기 대기)
| 항목 | 왜 막혔나 |
|---|---|
| N4 (IMU 지자기 절대방위 조사) | 실제 드라이버·장비로 조사해야 결론이 남 |
| N3 (듀얼 GPS로 방향 측정) | GPS 보드가 아직 없음 |
| `fit_dynamics` (배의 물리 특성 역산) | 실제 주행 데이터(CSV)가 있어야 시작 |

### 배가 뜨면 반드시 확인할 것 (벤치 체크리스트)
소프트웨어로는 못 잡고 **실제로 재봐야만** 아는 값들입니다. `CLAUDE.md`의 "7-2 출발 전 체크리스트"에 정리돼 있습니다.

- **조향 좌/우 부호**: 배선이 반대면 배가 정반대로 갑니다. **가장 흔한 사고.**
- **IMU 절대방위**: 배를 정북에 맞추고 `/imu/yaw`가 0을 읽는지, 시계방향으로 돌렸을 때 값이 커지는지.
- **GPS 속도 방향(gps_vel_frame)**: 정북·정동 두 방향으로 확인(한 방향만으론 부족).
- **화각(hfov_deg)**: 격자·자로 실측 재확인.
- **모터 세기 값들**: 순항 PWM, 후진 PWM 등 실측.

### 그리고 — 소프트웨어에서 더 짤 게 없습니다
배가 뜨기 전까지 소프트웨어 파트에서 할 수 있는 수정은 **사실상 다 끝났습니다.**
남은 건 전부 **실기(실제 배)** 가 있어야 시작됩니다.
