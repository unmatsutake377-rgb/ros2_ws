# Ⅲ. 소프트웨어

## 1) 시스템 구성

### 1.1) 플랫폼
- 선내 연산: {{LAPTOP}} (Ubuntu 22.04, ROS2 Humble). 노트북 1대가 본 선박의 ROS2 스택 전체를 돌리고, DDS 도메인을 따로 둔다.
- 하위 제어: Arduino Mega 2560 R3 — ssf_bridge 가 USB 시리얼로 L/R PWM(µs)을 보내고, 펌웨어가 ESC 2채널(핀 12 좌 / 11 우)로 내보낸다({{ESC_FANOUT}}). 명령 500 ms 무수신 시 펌웨어가 자동 중립.
- 모드 전환은 조종기 스위치뿐(WAIT 0 / MANUAL 1 / AUTO 2). 노트북이 모드를 바꾸는 경로는 두지 않는다.
- 추력 부호: ROS 내부는 <1500 = 전진, 실물 ESC 는 >1500 = 전진. 반전은 ssf_bridge 한 곳(invert_thrust_direction).
- 실행 인자: 본 선박은 `ros2 launch launch_files launch_files.launch.py boat:={{BOAT}}` 로 띄운다. `boat` 는 기본값이 없는 필수 인자로 IMU 장착값 파일 `ssf_heading_{{BOAT}}.yaml` 을 고르고, `gps_config` 는 수신기 설정 파일을 고르며 본 선박은 {{GPS_CFG}} 이다 [근거: src/launch_files/launch/launch_files.launch.py:74-79] [근거: docs/기준/1번배_구성.md:14-15]. `boat` 가 빠지거나 잘못되면 launch 가 거부되고, 장착값 파일이 없으면 어떤 노드도 띄우기 전에 launch 전체를 세운다 [근거: src/launch_files/launch/launch_files.launch.py:26-32] [근거: src/launch_files/launch/launch_files.launch.py:84-86].

## 2) 센서 처리

### 2.1) 좌표계·헤딩
헤딩은 웨이포인트 목표 방위와 빼서 조향 오차를 만드는 기준값이고, 지오펜스 광선의 방향도 정한다 [근거: src/ship_goal_angle/ship_goal_angle/ship_goal_angle.py:112] [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:35]. 각도 규약은 전 구간 같다: 0~360°, 0° = 진북, 시계방향 증가 [근거: src/ssf_heading/ssf_heading/heading_logic.py:20-21]. 올해는 드라이버가 보정 없는 원시값을 `/imu/yaw_raw` 로만 내고, 새 패키지 `ssf_heading` 의 `yaw_mux` 가 보정해 `/imu/yaw` 를 단독 발행한다 [근거: src/ssf_heading/ssf_heading/yaw_mux.py:1-14]. 한 토픽에 발행자가 둘이면 보정 전·후 값이 번갈아 나와도 ROS 는 오류를 내지 않으므로, 대회 launch 가 드라이버의 `yaw_topic` 을 명시하고 드라이버는 `/imu/yaw` 로 설정되면 경고한다 [근거: src/launch_files/launch/launch_files.launch.py:109-113] [근거: src/iahrs_driver_ros2-main/iahrs_driver/src/iahrs_driver.cpp:92-96].

| 토픽 | 발행 → 구독 | 주기 |
|---|---|---|
| `/imu/yaw_raw` | iahrs_driver → yaw_mux | 100 Hz [근거: src/iahrs_driver_ros2-main/iahrs_driver/src/iahrs_driver.cpp:213] |
| `/ublox_gps_node/fix_velocity`, `/motor_reverse` | ublox_gps_node, motor_control → yaw_mux (COG 추정, 후진 게이트) | 수신기 측, 0.05 s [근거: src/ssf_heading/config/ssf_heading.yaml:82-83] [근거: src/motor_control/motor_control/motor_control.py:90] |
| `/imu/yaw`, `/heading_status` | yaw_mux → ship_goal_angle, north_goal_angle, ship_turn / healthcheck | 50 Hz / 변화 시·1 s [근거: src/ssf_heading/config/ssf_heading.yaml:16] [근거: src/ssf_heading/ssf_heading/yaw_mux.py:185-190] |
| `/yaw_error` | ship_goal_angle → ship_direction | 20 Hz [근거: src/ship_goal_angle/config/ship_goal_angle.yaml:4] |

표 Ⅲ-2 헤딩 토픽 흐름과 주기

**보정식과 소스.** yaw_mux 는 ψ = wrap360(s·ψ_raw + `mount_offset_deg` + δ) 를 적용한다(s = −1 은 `invert_yaw`) [근거: src/ssf_heading/ssf_heading/heading_logic.py:87-93]. 편각 δ 는 자기북 기준 소스에만 넣는다. 듀얼 GPS·COG 는 이미 진북 기준이라 편각을 더하면 약 8° 이중 보정이 된다 [근거: src/ssf_heading/ssf_heading/heading_logic.py:39-46]. 기본 소스 `imu_relative` 는 원시 yaw 에 고정 오프셋을 더하며, 기준축이 임의라 편각도 오프셋이 흡수한다 [근거: src/ssf_heading/config/ssf_heading.yaml:14] [근거: src/ssf_heading/ssf_heading/heading_logic.py:32,42]. 대안 `cog_offset` 은 GPS COG 와 IMU 의 차 e_i = COG − ψ_imu 를 단위벡터로 누적(반감기 감쇠)해 오프셋을 추정하고, 신뢰도 R = |Σ|/n 과 표본 수가 기준을 넘을 때만 발행한다. 산술평균은 359° 와 1° 를 180° 로 만들어 쓰지 않는다 [근거: src/ssf_heading/ssf_heading/heading_logic.py:157-158] [근거: src/ssf_heading/ssf_heading/heading_logic.py:221-265]. 저속·급선회·후진 표본은 버린다. 후진만 이어지면 180° 틀린 채 R = 1.0 으로 수렴하므로 `/motor_reverse` 로 따로 막는다 [근거: src/ssf_heading/ssf_heading/heading_logic.py:164-170] [근거: src/ssf_heading/ssf_heading/heading_logic.py:203-219]. 이 추정치에는 그날의 평균 게걸음각이 섞인다 [근거: src/ssf_heading/ssf_heading/heading_logic.py:150-155]. `dual_gps`·`imu_absolute` 는 입력이 배선되지 않아 0 대신 발행을 멈춘다 [근거: src/ssf_heading/ssf_heading/heading_logic.py:361-371].

**본 선박 장착값.** 선박 고유 값은 `invert_yaw`·`mount_offset_deg` 두 개뿐이며 `ssf_heading_{{BOAT}}.yaml` 에 둔다. launch 는 공통 → 선박 파일 순서로 넘겨 뒤 파일 값이 이기고, 벤치 실행도 같은 `boat` 인자를 요구한다 [근거: src/launch_files/launch/launch_files.launch.py:11-18] [근거: src/ssf_heading/launch/ssf_heading.launch.py:56-58]. 선박 파일에 두 키 외의 값(안전 스위치 등)이 들어가거나 `mount_offset_deg` 를 정수로 적으면(yaw_mux 부팅 즉시 사망) 정적 테스트가 잡는다 [근거: src/ssf_heading/config/ssf_heading_A.yaml:8-14] [근거: src/ssf_heading/test/test_boat_config.py:7-14].

| 이름 | 값 | 정한 근거 |
|---|---|---|
| `heading_source` | `"imu_relative"` | 입력 조건 없이 발행되는 소스. 오타면 기동 시 예외 [근거: src/ssf_heading/ssf_heading/yaw_mux.py:44-48] |
| `period_sec` / `stale_sec` | 0.02 s / 0.5 s | stale 은 소비자 IMU 한계와 같다 [근거: src/ssf_heading/config/ssf_heading.yaml:16-17] [근거: src/ship_goal_angle/config/ship_goal_angle.yaml:6] |
| `invert_yaw` / `mount_offset_deg` (선박 고유) | false / 0.0 | `ssf_heading_{{BOAT}}.yaml` 에만 둔다 [근거: src/ssf_heading/config/ssf_heading_A.yaml:25-30] |
| `magnetic_declination_deg` | 0.0 | `imu_absolute` 에만 적용 [근거: src/ssf_heading/config/ssf_heading.yaml:27-31] |

| `cog_min_samples` / `cog_min_resultant` / `cog_half_life_sec` | 30 / 0.9 / 60 s | 감쇠로 생기는 표본 상한과의 조합을 기동 시 검사 [근거: src/ssf_heading/config/ssf_heading.yaml:48-50] [근거: src/ssf_heading/ssf_heading/yaw_mux.py:102-108] |
| `cog_require_reverse_gate` | true | 대회값 고정, 공통 파일에만 [근거: src/ssf_heading/config/ssf_heading.yaml:70] |

표 Ⅲ-3 헤딩 파라미터와 정한 근거

헤딩을 믿을 수 없으면 0 같은 대체값 대신 발행을 멈춘다. 원시 yaw 가 0.5 s 넘게 끊기면 `/imu/yaw`·`/yaw_error` 가 차례로 멈추고 지오펜스는 빈 배열을 내며, 이 침묵을 `ship_direction` 이 잡는다(Ⅲ-5) [근거: src/ssf_heading/ssf_heading/heading_logic.py:389-395] [근거: src/ship_goal_angle/ship_goal_angle/ship_goal_angle.py:95-101].

### 2.2) GPS RTK
GPS 처리는 외부 드라이버 `ublox_gps`·`ntrip_client` 와 우리 노드 `north_goal_angle` 로 이뤄진다. `north_goal_angle` 은 다음 웨이포인트 방위 `/north_goal_angle_tp`, 임무 번호 `/wp_mode`, 경계 광선 `/geofence_state` 를 0.5 s 주기로 낸다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:180-184] [근거: src/north_goal_angle/config/north_goal_angle.yaml:4]. 설계 원칙은 "모르면 입을 다문다"이다.

#### 수신기와 RTK 보정
단독 측위 오차(±3~5 m)가 부표 간격보다 커서 웨이포인트에는 RTK 가 필요하다 [근거: docs/절차/웨이포인트_녹화절차.md:31]. 보정은 인터넷 NTRIP 으로 받아 UHF 안테나를 달지 않는다 [근거: docs/전달용/하드웨어_배치_요구사항.md:85]. `ntrip_client` 는 수신기 드라이버보다 2.0 s 늦게 뜨고, 계정은 저장소 밖(~/.ssf/) 파일에서 읽는다. 파일이 없으면 예외 없이 그 노드만 생략한다 — 예외가 나면 메인 launch 전체가 내려가기 때문이다 [근거: src/launch_files/launch/launch_files.launch.py:135-138] [근거: src/ntrip_client/launch/ntrip_client_launch.py:13-16]. 세션이 끊기면 5 s 간격 최대 10회 재연결한다 [근거: src/ntrip_client/launch/ntrip_client_launch.py:101-105]. 외부 드라이버는 설정만 바꿨다: 해상 모델 `sea`, EEPROM 저장 없이 RAM 적용, ZED-F9P 용 이동국 파일 신설, 메인 launch 의 `gps_config` 전달 [근거: src/ublox/ublox_gps/config/c94_m8p_rover.yaml:21] [근거: src/ublox/ublox_gps/config/zed_f9p_rover.yaml:5-6] [근거: src/launch_files/launch/launch_files.launch.py:125-130].

#### fix 검증·필터·신선도
드라이버는 fix 가 없어도 status −1, 위경도 0.0 인 메시지를 계속 내므로, fix 상태를 확인하지 않으면 위도 0°·경도 0° 를 기준으로 한 잘못된 방위가 나온다 [근거: src/north_goal_angle/north_goal_angle/gps_guard.py:3-13]. 이를 막기 위해 fix 를 다섯 층으로 거른다.

| 공분산 | `position_covariance[0]` 이 임계 초과면 그 프레임만 버림. 0 이하는 정보 없음으로 통과 [근거: src/north_goal_angle/north_goal_angle/gps_filter.py:43-45] | `gps_cov_threshold` 2.0 |
| 점프 | 직전 fix 대비 속도가 상한 초과면 순간이동(멀티패스)으로 버림 [근거: src/north_goal_angle/north_goal_angle/gps_filter.py:47-55] | `gps_max_speed_mps` 15.0 m/s |

표 Ⅲ-4 GPS fix 검증·필터·신선도 단계

필터가 버리는 것은 한 프레임뿐이며 fix 상실로 보지 않는다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:288-297]. 신선도 2.5 s 는 1 Hz 에서 한 프레임 빠짐(2.0 s)은 견디고 두 프레임부터 stale 로 보는 값이다.

#### 웨이포인트 설정 — 대회장 녹화
대회장 좌표는 공개되지 않으므로 현장에서 직접 찍는다. 단독 측위 오차(±3~5 m)는 부표 간격보다 커서 RTK FIXED 가 잡힌 뒤에만 녹화하며, NTRIP 마운트포인트는 측정 장소 기준 30 km 이내로 고른다(지난 야외 시험에서 대회장 기준으로 고른 기준국이 시험 장소에서 199 km 떨어져 RTK 가 잡히지 않은 적이 있다). 녹화기 waypoint_recorder 는 한 표본이 아니라 최근 2 s 의 유효 fix 를 평균해 한 점으로 삼고(fix 가 없으면 거부), 저장 전에 웨이포인트 로더와 같은 검증(좌표 범위·mode)을 거치며, 기존 waypoints.yaml 은 건드리지 않고 새 파일에 써서 오입력을 되돌릴 수 있게 한다. 새 파일은 launch 인자로 먼저 태워 확인한 뒤 확정되면 실전 파일로 복사한다. 코스(남북 약 106 m, 동서 약 65 m) 전역을 빠짐없이 찍고, 파일에서는 좌표만 바꾸고 mode 와 순서는 그대로 둔다(미션 진행 순서이기 때문이다). [근거: docs/절차/웨이포인트_녹화절차.md] [근거: src/north_goal_angle/north_goal_angle/waypoint_recorder.py] [근거: src/north_goal_angle/config/waypoints.yaml]

| 단계 | 하는 일 | 확인 |
|---|---|---|
| ① RTK | NTRIP 접속(휴대폰 핫스팟), 마운트포인트는 소스테이블에서 측정 장소 30 km 이내로 선택 | navpvt carrSoln = 2 (FIXED), healthcheck GPS ✅ |
| ② 접속 | 물가 노트북 → SSH(Tailscale) → 배 노트북에서 waypoint_recorder 실행 | 프롬프트 "Enter = 캡처" |

표 Ⅲ-5 대회장 웨이포인트 녹화 절차 (waypoint_recorder)

#### 웨이포인트와 LOS·ILOS 유도
웨이포인트는 `config/waypoints.yaml` 의 `{구역, lat, lon, mode, dwell}` 목록이다. 로더가 좌표 범위(빈칸 0.0, 위경도 뒤바뀜)·mode·dwell 을 검사해 틀리면 몇 번째 항목이 왜 틀렸는지 남기고 노드를 세운다 [근거: src/north_goal_angle/north_goal_angle/waypoint_loader.py:42-91] [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:224-248]. [근거: src/north_goal_angle/north_goal_angle/waypoint_recorder.py:86-112].

목표 방위로 바로 향하면 조류에 밀렸을 때 경로로 돌아오지 못하고 비스듬히 접근하므로 [근거: src/north_goal_angle/north_goal_angle/los_logic.py:3-6], 이전 웨이포인트 P 에서 목표 W 로 가는 경로선을 기준으로 한다.
- 경로선 이탈: XTE = d(P, 배)·sin(ψ(P→배) − ψ(P→W)), 양수는 오른쪽으로 밀린 것 [근거: src/north_goal_angle/north_goal_angle/los_logic.py:45-56].
- 전방주시: L = clamp(1.2·v, 2.0, 6.0) m. 빠를수록 멀리 봐 완만하게 복귀한다 [근거: src/north_goal_angle/north_goal_angle/los_logic.py:38-42] [근거: src/north_goal_angle/config/north_goal_angle.yaml:7-9].
- 목표 방위: ψ_d = ψ(P→W) − atan2(XTE + k_i·I, max(0.1, L)) [근거: src/north_goal_angle/north_goal_angle/los_logic.py:67-71].
- ILOS 적분: I ← I + XTE·Δt, |I| ≤ 50(anti-windup), k_i = 0.02. 조류·바람처럼 계속 미는 외란을 상쇄한다. 웨이포인트를 넘길 때 P 를 갱신하고 I 를 0 으로 되돌린다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:479-481] [근거: src/north_goal_angle/config/north_goal_angle.yaml:10-11] [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:548-549].
- 도착 반경: 도킹(mode 7) 2.0 m, 그 외 속도 2 m/s 미만 2.5 m, 5 m/s 미만 3.5 m, 그 이상 4.5 m. 반경 안에 dwell 초 머무르면 다음 웨이포인트로 넘어간다 [근거: src/north_goal_angle/north_goal_angle/los_logic.py:75-83] [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:538-554].

`require_boat_mode_auto` 가 true 이면 RC 모드가 AUTO 일 때만 웨이포인트가 전진하고, 그 전까지 타이머·dwell·적분·경로 시작점을 초기화해 AUTO 전환 순간 WP0 부터 시작한다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:498-511].

#### 지오펜스 생성
경계 최근접점 방향으로 원뿔을 막으면 사각 경기장 모서리에서 대각선을 향한 배의 정면이 두 원뿔 사이로 열린다. 광선 방식은 정면 경계 거리가 그대로 벽이 되고 튜닝 파라미터도 없다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:18-25]. 상대방위 −80°~+80° 를 1° 간격으로, 절대 방위 `/imu/yaw` + 상대방위 방향 광선과 경계 폴리곤 변의 최근접 교점 거리(30 m 초과는 inf)를 구해 `[−80, 1, r0 … r160]` 으로 낸다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:391-401] [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:409-410]. fix 없음·stale, `/imu/yaw` 0.5 s 초과, 배가 이미 경계 밖이면 빈 배열을 낸다. 헤딩이 얼면 "없는 벽"이 배를 가두고, 이미 밖이면 경계가 복귀로를 막기 때문이다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:350-401]. 부팅 5 s 뒤 구독자가 0 이면 ERROR 를 낸다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:413-420]. 대회장 경계 좌표가 아직 없어 `geofence_polygon` 은 비어 있다(꺼짐) [근거: src/north_goal_angle/config/north_goal_angle.yaml:39-41].

### 2.3) LiDAR 처리
`rplidar_node` 의 `/scan` 은 `ship_direction` 이 받아 갭 선택 회피(Ⅲ-4.4), 감속 신호, 지오펜스 병합, 센서 감시(Ⅲ-5)에 쓴다 [근거: src/ship_direction/ship_direction/ship_direction.py:262-276]. 회전수는 드라이버 파라미터로 바꿀 수 없어 개체마다 실측값이 다르다. {{BOAT_NO}}는 {{LIDAR}} 이다 [근거: docs/기준/CLAUDE_상세.md:117-125] [근거: docs/문제와작업/라이다_고장진단_20260818.md:76-77]. 이 절은 신호 처리만 다룬다.

- **수신과 계산의 분리.** `scan_callback` 은 스캔을 저장만 하고 계산·발행은 10 Hz 타이머 `control_cb` 가 한다. 그래서 LiDAR 가 끊겨도 발행은 계속된다 [근거: src/ship_direction/ship_direction/ship_direction.py:74-79] [근거: src/ship_direction/ship_direction/ship_direction.py:515-547]. `/scan` 구독은 BEST_EFFORT·depth 1 로 묵은 스캔이 쌓이지 않게 한다 [근거: src/ship_direction/ship_direction/ship_direction.py:62-66].
- **정면 정렬.** LiDAR 프레임 80° 를 선수 정면으로 두고 0~160°(정면 ±80°)만 쓴다. 인덱스는 메시지의 Δθ 로 매번 계산하므로 각분해능이 다른 두 개체에 같은 코드가 돈다 [근거: src/ship_direction/ship_direction/ship_direction.py:23] [근거: src/ship_direction/ship_direction/ship_direction.py:723-735].
- **inf·nan 처리.** 측정 없음은 회피 마스크에서는 빈 셀, 빈 구간 가장자리 거리로는 `detection_distance`, 감속 신호에서는 유효점 제외로 다룬다 [근거: src/ship_direction/ship_direction/ship_direction.py:755-761] [근거: src/ship_direction/ship_direction/ship_direction.py:26-32] [근거: src/ship_direction/ship_direction/failsafe.py:53-56]. `detection_distance` 는 기본 3.0 m, 게이트 구간(`wp_mode` 0·1) 2.0 m 다 [근거: src/ship_direction/ship_direction/ship_direction.py:385-389].
- **감속 신호의 공간 median.** 인덱스마다 창 [i−2, i+2](커널 5)의 유효점이 3개 이상이면 위쪽 중앙값을, 미만이면 고립 반사로 버리고, 그 최소값과 각도를 `/obstacle_distance_array` 로 낸다 [근거: src/ship_direction/ship_direction/failsafe.py:31-35] [근거: src/ship_direction/ship_direction/ship_direction.py:578-584]. 이 필터는 감속 신호에만 걸고 회피 마스크에는 걸지 않아 회피 접촉 성능을 바꾸지 않는다 [근거: src/ship_direction/ship_direction/ship_direction.py:154-160]. 시뮬(시드 20, 물보라 30%)에서 가짜 감속이 36.8% → 8.9% 로 줄었고 접촉은 전 조건 0 이었다 [근거: src/ship_direction/config/ship_direction.yaml:39]. 버린 점 수는 `/obstacle_reject_count` 로 내 물보라 대리 지표로 기록한다 [근거: src/ship_direction/ship_direction/failsafe.py:17-20].
- **지오펜스 병합과 경계 정지.** 자율 회피 구간에서는 셀마다 대응하는 경계 광선을 찾아 ranges = min(real, geofence) 로 병합한다. 병합이 마스크 생성 전이라 경계도 장애물과 같은 팽창·갭 선택을 거친다 [근거: src/ship_direction/ship_direction/ship_direction.py:619-631]. 빈 배열이나 2.0 s 넘게 묵은 경계는 병합하지 않는다 [근거: src/ship_direction/ship_direction/ship_direction.py:603-609]. 임무 노드가 조향하는 후보각·제자리 선회 구간은 병합할 마스크가 없어 하드 가드를 둔다. 최근접 경계가 2.0 m 안이고 그 방위가 의도한 진행 방향(후보각, 선회는 0°) ±60° 안이면 STOP_HOLD 를 낸다 [근거: src/ship_direction/ship_direction/ship_direction.py:661-676] [근거: src/ship_direction/ship_direction/ship_direction.py:694-699].

| 이름 | 값 | 정한 근거 |
|---|---|---|
| `detection_distance_default` / `_gate` (`gate_wp_modes` [0, 1]) | 3.0 / 2.0 m | 시뮬: 1.8 이면 8/8 충돌. 게이트는 좁아 3.0 이면 접촉 증가 [근거: src/ship_direction/config/ship_direction.yaml:57-60] |
| `obst_median_kernel` | 5 | 가짜 감속 36.8% → 8.9%. 군집 물보라면 7/9 검토 [근거: src/ship_direction/config/ship_direction.yaml:41-43] |
| `geofence_stale_sec` | 2.0 s | north 주기 0.5 s 의 4배 [근거: src/ship_direction/config/ship_direction.yaml:29] |
| `geofence_stop_margin_m` / `_cone_deg` | 2.0 m / 60° | 후보각 구간 경계 이탈 방지 [근거: src/ship_direction/config/ship_direction.yaml:33-34] |

표 Ⅲ-7 영상 처리 파이프라인 단계

![그림 Ⅲ-2 영상 처리 단계 — 실제 OAK 화면에 검출기와 같은 함수·설정값(vision.yaml)을 단계별로 적용. 하늘색 두 선은 검출 높이 띠, 글자와 초록 윤곽은 촬영 때 판정 도구가 그린 표시 (tools/vision_pipeline_figure.py)](vision_pipeline.png)

- **거리는 쓰지 않는다.** 카메라는 방위각만 내고 거리는 LiDAR 전방 섹터 최소거리로 얻는다(핀홀 거리 추정의 실해역 오차 회피) [근거: src/color_shape_detector/color_shape_detector/basic_image_subscribergate.py:70-72]. 방위각은 화면 왼쪽이 + 이고 왜곡 보정은 하지 않는다. 화각은 해상도별 센서 크롭에 딸려 있어 `color_profile` 을 바꾸면 `hfov_deg` 도 바꾼다 [근거: src/color_shape_detector/color_shape_detector/vision_geom.py:73-77] [근거: src/color_shape_detector/config/vision.yaml:31-40].
- **확인과 유예.** 창 안 다수결이 아니라 이번 프레임 key 가 최근 창에 N 회 이상일 때만 확정해, 흰색 각도를 빨강으로 잘못 내는 일이 없다 [근거: src/color_shape_detector/color_shape_detector/dock_logic.py:112-114]. 미확정이면 2.0 s 안의 마지막 확정값을, 아니면 무효값 10000.0 을 낸다. 침묵하면 소비자가 "사라졌다"로 읽기 때문이다 [근거: src/color_shape_detector/color_shape_detector/basic_image_subscribergate.py:206-216].
- **모드 게이팅.** 판정은 콜백 맨 앞이라 비활성 검출기는 영상 변환도 하지 않는다. turn 과 dock 이 같은 `/image_angle` 을 내므로 담당 모드가 겹치지 않는지, 첫 발행이 게이트 뒤인지를 정적 테스트가 검사한다 [근거: src/color_shape_detector/color_shape_detector/mode_gate.py:78-103] [근거: src/color_shape_detector/test/test_detector_gate_order.py:1-5].
- **카메라.** 자율 비전은 OAK-1 PoE, 수동 조종 화면은 D455 로 역할을 나눈다. OAK-1 PoE 는 뎁스가 없지만 거리는 LiDAR 가 재고, D455 도 뎁스를 켜면 USB 에서 떨어져(2분간 13회) 끄고 쓰므로 잃는 기능이 없다 [근거: src/launch_files/launch/launch_files.launch.py:216-221]. 진동에 강한 고정초점, HFOV 45° 인 32MP 대신 69° 표준형을 골랐다 [근거: docs/전달용/구매_목록.md:76].
- **OAK 화각 실측({{BENCH_BOAT}}).** 빨간 원 두 장(중심 간격 1.00 m)을 렌즈에서 2.40 m 떨어진 벽에 붙이고 60 프레임의 원 중심 간격 213.8 px(표준편차 0.27 px)으로 fx = 간격 × 거리 / 1.00 m 를 구해 **63.9°** 를 얻었다. 카메라 공장 보정값(camera_info fx 513.5)에서 나온 63.87° 와 0.01° 차이다. 스펙 69° 는 4:3 센서 전체 값이고 1080P(16:9)는 가로도 일부 잘린다 [근거: docs/절차/oak_arrival_runbook.md:110-121].
- **해상도 설정의 함정.** 드라이버에 640×360 만 주면 1080P 를 2/3 로 줄인 1280×720 의 **가운데만 잘라** 화각이 40.3° 가 된다(그림 Ⅲ-3 a). 그런데 camera_info 는 잘린 화면에서도 같은 fx 를 내므로 오류 없이 방위각이 틀린다. ISP 축소 비율 1/3 을 함께 줘 1080P 전체를 640×360 으로 줄인다(그림 Ⅲ-3 b) [근거: docs/절차/oak_arrival_runbook.md:122] [근거: tools/oak/oak_640x360_full.yaml].

- **방위각 검증.** 마스트 위 OAK 에서 벽까지 2.0 m, 게이트 검출기 `/red_angle` 을 표식 위치별로 읽었다. 정중앙 +1.34°(흔들림 0.02°), 왼쪽 1.00 m +26.99°(기하 기대 +27.63°), 화면 왼쪽 끝 1.10 m +28.91°(기대 +29.83°)로 **왼쪽 = + 부호**가 맞고 오차는 1° 안이다. 렌즈 왜곡을 보정하지 않아 생기는 오차는 계산상 최대 약 1° 다 [근거: docs/절차/oak_arrival_runbook.md:127-139] [근거: docs/절차/oak_arrival_runbook.md:124].

## 3) 전체 임무 상태기계
/wp_mode 값이 담당 노드를 정하고, 검출기는 해당 모드에서만 발행한다. /wp_mode 2 s 이상 stale 이면 검출기 발행 정지. `/wp_mode` 를 바꾸는 것은 `north_goal_angle` 하나다. 현재 웨이포인트의 mode 를 매 주기 내고, 도착(반경 안 dwell) 또는 시간 초과로 다음 웨이포인트로 넘어갈 때 값이 바뀐다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:453] [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:490]. fix 가 없어도 `/wp_mode` 는 계속 낸다. 멈추면 검출기 3종이 모두 꺼지기 때문이다. 대신 fix 없이는 도착 판정을 하지 않는다 [근거: src/north_goal_angle/north_goal_angle/north_goal_angle.py:458-460].

| wp_mode | 임무 | 임무 노드 | 검출기 → 발행 | dwell / 시간 초과 |
|---|---|---|---|---|
| 0, 1 | 게이트 시작·끝 (항로추종) | ship_gate | gate → /red_angle, /green_angle | 3 s / 120 s |
| 2 | 위치유지 | ship_back | turn(white) → /image_angle | 3 s / 120 s |
| 3 | 탐색 (부표 앞 위치유지) | ship_back (옵션: ship_turn 선회) | turn(red) → /image_angle | 3 s / 90 s |
| 5 | 장애물 회피 | 없음 — ship_direction 순수 회피 | 없음 | 50 s / 120 s |
| 7 | 도킹 | ship_dock | dock → /image_angle | 60 s / 150 s |
| 8 | 토너먼트 자율 회피 | 없음 | 없음 | 60 s / 없음 (마지막 WP) |

표 Ⅲ-8 wp_mode 별 임무·담당 노드·시간 초과

dwell 은 `waypoints.yaml`, 시간 초과는 WP 하나당 값으로 `wp_timeout_modes`·`wp_timeout_sec` 에 둔다 [근거: src/north_goal_angle/config/waypoints.yaml:20-30] [근거: src/north_goal_angle/config/north_goal_angle.yaml:35-36]. 시간 초과는 위치와 무관하게 다음 웨이포인트로 넘기는, GPS 가 죽어도 진행하는 유일한 수단이다 [근거: src/north_goal_angle/config/north_goal_angle.yaml:27-29]. 도킹 150 s 는 ship_dock 선형 최악 약 129 s 와 dwell 60 s 보다 크게 잡았다 [근거: src/north_goal_angle/north_goal_angle/wp_timeout.py:29]. 값이 비었거나 0 이하·NaN·길이 불일치면 출발 전에 노드를 세운다 [근거: src/north_goal_angle/north_goal_angle/wp_timeout.py:43-54].

특수 명령 코드(/candidate_angle·/desired_angle): 5000 우선회, 6000 좌선회, 20000 미션 없음 → 전진 폴백(모드 5·8 만), 50000 정지. 20000 은 담당 임무 노드가 없는 모드 5·8 에서 `north_goal_angle` 이 낸다.

### 4.1) 항로추종 — ship_gate
- 검출기가 빨강·초록 부표 방위각을 내면 두 방위의 중간을 목표로, 한쪽만 보이면 그쪽 기준 오프셋, 둘 다 없으면 20000(미션 없음)을 내 GPS 웨이포인트 항법에 맡긴다(3분기).
- 거리는 LiDAR 전방 섹터 최소거리. 통과 수는 /gates_passed 로 기록.
- 실제 노드 코드로 돌린 항로추종 시뮬레이션(부호·통과 카운트 수정 전/후)은 Ⅲ-6.2(그림 Ⅲ-18)에 둔다.

### 4.2) 위치유지 — ship_back
- 흰 부표 방위는 검출기 turn(white), 거리는 그 방위의 LiDAR 최소거리로 잰다. 목표 거리 2.5 m 에서 ±0.4 m 데드밴드를 벗어나면 전진·후진으로 되돌리고(bang-bang), 규정대로 5 m 이내에 5 s 연속 머물면 완료한다. 부표를 못 보면 GPS 웨이포인트로 접근한다 [근거: src/ship_back/ship_back/hold_logic.py].

### 4.3) 탐색 — ship_back (부표 앞 위치유지)
- 2026 안내문 기준 탐색은 특정 색 부표를 찾아 그 위치에서 위치유지하는 미션이다. 검출기 turn 이 모드 3 에서 빨강 부표 방위를 내면 ship_back 이 모드 2 와 같은 로직으로 LiDAR 거리 2.5 m 를 유지한다(launch 인자 `search_behavior` 기본 hold: 모드 2·3 모두 ship_back 담당, ship_turn 은 침묵) [근거: src/launch_files/launch/launch_files.launch.py:45-70] [근거: docs/문제와작업/계약서_탐색hold스위치_20261102.md].
- 2025 규정의 부표 선회(ship_turn: 빨강·초록 시계, 흰색 반시계, 선회 자세에서 부표가 카메라 시야 밖이라 LiDAR 로 방위 추적)는 `search_behavior:=orbit` 옵션으로 남겨 두었다. 색 토픽은 `/image_color` 로 고정(개명하면 영구 정지한 이력) [근거: src/ship_turn/ship_turn/ship_turn.py].

### 4.4) 장애물 회피 — ship_direction
`/candidate_angle` 이 20000(미션 없음)이면 LiDAR 갭 선택으로 조향각을 정한다 [근거: src/ship_direction/ship_direction/ship_direction.py:722]. 그 밖의 명령은 먼저 처리한다. 50000 이면 STOP_HOLD, 5000·6000 은 그대로 통과, 일반 후보각은 LiDAR 각 격자(정면 80)로 옮기고 0~160° 밖이면 STOP_HOLD 다 [근거: src/ship_direction/ship_direction/ship_direction.py:686-689] [근거: src/ship_direction/ship_direction/ship_direction.py:702-720].

LiDAR 스캔에서 안전 구간(연속 빈 셀)을 찾는 순서는 다음과 같다.
- 이진 마스크: 병합 거리 r 이 `detection_distance` 미만이면 장애물 [근거: src/ship_direction/ship_direction/ship_direction.py:754-761].
- 잡음 정리: 길이 `int(n × max_spike_ratio)` 셀 이하 장애물 구간을 지우고 경계 `border_margin` 셀을 깎는다. 고립 1~3셀은 사라지고 회피 거리의 실제 부표(약 30셀)는 남는다 [근거: src/ship_direction/ship_direction/ship_direction.py:830-861] [근거: src/ship_direction/test/test_avoidance_filters.py:105-143].
- 팽창: 장애물 구간 최근접 거리 r_min 으로 m = max(1, round(atan((half_width + clearance)/r_min)/Δθ)) 셀씩 양옆을 넓힌다 [근거: src/ship_direction/ship_direction/ship_direction.py:881-897].
- 폭 판정: 빈 구간 (s, e) 마다 호 길이 arc = Δθ·r_edge·(e−s) 가 min_required_width = half_width×2 + clearance 이상인 구간만 후보로 남긴다. r_edge 는 양 끝 중 가까운 쪽 거리다. 먼 쪽으로 재면 실제보다 넓게 보이기 때문이다 [근거: src/ship_direction/ship_direction/ship_direction.py:39-50] [근거: src/ship_direction/ship_direction/ship_direction.py:786-788].
- 후보 선택: 각 후보 구간 안으로 목표 방위를 잘라 넣어(clamp) 목표에 가장 가까운 각을 고르고(동률이면 호가 긴 구간), 그 각을 /desired_angle 로 고정주기 발행한다 [근거: src/ship_direction/ship_direction/ship_direction.py:799-808] [근거: src/ship_direction/ship_direction/ship_direction.py:822-823].
- 경로 없음: 후진 0.5 s 후 3.0 s STOP_HOLD 로 재탐색하고, 그래도 없으면 반복한다. 뒤쪽은 보지 못하므로 계속 후진하지 않는다 [근거: src/ship_direction/ship_direction/ship_direction.py:471-504] [근거: src/ship_direction/ship_direction/ship_direction.py:813-816].
- 변화율 제한: 0~160° 정상 조향값은 한 틱에 15° 까지만 바꾸고 특수 신호는 즉시 통과시킨다 [근거: src/ship_direction/ship_direction/ship_direction.py:438-466].
- 실제 노드 코드로 돌린 회피 시뮬레이션과 재구현 스윕의 비교는 Ⅲ-6.2(표 Ⅲ-14, 그림 Ⅲ-17)에 둔다.

| 파라미터 | 값 | 근거 |
|---|---|---|
| half_width | 0.29 m | {{HALF_WIDTH_REASON}} [근거: src/ship_direction/config/ship_direction.yaml:61-65] |
| clearance | 0.25 m | 20 시드 스윕 최적 (Ⅲ-6.1) [근거: src/ship_direction/config/ship_direction.yaml:71] |
| min_required_width | 0.83 m | 0.29×2 + 0.25 |
| detection_distance 기본 / 게이트 | 3.0 / 2.0 m | 시뮬 스윕 [근거: src/ship_direction/config/ship_direction.yaml:57-58] |
| min_obstacle_cells | 1 | 3 이면 작은 부표를 무시한다 [근거: src/ship_direction/config/ship_direction.yaml:75] |
| 후진 / 재탐색 | 0.5 / 3.0 s | 뒤를 못 보므로 계속 후진 대신 정지 후 재탐색 [근거: src/ship_direction/config/ship_direction.yaml:77-78] |
| rate_limit_max_deg_per_tick | 15° (150°/s) | 한 주기(0.1 s) 조향각 변화 상한 [근거: src/ship_direction/config/ship_direction.yaml:80] |

### 4.5) 도킹 — ship_dock
- 도크 3개 중 당일 지정 표식(삼각·원·사각 × 빨강·주황·노랑·초록·파랑·흰색)을 찾는다. 검출기 dock 이 target_color·target_shape 와 일치하는 후보의 방위각만 발행한다. 목표는 yaml 한 줄로 바꾼다 [근거: src/color_shape_detector/config/vision.yaml:169-174] [근거: src/color_shape_detector/color_shape_detector/dock_logic.py:20-26]. 목표가 유효값 밖이면 기동 시 ERROR, 검출 없이 도킹 모드에서만 무효값 10000 을 내고 5 s 마다 ERROR 로 다시 알린다(다른 모드에서는 발행하지 않는다). 도크 간격 1.0 m.
- 표식 판정: 마스크는 목표 색 하나로 만들고, 컨투어마다 형상을 판정해 목표와 다르면 버린다 [근거: src/color_shape_detector/color_shape_detector/basic_image_subscriberdock.py:248-279]. 꼭짓점 3 → Triangle(원형도 ≥ 0.82 면 노이즈), 4~6 → extent > 0.4·종횡비 0.6~1.4 면 Square(원형도 ≥ 0.82 면 Circle), 7 이상 → Circle(원형도 < 0.60 이면 노이즈)이다 [근거: src/color_shape_detector/color_shape_detector/dock_logic.py:71-94]. 통과 후보 중 화면 높이 0.15~0.55 안의 면적 최대 하나를 쓰고, key = (색, 형상) 이 연속 3 프레임 같아야 확정한다 [근거: src/color_shape_detector/color_shape_detector/basic_image_subscriberdock.py:284-293] [근거: src/color_shape_detector/color_shape_detector/basic_image_subscriberdock.py:131-135].
- 색 범위에서 헷갈리기 쉬운 곳은 둘이다: `hsv.blue` 가 S 18~60·V 160~200 이라 흐린 하늘에 가깝고, 빨강(H 0~5)과 주황(H 3~20)이 H 3~5 에서 겹친다 [근거: tools/dock_eval.py:5-8] [근거: docs/문제와작업/비전_개선후보_20261027.md:62-63].

### 4.6) 제어기 — motor_control
PID 가 아니라 각도 기반 차동 조향이다. 상류 체인(/candidate_angle → /desired_angle)이 이미 "가야 할 방위" 를 주므로 제어기는 그 각도 오차를 좌·우 PWM 차동으로 바꾸고, 전방 장애물 거리와 페일세이프 레벨로 속도만 깎는다. 20 Hz 고정주기 타이머.

| /desired_angle | 분기 | 좌/우 PWM (ROS 기준, <1500 = 전진) | 감속 적용 |
|---|---|---|---|
| ≥ 50000 | 정지 STOP_HOLD | 1500 / 1500 | — |
| 20000 ~ 50000 | 미션 없음 → 전진 폴백 | base_pwm / base_pwm (1360) | ○ |
| 5000 (6000) | 제자리 우선회 (좌선회) | spin_forward_pwm ± spin_diff = 1600 / 1400 (1400 / 1600) | × |
| −1 ~ 161 (정면 = 80) | 정상 조향 | offset = θ − 80, diff = abs(offset) / max_angle × max_diff(100) → base ± diff (좌우 반대 부호) | ○ |
| 161 ~ 5000 | 후진 | reverse_pwm / reverse_pwm (1590) | × |
| 명령 0.5 s 무수신 | 워치독 | 1500 / 1500 | — |

표 Ⅲ-11 motor_control 조향 분기와 PWM

감속비 = min(장애물 근접비, 페일세이프 상한). 근접비는 전방 최근접 거리 d 에 대해 d ≥ 1.2 m 이면 1.0, 그 아래서 0.7 + 0.3·d/1.2 로 선형. 페일세이프 레벨 1 이면 0.7. 적용은 PWM 을 중립 쪽으로 당기는 식 1500 + (PWM − 1500)·ratio.
- steer_invert 하나가 조향과 SPIN 을 함께 뒤집는다(배선 반대 대비).

- 출력 PWM 좌우 평균이 1500 보다 크면 `/motor_reverse` 를 참으로 내 헤딩 COG 추정의 후진 게이트로 쓴다(Ⅲ-2.1) [근거: src/motor_control/motor_control/motor_control.py:162-164].

표 Ⅲ-14 장애물 회피 구간 40 시드 — 실제 노드 코드와 재구현 비교 (tools/sim/avoid_sim.py)

경계 병합을 끄면 실제 코드와 재구현은 도달 40/40, 접촉 평균 0.82 로 같고 시드별 접촉 수도 40 시드 중 33 에서 일치하여, 6.1 의 스윕이 노드 동작을 재현한다고 볼 수 있다. 경계 병합을 켜자 4 시드가 경계 2 m 안에서 후진·재탐색을 반복하며 정체하였는데, 원인은 /geofence_state 상대방위의 좌우 부호가 발행 노드(나침반 기준, 우 양수)와 소비 노드(LiDAR 프레임, 좌 양수)에서 달라 경계 벽이 거울로 병합되던 것이었다. 발행 쪽 광선 방위를 LiDAR 프레임 규약으로 맞추고 부호 테스트를 추가한 뒤 같은 40 시드에서 40/40, 후진 30회가 되었다. 지오펜스 폴리곤은 대회장에서 입력하므로 물 위에서 쓰기 전에 부호를 확인하는 절차를 수조 시험 계획에 넣었다. 추력 응답에 0.5 s 지연을 두면 접촉이 0.97 로 늘고 1 시드가 정체하여, 경계 근처의 후진·재탐색 반복은 실제 배에서 확인할 항목이다. 운동 모델(순항 1.2 m/s, 선회 응답)은 가정이라 접촉 수치는 경향으로만 본다. 항로추종도 같은 방식으로 실제 ship_gate·ship_direction·motor_control 코드를 돌렸다. 카메라는 색별로 시야(HFOV 80.3°)·0.5~12 m 안의 가장 가까운 부표(검출기의 '가장 큰 컨투어 1개'와 같다) 방위를 /red_angle·/green_angle 로 내고(왼쪽 양수, 방위 잡음 0.5°), 게이트 4개(폭 3~6 m, 중심 ±1 m, 사이 9 m, 빨강 = 진행 방향 좌현)를 40 시드, 출발 헤딩 90°±30° 로 주행하였다. 수정 전 코드는 통과 110/160·접촉 22 였는데, 원인은 한쪽 부표만 보일 때의 오프셋 부호가 비전 규약(왼쪽 양수)과 반대여서 빨강(좌현)만 보이면 빨강 쪽으로 더 트는 것이었다. 부호를 맞춘 뒤 통과 160/160·접촉 0, 통과 위치는 게이트 중심에서 반폭의 0.06(중앙값, 최대 0.29)이었고 추력 응답 지연 0.5 s 에서도 160/160 이었다. 통과 수를 기록하는 /gates_passed 는 부표가 ±75° 뒤로 가야 세도록 되어 있었으나 카메라 반화각이 40° 라 물리적으로 도달 불가능해 항상 0 이었다. 임계를 35° 로 낮추고(코드 기본값·yaml 동시), 요잉 복귀로 같은 게이트를 두 번 세지 않도록 "다음 쌍의 LiDAR 거리가 직전 게이트에서 잰 최소 거리보다 1 m 이상 멀거나 두 부표가 모두 사라진 뒤에만" 다시 세게 하여 40 시드 모두 기하학적 통과 수와 일치하였다. 다만 카메라만으로는 게이트 사이 거리가 6 m 이하이고 게이트가 넓을 때 앞 게이트 부표가 보이는 채로 다음 쌍이 비슷한 거리에 들어와 누락될 수 있어(시뮬: 사이 8 m 40/40, 6 m 35/40, 4 m 22/40, 이중 카운트는 6 m 에서 1 런), 부표 LiDAR 추적은 대회 후 과제로 남겼다. GPS 웨이포인트만으로 160/160 인 것은 웨이포인트가 게이트 중점과 정확히 같을 때의 결과이며, 대회는 좌표를 공개하지 않으므로 비전 조향이 필요하다.
