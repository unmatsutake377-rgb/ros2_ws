## 0. 먼저 큰 그림 — 배 한 대 안에서 데이터가 도는 길

```
 [센서]                  [정리]                    [판단]                       [실행]
 IMU ──/imu/yaw_raw──▶ yaw_mux ──/imu/yaw──┬─▶ ship_goal_angle ──/yaw_error──┐
                                          │                                  │
 GPS ──/fix─────────▶ north_goal_angle ───┼─/north_goal_angle_tp─▶(위)       │
                       │  /wp_mode (지금 몇 번 임무?)                         ▼
                       │  /geofence_state (경계 = 가짜 LiDAR)  ──▶ ship_direction ──/desired_angle──▶ motor_control
                       ▼                                          ▲   (최종 각도 1개)          (좌/우 PWM)
 카메라 ─영상─▶ 검출기 3종 ─/red_angle 등─▶ 임무 노드 4종 ─/candidate_angle─┘                      │
 LiDAR ──/scan───────────────────────────────────────────────────▶ ship_direction                Motor_run
                                                                                                   ▼
                                                                     ssf_bridge ──USB 시리얼──▶ 아두이노 ──▶ ESC ──▶ 스러스터
```

**한 문장**: 센서 값을 "정리"하는 노드들이 각도 하나씩을 만들고, 그 각도들이 **ship_direction 한 곳에 모여 최종 조향각 1개**가 되고, motor_control 이 그걸 좌/우 모터 세기로 바꾼다.

이해의 열쇠 세 가지:
1. **모든 게 "각도" 로 흐른다.** 속도·위치를 제어하는 게 아니라 "어느 방향으로 갈래" 를 계속 넘긴다.
2. **특수 숫자가 명령어 역할을 한다.** 각도 자리에 5000(우선회), 20000(미션 없음), 50000(정지), 10000(카메라 못 봄) 같은 큰 숫자가 오면 각도가 아니라 신호다.
3. **모르면 입을 다문다.** 센서가 이상하면 0 같은 가짜 값을 내지 않고 발행을 멈춘다. 그 "침묵" 을 아래 노드가 감지해서 배를 세운다(Ⅲ-5).

## Ⅲ-1. 시스템 구성

### 한 줄 요약
노트북(ROS2)이 머리, 아두이노가 손. 노트북은 "좌 몇, 우 몇" 숫자만 보내고 아두이노가 그걸 ESC 에 그대로 전달한다.

### 실제 동작
- `motor_control` 이 좌/우 PWM 을 정하면 `Motor_run = 오른쪽×10000 + 왼쪽` 한 숫자로 합쳐 보낸다. 예: 우 1400, 좌 1600 → `14001600`.
- `ssf_bridge` 가 이 숫자를 USB 시리얼로 아두이노에 쓴다. 아두이노 펌웨어는 그대로 핀 12(좌)·11(우)로 내보낸다.
- **0.5 s 동안 명령이 안 오면 아두이노가 스스로 1500(중립)** — 노트북이 멈춰도 배는 선다.
- 모드(WAIT/MANUAL/AUTO)는 **조종기 스위치로만** 바뀐다. 노트북이 모드를 바꾸는 코드는 일부러 없다. 노트북은 `/boat_mode` 로 "지금 몇 번 모드인지" 읽기만 한다.
- **추력 부호 함정**: ROS 안에서는 1500 보다 **작으면 전진**, 실제 ESC 는 1500 보다 **크면 전진**. 뒤집는 곳은 `ssf_bridge` 딱 한 곳(`invert_thrust_direction`). 다른 데서 또 뒤집으면 배가 후진한다.
- 두 배는 같은 코드. `boat:=A` 또는 `boat:=B` 를 안 주면 launch 가 아예 안 뜬다(실수로 남의 배 설정으로 뜨는 걸 막음).

### 코드 위치
`src/ssf_bridge/`, `arduino/ssf_boat/ssf_boat.ino`, `src/launch_files/launch/launch_files.launch.py`

### 심사 질문 대비
- *"노트북이 다운되면?"* → 아두이노 0.5 s 워치독으로 중립. motor_control 도 명령 0.5 s 무수신 시 중립.
- *"자율 중 사람이 개입하려면?"* → 조종기 스위치 하나. 소프트웨어 경로가 없어서 소프트 버그로 모드가 꼬일 수 없다.

## Ⅲ-2.1 헤딩 (뱃머리 방향) — `ssf_heading` / `yaw_mux`

### 한 줄 요약
IMU 가 주는 "아무 기준 각도"를 **진북 기준 0~360°** 로 바꿔 주는 번역기. `/imu/yaw` 는 **이 노드 하나만** 낸다.

### 왜 따로 노드를 만들었나
작년엔 IMU 드라이버가 **켜진 순간 방향을 0°** 로 잡았다. 배가 동쪽을 보고 켜지면 동쪽이 0° — GPS 목표 방위(진북 기준)와 빼면 의미가 없다. 그래서 올해는:
- 드라이버는 원시값 `/imu/yaw_raw` 만 낸다.
- `yaw_mux` 가 보정해서 `/imu/yaw` 를 낸다.
- 두 노드가 같은 토픽을 내면 ROS 는 에러 없이 값이 번갈아 섞인다 → launch 에서 드라이버 출력 이름을 못 박고, 잘못 설정되면 경고.

### 실제 동작 (기본 소스 `imu_relative`)
식: **ψ = wrap360( s·원시값 + mount_offset_deg )**  (s = invert 면 −1, 아니면 +1)
- 예: 원시값 120°, `mount_offset_deg` = 232.0 → 120 + 232 = 352 → `/imu/yaw` = 352°.
- `wrap360` 은 0~360 으로 접는 함수. 370 → 10, −10 → 350.
- 50 Hz(0.02 s)마다 발행. 원시값이 0.5 s 넘게 안 오면 **발행을 멈춘다**(0 을 내지 않음).

### 정북 정렬은 이렇게 한다 (배마다 한 번)
1. 나침반으로 배를 북쪽에 맞춘다. 단 나침반은 **자북**을 가리킨다. 한국은 자북이 진북보다 약 8° 서쪽 → 그때 뱃머리의 진북 기준 방위는 **약 352°**.
2. `ros2 topic echo /imu/yaw` 가 352 근처가 될 때까지 `ssf_heading_A.yaml` 의 `mount_offset_deg` 를 바꾼다 (**반드시 소수점**, 37 ❌ 37.0 ✅ — 정수면 노드가 부팅하자마자 죽는다).
3. 시계방향으로 90° 돌린다. 값이 352 → **약 82**(한 바퀴 넘어감)로 가면 정상. **약 262** 로 가면 방향이 반대 → `invert_yaw: true` 로 바꾸고 1번부터.

### 대안 소스 `cog_offset` (지금은 안 씀, 사용 금지 상태)
- 아이디어: 배가 **곧게 앞으로 달리는 중**이면 GPS 가 재는 "실제 지나간 방향(COG)" ≈ 뱃머리 방향. 그러니 `COG − IMU` 를 여러 번 재면 IMU 오프셋을 자동으로 알 수 있다.
- 평균을 그냥 내면 안 된다: 359° 와 1° 를 평균하면 180° 가 나온다. 그래서 각도를 **화살표(단위벡터)** 로 바꿔 더한다. 화살표들이 한 방향으로 잘 모이면(신뢰도 R ≥ 0.9, 표본 30개 이상) 그때만 쓴다.
- 버리는 표본: 느릴 때(0.8 m/s 미만 — COG 가 잡음), 급선회 중(8°/s 초과 — 배가 미끄러짐), **후진 중**(COG 가 뱃머리와 180° 반대). 후진은 `motor_control` 이 내는 `/motor_reverse` 로 안다.
- 10-30 고친 버그(F11): 이 경로가 mount·invert 를 한 번 더 적용하고 있었다 → 고침(94ed89f). **물 위에서 북·동 두 구간 확인 전까지 사용 금지**는 유지.

### 코드 위치
`src/ssf_heading/ssf_heading/heading_logic.py`(계산, ROS 없음 — 테스트 76개), `yaw_mux.py`(ROS 껍데기), `config/ssf_heading*.yaml`

### 심사 질문 대비
- *"자기편각은 어떻게 처리?"* → 나침반 기준 소스에만 더한다. 지금 쓰는 `imu_relative` 는 정렬할 때 오프셋 안에 편각이 같이 들어간다(그래서 목표값이 0 이 아니라 352).
- *"IMU 가 죽으면?"* → `/imu/yaw` 가 멈춤 → `/yaw_error` 도 멈춤 → `ship_direction` 이 0.7 s 에 감속, 3 s 에 정지.

## Ⅲ-2.2 GPS — `north_goal_angle`

### 한 줄 요약
GPS 위치로 **"다음 웨이포인트는 어느 방위인가"**, **"지금 몇 번 임무인가(/wp_mode)"**, **"경계선은 어디인가"** 를 0.5 s 마다 낸다.

### ① 받는 단계 — RTK
- 그냥 GPS 는 ±3~5 m 틀린다. 부표 간격보다 커서 못 쓴다 → **RTK**(기지국 보정)로 ±1.5 cm (08-07 실측 FIXED ±0.015 m).
- 보정 데이터는 인터넷(NTRIP)으로 받는다. 계정 파일(`~/.ssf/`)이 없으면 그 노드만 빠지고 나머지는 뜬다.

### ② 거르는 단계 — 다섯 겹 필터 (작년엔 0겹이었다)
작년 코드는 GPS 가 아직 위치를 못 잡아서 (위도 0, 경도 0) 을 줘도 그걸로 방위를 계산했다(08-06 실제로 47.96° 라는 엉터리 방위가 나옴).

| 겹 | 하는 일 | 예시 |
|---|---|---|
| 1. fix 검증 | 상태 −1, (0,0), NaN, 범위 밖 → "위치 모름" | 아직 위성 못 잡음 → 방위 발행 안 함 |
| 2. 공분산 | 수신기가 "이번 값 자신 없음"(분산 > 2.0) → 그 한 번만 버림 | |
| 3. 점프 | 직전 위치에서 15 m/s 이상 속도로 순간이동 → 버림 | 건물 반사(멀티패스)로 10 m 튐 |
| 4. 스무딩 | 오차 작으면 천천히(α 0.15), 크면 빨리(α 0.80) 따라감 | 흔들림 줄이고, 진짜 이동은 빨리 따라감 |
| 5. 신선도 | 받아들인 위치가 2.5 s 넘게 없으면 방위·경계 발행 중단 | 1 Hz 라 한 번 빠짐(2 s)은 버티고, 두 번 빠지면 중단 |

### ③ 길 찾기 — LOS·ILOS (줄 따라가기)
- 작년: "지금 위치에서 목표점을 똑바로 바라봐라" → 조류에 밀리면 비스듬히 휘어 들어간다.
- 올해: **이전 웨이포인트 P → 목표 W 를 잇는 가상의 줄**을 따라간다.
  - XTE = 줄에서 옆으로 벗어난 거리(오른쪽 +).
  - 줄 위의 앞쪽 L m 지점(L = 속도×1.2, 2~6 m)을 바라본다. 벗어날수록 줄 쪽으로 더 꺾는다.
  - **I(적분)**: 계속 한쪽으로 밀리면(조류) XTE 를 누적해서 그만큼 미리 반대쪽으로 꺾는다. 웨이포인트 넘어가면 0 으로 초기화.
- 도착 판정: 반경(도킹 2.0 m, 그 외 속도별 2.5~4.5 m) 안에 **dwell 초** 머무르면 다음 WP.
- 조종기가 AUTO 가 될 때까지는 WP0 에서 대기(타이머·적분 다 초기화) → AUTO 넣는 순간부터 시작.

### ④ 경계 — 지오펜스 = 가짜 LiDAR
- 경기장 밖으로 나가면 실격. 그래서 경계선을 **LiDAR 처럼** 만든다: 정면 −80°~+80° 를 1° 간격으로 광선을 쏴서 "이 방향으로 경계까지 몇 m" 를 계산 → `/geofence_state`.
- `ship_direction` 은 이걸 진짜 LiDAR 와 **둘 중 가까운 값**으로 합친다 → 경계가 그냥 "벽" 이 되어 회피 로직이 알아서 피한다.
- 헤딩이나 GPS 가 이상하면 빈 배열(벽 없음). 엉뚱한 벽이 배를 가두는 것보다 낫기 때문.
- 대회장 경계 좌표가 아직 없어 지금은 꺼져 있다.

### 코드 위치
`src/north_goal_angle/north_goal_angle/` — `gps_guard.py`(필터), `north_goal_angle.py`(LOS·지오펜스), `config/waypoints.yaml`, 녹화 도구 `waypoint_recorder`

### 심사 질문 대비
- *"GPS 가 끊기면 임무가 멈추나?"* → 방위는 멈추지만 `/wp_mode` 는 계속 나가고, WP 마다 **시간 초과**가 있어 GPS 없이도 다음 임무로 넘어간다.
- *"웨이포인트는 어떻게 넣나?"* → 대회장에서 배를 그 자리에 두고 `waypoint_recorder` 로 2 s 평균 좌표 녹화 → yaml. 틀린 값(0.0, 위경도 뒤바뀜)은 노드가 부팅 때 거부.

## Ⅲ-2.3 LiDAR — `ship_direction` 의 입력부

### 한 줄 요약
360° 스캔 중 **앞쪽 160°** 만 잘라 "각도별 거리 배열"로 쓴다.

### 실제 동작
- **받기와 계산 분리**: `/scan` 이 오면 저장만. 계산·발행은 10 Hz 타이머가 따로 한다. → LiDAR 가 죽어도 타이머는 계속 돌아서 "LiDAR 죽었음" 을 알아챌 수 있다(작년엔 LiDAR 가 끊기면 조향 명령이 0회 → 마지막 명령으로 계속 감).
- **최신만**: 큐 깊이 1. 늦게 처리하면 옛 스캔은 버리고 최신만.
- **각도 격자**: LiDAR 프레임 80° = 정면. 0~160 = 오른쪽 80° ~ 왼쪽 80°(80 보다 크면 왼쪽). 이 "0~160, 정면 80" 격자가 `/desired_angle` 까지 그대로 이어진다.
- **물보라 거르기(감속용만)**: 한 점만 튀는 반사는 주변 5칸 중 3칸 이상 값이 있어야 인정 → 시뮬에서 가짜 감속 36.8% → 8.9%. 회피 판단에는 이 필터를 안 건다(작은 부표를 놓칠까 봐).

### 코드 위치
`src/ship_direction/ship_direction/ship_direction.py`

## Ⅲ-2.4 영상 — 검출기 3종 (`basic_image_subscriber{gate,turn,dock}`)

### 한 줄 요약
카메라 한 장에서 **원하는 색 부표의 "방위각" 하나**만 뽑는다. 거리는 안 쓴다(거리는 LiDAR 담당).

### 7단계를 숫자로 따라가 보기 (640×480, D455 화각 80.32°)
1. **입력**: 최신 프레임 1장만(밀리면 버림).
2. **색 분리**: 사진을 HSV(색상·채도·밝기)로 바꿔 "빨강 범위" 픽셀만 흰색으로. 빨강은 색상환 0° 근처라 [0-5]와 [165-180] 두 범위를 합친다.
3. **후보**: 흰 덩어리(컨투어)들 중 → 너무 작은 것(40픽셀 미만) 버림 → 모양 검사 → 화면 위아래 일정 높이(물 위 부표가 보일 자리)만 → **가장 큰 것 하나**.
4. **(도킹만) 모양**: 꼭짓점 수 + 원형도로 삼각/사각/원.
5. **확인**: 한 프레임 오탐에 배가 튀지 않게, 최근 몇 프레임에서 같은 결과가 N 번 나와야 확정(게이트·탐색 1, 도킹 연속 3).
6. **각도 변환**: 부표 중심 x = 480 픽셀이라면
   - 화면 중심 cx = 320, fx = 320 / tan(40.16°) ≈ 378
   - θ = −atan((480 − 320)/378) ≈ **−22.9°** → 오른쪽 23°. (화면 왼쪽이 +)
7. **발행**: 지금 `/wp_mode` 가 내 담당일 때만. 2 s 동안 못 보면 무효값 **10000**.

### 왜 이렇게
- 작년엔 같은 초록색 범위가 파일 3곳에 다르게 적혀 있어서 게이트 검출기는 보는데 도킹 검출기는 못 봤다 → 올해 `vision.yaml` 한 곳.
- 작년엔 모드가 바뀔 때마다 검출기를 껐다 켰다 → 켜지는 동안 눈이 먼다. 올해는 3개 다 상주, 자기 모드에서만 일한다(나머지 땐 영상 변환도 안 해서 CPU 절약).
- 화각을 71.5° 로 잘못 쓰고 있었다 → 가장자리에서 최대 4.4° 틀림 → 카메라가 알려주는 값(camera_info)으로 80.32° 실측.

### 코드 위치
`src/color_shape_detector/` — `vision_geom.py`(각도 계산), `dock_logic.py`(확인 로직), `config/vision.yaml`, 도구 `tools/dock_eval.py`·`tools/vision_probe.py`

### 심사 질문 대비
- *"왜 카메라로 거리를 안 재나?"* → 핀홀 거리 추정은 부표 크기·흔들림에 민감. LiDAR 가 cm 단위로 직접 잰다.
- *"역광이면?"* → HSV 값은 실외에서 재조정(튜닝 노드 `basic_image_subscriberhsv`, 값은 `vision.yaml` 한 곳), 확인 프레임으로 한두 프레임 튀는 건 무시.

## Ⅲ-3. 전체 임무 상태기계 — `/wp_mode`

### 한 줄 요약
**`/wp_mode` 숫자 하나가 "지금 누가 일할지" 를 정한다.** 이 숫자를 바꾸는 건 `north_goal_angle` 하나뿐.

| wp_mode | 임무 | 일하는 노드 | 카메라 |
|---|---|---|---|
| 0, 1 | 게이트 통과 | ship_gate | gate 검출기 (빨강·초록) |
| 2 | 위치유지 | ship_back | turn 검출기 (흰색) |
| 3 | 부표 선회 | ship_turn | turn 검출기 (빨강) |
| 5 | 장애물 회피 | (없음) ship_direction 혼자 | 없음 |
| 7 | 도킹 | ship_dock | dock 검출기 |
| 8 | 토너먼트 회피 | (없음) | 없음 |

- 웨이포인트마다 mode 가 적혀 있고, 도착하거나 **시간 초과**(WP 하나당 90~150 s)되면 다음 WP → mode 가 바뀐다.
- 시간 초과는 GPS 가 죽어도 진행되는 **유일한 안전장치**.
- 특수 숫자: **5000** 우선회 / 6000 좌선회 / **20000** 미션 없음 → GPS 방향으로 전진 / **50000** 정지.

## Ⅲ-4. 임무별 알고리즘

### 4.1 게이트 — `ship_gate`
- 빨강·초록 **둘 다 보이면 그 가운데**로.
- **하나만** 보이면 그 부표에서 게이트 안쪽으로 40° 틀어서(빨강은 왼쪽에 둔다는 규칙 `red_on_port`).
- **둘 다 안 보이면 20000**(미션 없음) → `ship_direction` 이 GPS 웨이포인트 방향으로 간다.
- 부표가 옆으로 75° 넘게 지나가면 통과 1회 → `/gates_passed`. 먼 게이트를 미리 세지 않게 6 m 안에서만 센다.
- 코드: `src/ship_gate/ship_gate/gate_logic.py`

### 4.2 위치유지 — `ship_back`
- 흰 부표의 방위(카메라) + 거리(LiDAR)로 부표 근처를 유지. RTK 는 보조.

### 4.3 탐색 — `ship_turn`
- 빨강/초록이면 시계방향, 흰색이면 반시계로 부표 둘레를 돈다. 색을 잃으면 SEARCH 상태로 다시 찾는다.
- 주의: 토픽 이름 `/image_color` 를 바꿨다가 노드가 영원히 멈춘 적 있음 — 이름은 고정.

### 4.4 장애물 회피 — `ship_direction` (가장 중요)
**한 줄**: LiDAR 160° 배열에서 **배가 지나갈 만큼 넓은 빈 틈**을 찾고, 그중 **목표 방향에 가장 가까운 각도**를 고른다.

예시로 따라가기 (탐지거리 3.0 m, half_width 0.29 m, clearance 0.25 m):
1. **흑백 칠하기**: 3.0 m 안에 뭐가 있으면 "막힘", 아니면 "빈칸". → `□□□■■■□□□□□□■□□□`
2. **잡티 지우기**: 1~3칸짜리 막힘은 물보라로 보고 지운다(진짜 부표는 수십 칸).
3. **부풀리기**: 배 폭만큼 장애물을 양옆으로 넓힌다. 가까운 장애물일수록 각도로 많이 부풀린다. (배를 점으로 취급할 수 있게 장애물을 키우는 것)
4. **폭 재기**: 남은 빈 구간의 실제 폭(호 길이) ≥ **0.83 m**(0.29×2 + 0.25) 인 틈만 후보.
5. **고르기**: 목표 방향이 후보 틈 안에 있으면 그대로, 밖이면 틈 가장자리 중 목표에 가까운 쪽.
6. **틈이 없으면**: 0.5 s 후진 → 3 s 멈춰 다시 탐색(뒤는 못 보니 계속 후진 안 함).
7. **급변 금지**: 한 번(0.1 s)에 15° 이상 안 바꾼다.

왜 이 숫자: 시뮬 2,400 판 돌려서 1번배 폭(0.58 m)에서 접촉이 가장 적고 막혀서 멈추는 일 0% 인 clearance 가 0.25.
코드: `ship_direction.py` (그림 Ⅲ-3 `tools/gap_selection_figure.py` 가 이 6단계를 그린다)

### 4.5 도킹 — `ship_dock`
- 당일 공지된 표식(예: 파랑 삼각형)을 yaml 한 줄로 지정 → dock 검출기가 그 색·모양만 찾아 방위각을 낸다.
- 연속 3 프레임 같아야 확정. 목표 오타면 부팅 때 ERROR + 도킹 모드에서 10000 + 5 s 마다 ERROR.
- 위험: 파랑이 흐린 하늘과 비슷, 빨강·주황이 색상 3~5 에서 겹침 → 실외 조정 대상.

### 4.6 모터 — `motor_control`
**한 줄**: 각도를 좌/우 PWM 차이로 바꾼다. PID 아님.

예시 (`/desired_angle` = 100°, base 1360):
- offset = 100 − 80 = **+20** (왼쪽으로 20°)
- diff = 20/81 × 100 ≈ **24**
- 오른쪽 1360 − 24 = 1336, 왼쪽 1360 + 24 = 1384 → ROS 에선 작을수록 전진 → **오른쪽이 더 세게 → 왼쪽으로 돈다.**
- 장애물이 1.2 m 안으로 오면 속도 줄임(최대 0.7배까지), 페일세이프 레벨 1 이면 0.7배.
- 5000 → 1600/1400 제자리 우선회(감속 안 걸음 — 걸면 뒤로 밀리며 돈다).
- 좌우 평균이 1500 보다 크면(후진) `/motor_reverse` = true → 헤딩 추정이 그 표본을 버린다.
- `steer_invert`: 배선이 반대면 이것 하나로 조향·선회가 같이 뒤집힌다. 물 위 첫 시험에서 확정.

## Ⅲ-5. 페일세이프 — "침묵을 감지해서 세운다"

### 한 줄 요약
`ship_direction` 안의 `SensorWatch` 가 **LiDAR(`/scan`)와 헤딩(`/yaw_error`)이 마지막으로 온 시각**을 10 Hz 로 본다.

| 끊긴 시간 | 레벨 | 배 |
|---|---|---|
| 0.7 s 넘음 (3번 연속 확인) | 1 경고 | 하던 조향 그대로, 속도 0.7배 |
| 3.0 s 넘음 (3번 연속) | 2 정지 | 50000 정지 |
| 다시 들어옴 | 0 | 자동 복구 |

- 08-06 실측: IMU 드라이버를 끄자 4.78 s 에 레벨 1, 7.08 s 에 레벨 2. LiDAR 끄자 0.70 s / 2.99 s.
- 레벨 1 에서 "직진" 하지 않는 이유: 부표를 피하던 중이면 직진이 바로 충돌이다.
- 시계는 `time.monotonic()`(벽시계가 바뀌어도 안 튐), 센서가 **한 번이라도 온 뒤에만** 감시 시작(부팅 직후 오경보 방지).
- 2중·3중: motor_control 0.5 s 워치독, 아두이노 0.5 s 워치독, 비상정지 접촉기 → 아두이노 핀 38 로 상태 보고.
- `/health_ok` 같은 진단은 **로그만** — 진단 버그로 배가 서는 "거짓 정지" 를 막으려고 제어에 연결 안 함.
