# 🎯 결론 먼저: 개선안 시뮬레이션 결과

물보라 오탐 25%가 있는 수면 환경에서 전 코스(70×20m)를 6회 반복:

| | 접촉 횟수 | 주행시간 | **최종 기록** (접촉×30초 포함) |
|---|---|---|---|
| **개선 전** | **3.0회** | 139.9초 | **229.9초** |
| **개선 후** | **0.2회** | 146.4초 | **152.4초** |
| 변화 | **-93%** | +5% | **-33.7%** ✅ |

**접촉이 3회 → 0.2회로 거의 사라졌고, 기록이 34% 단축**됐습니다. 주행시간은 감속 때문에 5% 늘었지만, 접촉 패널티(30초/회)가 사라진 이득이 압도적입니다.

**시뮬로 찾은 최적 파라미터:**
- `clearance` = **0.25m** (0.15 → 0.25)
- `detection_distance` = **게이트 2.0m / 일반 3.0m** (1.8 고정 → 구간별)
- 감속 시작 거리 = **1.2m**, 최저속도 = **70%**
- 시간 필터 = 최근 3프레임 중 2회 이상
- `rear_obstacle_ignore_margin` **제거**, 침식 **제거**, `min_obstacle_cells` **3→1**

> ⚠️ **주의: clearance를 0.45m로 올리면 오히려 807초로 폭주합니다.** 너무 보수적이면 "지나갈 수 없다"고 판단해 후진을 반복합니다. **0.25가 최적점**입니다. 제가 전에 "0.3~0.5m"라고 한 건 과했습니다.

# 🔥 CPU 부담 우려 — 실측 결과 "전혀 문제없음"

**말씀하신 우려 두 가지 모두 사실과 다릅니다.**

### ① "LiDAR가 1초에 1번 돈다" → **아닙니다. 10Hz(초당 10바퀴)입니다.**
코드에서 확인: `declare_parameter<float>("scan_frequency", 10)`. RPLIDAR A3 기본값이 10Hz입니다.
→ **시간 필터 3프레임 = 0.3초** (3초 아님). 1.2m/s에서 **0.36m 이동**. 3m 탐지거리면 여유가 충분합니다.

### ② "탐지거리 늘리면 데이터가 기하급수적으로 는다" → **데이터 양은 전혀 안 늘어납니다.**
LiDAR는 탐지거리와 **무관하게 항상 같은 개수의 점**(회전당 약 1,600점)을 보냅니다.
`detection_distance`는 그중 **"이 점을 장애물로 볼지 말지" 판단하는 임계값**일 뿐입니다. **연산량이 그대로입니다.**

**실측 데이터 (개선안 로직으로 200회 측정):**

| 탐지거리 | 1스캔 처리 시간 | 10Hz 예산(100ms) 대비 |
|---|---|---|
| 1.8m | 0.15 ms | 0.1% |
| **3.0m** | **0.15 ms** | **0.1%** |
| 5.0m | 0.14 ms | 0.1% |

**100ms 중 0.15ms만 씁니다. 여유가 660배입니다.** 시간 필터 메모리도 3프레임 × 711개 = 2,133바이트로 무시 가능합니다.

**→ 15·17·20·21번 모두 CPU 부담 없이 안심하고 적용하세요.**

## 7번. 도킹 — "주석 처리 방식보다 나은 방법"

**작년 방식(코드 여러 벌 만들고 주석 처리)의 위험:** 대회장에서 **코드를 고치고 재빌드**해야 합니다. 빌드 실패·오타·잘못된 주석 해제 하나로 미션이 날아갑니다. 시간 압박 속에서 가장 사고 나기 쉬운 방식입니다.

**권장: ROS 파라미터 (재빌드 불필요, 5초면 끝)**

```python
# basic_image_subscriberdock.py
self.target_color = self.declare_parameter("target_color", "red").value
self.target_shape = self.declare_parameter("target_shape", "Square").value
```

대회장에서는 실행할 때 값만 바꿉니다:
```bash
ros2 launch launch_files launch_files.launch.py \
     target_color:=blue target_shape:=Triangle
```

**구조도 바꾸는 게 좋습니다.** 지금은 "목표 도형만 찾는" 구조인데, **모든 도형·색을 다 인식해서 목록으로 발행**하고, **별도 선택 노드가 파라미터와 맞는 것을 고르는** 구조가 안전합니다.
- 장점: 도크 3개가 동시에 보여도 "어느 게 목표인지" 확실히 고를 수 있음
- 장점: 인식 코드는 한 벌만 유지 → 주석 처리 지옥 없음
- 장점: 준비 기간에 3형상 × 5색을 전부 튜닝해두면 당일엔 파라미터만 바꿈

**준비 기간에 할 일:** 실제 도크 표식을 보고 **HSV 5색 + 3형상 인식률을 전부 검증**해두세요. 당일 어떤 조합이 나와도 대응됩니다.

## 10번. 페일세이프 — "미션 타임아웃"과 "고장 대응"은 다른 문제입니다

말씀하신 **"일정 시간 안에 미션 못 하면 다음 좌표로 이동"** 은 **전략적 포기**입니다. 좋은 설계이고 유지하세요.
하지만 그건 **"시스템이 정상인데 미션이 안 풀리는 경우"** 입니다. **"시스템이 고장 난 경우"** 는 완전히 다르게 다뤄야 합니다.

**권장: 3단계 계층 구조**

| 단계 | 상황 | 대응 |
|---|---|---|
| **L1 — 성능 저하** | 비전 끊김 (LiDAR·IMU·GPS는 정상) | **계속 주행.** GPS/LiDAR만으로 항법. 미션은 포기하고 다음 구간으로 (= 지금 하시는 방식) |
| **L2 — 핵심 센서 이상** | LiDAR 또는 IMU가 0.5초 이상 stale | **감속 + 직진 유지**. 3초 내 복구 안 되면 **정지** |
| **L3 — 시스템 고장** | 노드 죽음 / 통신 두절 | **즉시 중립 정지** (11번 워치독) |
| **미션 타임아웃** | 시스템 정상, 미션만 안 풀림 | **감점 각오하고 다음 좌표로** (전략) |

**핵심: 미션 타임아웃은 "가던 길을 계속 가는 것", 고장 페일세이프는 "멈추는 것"입니다.** 둘을 섞으면 안 됩니다.

## 11번. 워치독 — "종료 좌표로 이동"은 **불가능**합니다

말씀하신 "미션 종료 좌표로 자동 이동"은 **좋은 아이디어지만 워치독에는 적용할 수 없습니다.**

**이유:** 펌웨어 워치독이 발동하는 상황은 **"ROS가 죽었거나 USB가 빠졌을 때"** 입니다. 그런데 **"종료 좌표로 이동"을 계산하는 주체가 바로 그 ROS**입니다. 아두이노는 GPS도 모르고 좌표도 모릅니다. **명령을 내려줄 사람이 없는데 어디로 가라고 할 수가 없습니다.**

**따라서:**
- **펌웨어 워치독 = 반드시 "중립 정지"** (다른 선택지가 물리적으로 없음)
- **"종료 좌표로 이동" = ROS가 살아있을 때의 상위 전략** (10번의 미션 타임아웃)

```cpp
// 펌웨어에 추가 (10줄)
volatile unsigned long last_cmd_ms = 0;
// subscription_callback 안에서: last_cmd_ms = millis();
// timer_callback 안에서:
if (millis() - last_cmd_ms > 500) {   // 0.5초 무응답
    AutoR = 1500; AutoL = 1500;       // 중립 정지
}
```

## 12번. RC 통신 두절 — 작년 참사 재발 방지

작년 상황(배가 멀어져 수동 전환이 안 됨)은 **RC 링크 두절**입니다. 3중 방어를 권합니다.

**① RC 수신기 자체 페일세이프 설정 (가장 중요, 하드웨어)**
대부분의 RC 수신기는 "신호 상실 시 각 채널을 지정한 값으로 출력"하는 기능이 있습니다. **Auto 채널을 '수동(>1500)'이 아니라 정해진 안전값으로 설정**해두세요. 수신기 설명서의 Failsafe 항목입니다.

**② 펌웨어에서 RC 신호 유효성 검사**
```cpp
// PulsesAuto가 일정 시간 갱신 안 되면 RC 두절로 판단
if (millis() - last_rc_ms > 1000) {
    rc_lost = true;
}
```
**RC 두절 시 어떻게 할지가 판단 포인트입니다:**
- **자율 계속 (권장)** — 경기 중이면 미션을 이어가는 게 낫습니다. 단 **반드시 geofence(9번)와 무선 비상스위치가 있어야** 경기장 밖으로 나가는 걸 막을 수 있습니다.
- 즉시 정지 — 가장 안전하지만 경기가 끝납니다.

**③ 무선 비상스위치 (규정 필수)**
RC와 **별개의 주파수/채널**을 쓰는 비상스위치가 있어야 합니다. RC가 끊겨도 이건 살아있어야 진짜 최후 수단이 됩니다. (하드웨어 파트에 RC와 다른 대역을 쓰도록 요청하세요)

**그리고 현재 코드의 버그를 반드시 고치세요:** 지금은 RC 신호가 없으면 `Auto_signal = 0 < 1500` → **자동으로 자율 모드**입니다. 즉 **"RC 없음"과 "자율 선택"을 구분하지 못합니다.** 최소한 이 둘을 구분하는 플래그가 필요합니다.

## 13번. iahrs GPS heading — "타임아웃 후 IMU 복귀" 조언에 대한 평가

**받으신 조언(타임아웃 걸어서 안 되면 IMU로 복귀)은 방향은 맞지만 절반만 해결합니다.**

**놓치는 것: GPS heading은 "진행 방향(COG)"이지 "뱃머리 방향"이 아닙니다.**
- 배가 **빠르게 직진**할 때 → COG ≈ 뱃머리 방향 (맞음)
- 배가 **느리거나 정지**할 때 → COG는 **완전한 노이즈** (위치유지·도킹이 바로 이 상황!)
- 배가 **조류에 옆으로 밀릴 때** → COG와 뱃머리가 **다름**

타임아웃만 걸면, GPS가 **살아있으면서 저속인 상황**(= 위치유지·도킹)에서 **방위가 튑니다.** 이게 더 위험합니다.

**제 권장 (가장 안전한 순서):**

**1단계 — 지금 당장 (가장 안전·단순): GPS override를 끄고 IMU만 사용**
```cpp
// if (!std::isnan(gps_heading)) { yaw_corrected = gps_heading; }   ← 주석 처리
```
iAHRS가 **9축(지자기 포함)** 이면 자체적으로 절대 방위를 냅니다. GPS 보정이 필요 없습니다.
**→ iAHRS 모델명을 알려주세요.** 9축인지 6축인지에 따라 답이 갈립니다.
- **9축(자이로+가속도+지자기)** → GPS 불필요. 이대로 끝.
- **6축(자이로+가속도)** → yaw가 시간에 따라 드리프트 → GPS 보정 필요 (2단계로)

**2단계 — 6축이라 GPS 보정이 필요하다면: 3중 안전장치**
```cpp
// ① 타임아웃 — 2초 안 들어오면 무효화
if (millis() - last_gps_ms > 2000) gps_heading = NAN;

// ② 저속에서는 GPS heading 배제 (COG가 무의미)
if (gps_speed < 1.0) gps_heading = NAN;   // NavPVT의 gSpeed 사용

// ③ 즉시 덮어쓰기 금지 — 천천히 융합 (상보 필터)
if (!isnan(gps_heading)) {
    yaw = 0.98 * imu_yaw + 0.02 * gps_heading;   // 드리프트만 서서히 보정
}
```
**핵심은 ③입니다.** 지금처럼 `yaw = gps_heading`으로 **통째로 덮어쓰면** GPS가 튈 때 배도 같이 튑니다. 98:2로 천천히 섞으면 **IMU의 부드러움 + GPS의 절대 기준**을 둘 다 얻습니다.

**필요한 하드웨어 정보:** iAHRS **모델명**(9축 여부), 그리고 NavPVT의 `gSpeed`(지상속도) 필드를 쓸 수 있는지.

## 18·19번. 침식 함수 위치 + "변수 늘면 하드웨어 퍼지나?"

**위치: `ship_direction/ship_direction/ship_direction.py`**

| 항목 | 줄 번호 |
|---|---|
| 파라미터 정의 | 47~57행 (`max_spike_ratio`, `border_margin`, `min_obstacle_cells`, `rear_obstacle_ignore_margin`) |
| `smooth_spikes()` | **336행** — 3셀 이하 장애물을 노이즈로 보고 삭제 |

- `suppress_spike_edges()`(침식)를 **제거하면 O(n) 루프가 하나 줄어듭니다.** 더 빨라집니다.
- 실측: 개선 후 로직도 **0.15ms/스캔** (100ms 예산의 0.1%)

## 20번. 우선순위에 대한 제 의견

**시간 필터는 우선순위가 높습니다.** 이유:

## 21번. 제어 주기 0.5s → 0.05s — CPU 부담 없음

`ship_goal_angle`이 하는 일은 **뺄셈 한 번 + Float32 발행**이 전부입니다. 20Hz로 돌려도 CPU 사용률이 **0.01%도 안 됩니다.**

**오히려 지금이 병목입니다:**
- IMU: 100Hz
- LiDAR/ship_direction: 10Hz
- motor_control: 20Hz
- **ship_goal_angle: 2Hz ← 여기만 느림**

체인 전체가 이 2Hz에 발목 잡힙니다. **10~20Hz로 맞추면 균형**이 잡힙니다.

## 23번. mode2_detection_distance가 뭔지 (자세히)

`ship_direction.py` 47행에 이런 게 있습니다:
```python
self.base_detection_distance = 1.8    # 평소 탐지거리
self.mode2_detection_distance = 1.8   # ← wp_mode==2(도킹)일 때 쓸 탐지거리
```
그리고 99행:
```python
new_dd = self.mode2_detection_distance if self.wp_mode == 2 else self.base_detection_distance
```
**의도:** "도킹할 때(wp_mode 2)는 탐지거리를 다르게 쓰자"
**문제:** **두 값이 똑같이 1.8이라 아무 효과가 없습니다.** (예전 버전엔 0.7이었습니다)

**왜 도킹에서 짧아야 하나:** 도크에 **접안(붙이는)** 하려면 도크에 가까이 가야 합니다. 그런데 탐지거리가 1.8m면 **도크 자체를 "장애물"로 보고 피해버립니다.** 접안이 불가능해집니다. 그래서 도킹 구간에서는 **0.8m 정도로 줄여서** "도크는 장애물이 아니다"라고 알려줘야 합니다.

**해결:** 구간별로 제대로 설정 — **장애물밭 3.0 / 게이트 2.0 / 도킹 0.8**

## 31·32번. OAK-1 W PoE — ⚠️ **중대한 문제가 있습니다**

**OAK-1 시리즈는 카메라가 1개입니다. 즉 depth(거리 측정)가 안 됩니다.**
(스테레오 depth를 쓰려면 **OAK-D** 계열이어야 합니다)

**지금 코드는 depth에 전적으로 의존합니다:**
- 부표까지 거리 → 게이트 중앙 계산
- 도형까지 거리 → 도킹 접근 판단 (`DIST_THRESHOLD = 0.8m`)
- 탐색 부표까지 거리 → orbit 반경 유지

**OAK-1로 바꾸면 이 거리들을 다른 방법으로 구해야 합니다:**

**① LiDAR로 거리 + 카메라로 색상/모양 (센서 퓨전) ← 강력 추천**
- 카메라: "저 방향에 빨간 부표가 있다" (색상·모양·각도)
- LiDAR: "그 방향에 물체가 2.3m 앞에 있다" (정확한 거리)
- **두 정보를 각도로 매칭**해서 합칩니다
- 장점: LiDAR 거리가 카메라 depth보다 훨씬 정확하고, 물 위에서도 안정적입니다

**② 물체 크기 기지(known size)로 거리 역산**
부표 크기를 미리 알면, 화면에서 차지하는 픽셀 크기로 거리를 추정할 수 있습니다.
- 단점: 부표가 부분적으로 가려지거나 기울면 부정확

**결정하실 것:** OAK-1로 확정이라면 **①번(LiDAR-카메라 퓨전)** 구조로 새로 짜는 걸 권합니다. 그게 아니라면 **OAK-D 계열로 바꾸는 것**도 고려해보세요. depth가 사라지는 건 생각보다 큰 변화입니다.
