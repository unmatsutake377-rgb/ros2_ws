## 1. 도킹 검출기 — 무효 목표가 모드 게이트보다 먼저 발행되는가

현상 재현(카메라만 있으면 됨, 배 불필요):
```bash
# 터미널 1 — 도킹 목표 형상을 일부러 오타로
ros2 run color_shape_detector basic_image_subscriberdock --ros-args \
  --params-file src/color_shape_detector/config/vision.yaml -p target_shape:=Squre
# 터미널 2 — 탐색 검출기 (모드 2·3 의 /image_angle 정상 발행자)
ros2 run color_shape_detector basic_image_subscriberturn --ros-args \
  --params-file src/color_shape_detector/config/vision.yaml
# 터미널 3 — 모드 3 (탐색)
ros2 topic pub /wp_mode std_msgs/Int32 "{data: 3}" -r 2
# 터미널 4
ros2 topic echo /image_angle
```

| 볼 것 | 계약서 예상(현재 코드) | 결과 |
|---|---|---|
| 모드 3 에서 `/image_angle` 에 10000 이 섞이나 | **섞인다** (dock 이 게이트 전에 매 프레임 발행) | ✅ **섞인다** — dock 단독·모드 3: 6초 91건 전부 10000 |
| `ship_turn` 을 같이 띄우면 부표를 잡았다 놓쳤다 하나 | 10000 이 오면 `buoy_rel = None` (`ship_turn.py:138-139`) | ✅ **번갈아 온다** — 빨간 부표 영상 + turn: 6초 181건 = 부표 −17.6° 90건 + 10000 91건. turn 만이면 −17.6° 91건(10000 0) |
| `/wp_mode` 를 끊으면 dock 이 계속 10000 을 내나 | 낸다 | ✅ **낸다** — /wp_mode 없이 91건 전부 10000 |
| 오타를 고치면(`Square`) 모드 3 에서 10000 이 사라지나 | 사라진다 | ✅ **사라진다** — dock 단독 0건, turn 과 함께면 −17.6° 91건만 |

**재현 방법 주의 (10-28 Ubuntu).** 위 터미널 1 의 `-p target_shape:=Squre` 는 **먹지 않는다.** `vision.yaml` 의 노드별 절
(`image_subscriber_dock:`)이 명령줄 `-p`(전역)보다 우선해, 노드 안 값이 `Square` 그대로였다(`ros2 param get` 로 확인).
→ yaml 을 복사해 `target_shape: "Squre"` 로 바꾼 파일을 `--params-file` 로 준다. 카메라 없이 재현: 160×120 가짜 영상(빨간 원) 발행 노드.
**한 번에 다시 확인: `bash tools/repro/dock_gate.sh`** (카메라·배 없이 약 1분, 별도 DDS 도메인 78). 10-28 결과: 기준 −17.6° 91건 / dock 오타 −17.6° 90건 + 10000 91건 / dock 정상 −17.6° 91건.
640×480 가짜 영상은 이 노트북 DDS 기본 설정에서 전달이 안 됐다(작은 영상은 15 Hz 정상) — 실물 카메라와 무관.

결정할 것(계약서 "사람이 정해야 할 것"): 모드 7 무효 목표 때 10000(A) / 침묵(B), 주기 ERROR, 순수 함수 위치·정적 순서 테스트, 문서 정정 커밋 방식.

## 2. GPS 신선도 — fix 가 끊겨도 방위가 계속 나오는가

| 시험 | 방법 | 계약서 예상(현재 코드) | 결과 |
|---|---|---|---|
| ① USB 분리 (⏳ GPS 연결 후) | 대회 launch 중 GPS USB 를 뽑는다 | 드라이버 프로세스는 **안 죽고**(async_worker 재시도) `/ublox_gps_node/fix` 만 끊김. `/north_goal_angle_tp` 는 **마지막 위치로 계속** 나옴 | ____ |
| ② 드라이버 kill | `kill <ublox PID>` (🚨 `pkill -f` 쓰지 말 것 — 자기 셸까지 잡는다, 10-28 실제로 겪음) | `OnProcessExit → Shutdown` 때문에 **대회 launch 전체가 내려갈** 수 있음 (⚠️ 미확인) | ⏳ GPS 연결 후. 단 ③ 과 같은 핸들러라 **내려갈 것이 거의 확실** |
| ③ 장치 없이 부팅 | GPS 를 뽑은 채 대회 launch | `"Failed to initialize."` 후 노드 종료 → launch 전체 종료? (⚠️ 미확인) | ✅ **전체 종료 확인** (10-27 로그): `Could not open serial port :/dev/ttyGPS` → ublox exit −6 → 바로 bridge·motor_control·ship_* 전부 SIGINT. 원인 = 우리 launch 가 include 하는 `ublox_gps_node-launch.py:74-77` 의 `OnProcessExit → Shutdown` |
| ④ 다시 꽂기 | ① 뒤 재연결 | `/fix` 복구, 방위 갱신 재개 | ____ |

```bash
ros2 topic hz /ublox_gps_node/fix
ros2 topic echo /north_goal_angle_tp
ros2 topic echo /geofence_state --once
ros2 topic echo /failsafe_level
```

이미 정한 것: `last_fix_t` 는 **GPSFilter 가 받아들인 프레임에서만** 갱신.
결정할 것: `gps_stale_sec`(제안 2.5), stale 방침(tp·distance·geofence 정지 / wp_mode·20000·남은시간·타임아웃 진행 유지), 잘못된 값 처리, healthcheck 표시, CLAUDE.md "죽은 토픽" 문구.
②③ 이 "전체 launch 종료" 로 확인되면 그것도 별도 계약 후보다(GPS 하나 때문에 배 전체가 꺼짐).
→ **③ 확인됨(10-28).** 별도 계약 후보로 올린다. 참고: 같은 10-27 로그에서 **라이다·IMU 드라이버는 죽어도 launch 를 안 내린다**(exit 255, 핸들러 없음) — 대신 respawn 도 없어 그 노드만 영영 죽어 있다. 셋의 실패 방식이 서로 다르다.
