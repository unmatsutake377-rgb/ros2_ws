# 🟠 LEVEL 1 — 미션 기능

## 5. 게이트 색상 (노랑 → 초록)
- **진단:** 규정은 **빨강–초록** 게이트인데 코드는 `/red_angle` + **`/yellow_angle`**. 비전 노드도 초록 HSV가 주석 처리됨.
- **사용자:** 색상만 바꾸면 될 듯.
- **최종:** ✅ **확정.** `/yellow_angle` → `/green_angle`, 비전에서 green HSV 활성화.

## 6. 탐색 orbit 기동 미구현
- **진단:** 규정은 부표를 **중심으로 원을 그리며 한 바퀴**(빨강·초록=시계 / **흰색**=반시계). 코드는 부표를 **옆으로 비껴 지나갈 뿐**. 흰색 인식도 없음.
- **사용자:** 무슨 뜻인지 설명 요청 → 설명 후 이해.
- **최종:** ✅ **신규 작성 필요.** 부표 중심 반경 R 유지 제어 + 색상별 회전 방향 + 흰색 HSV 추가. (배점 15%)

## 7. 도킹 표식 하드코딩
- **처음 진단:** `target_color="red"`, `target_shape="Square"` 하드코딩 → 당일 공지 대응 불가.
- **사용자 피드백 1:** 작년 코드에 파라미터가 있다던데?
- **검증:** 전수 조사 결과 `color_shape_detector` 패키지에 `declare_parameter`가 **0개**. 파라미터가 있는 건 미션노드의 `active_wp_mode`뿐(표식과 무관).
- **사용자 피드백 2:** 변수 방식 vs 파라미터, 뭐가 나은지 판단 요청.
- ⚠️ **정정:** "빌드 때문에 파라미터가 필요하다"는 제 논리는 **반쯤 틀렸습니다.** `--symlink-install`이면 변수만 고쳐도 반영됩니다.
- **최종 결론:** ✅ **파라미터가 맞습니다. 단 이유가 다릅니다** — **실패 모드** 때문입니다. 대회장에서 소스를 고치다 오타 하나 나면 **노드가 안 뜨고 0점**. 파라미터는 틀려도 **노드는 뜨고 다시 실행하면 됨**.
- **추가 개선:** 구조도 바꿔야 함 — **전체 표식 인식 → 목록 발행 → 선택 노드가 파라미터로 고름**. 그래야 도크 3개 중 목표를 고를 수 있음.
- **호환성:** 선택 노드가 기존 토픽(`/image_angle`, `/image_distance`)을 그대로 발행 → **`ship_dock` 수정 0** ✅

## 8. 위치유지 피드백 없음
- **진단:** 부표 5m 이내 5초 유지인데, 코드는 PWM 중립만 줌. **시뮬: 조류 0.5m/s면 5초에 2.5m 밀려 실패.**
- **사용자:** 그 위치에 머물게 수정 필요.
- **최종:** ✅ **확정.** 부표 탐지 + 거리/방위 피드백 제어. (배점 10%)

## 9. Geofence 없음
- **진단:** 경계선 이탈 = **실격**인데 코드에 개념 자체가 없음.
- **사용자:** 설명 요청 → 이해.
- **최종:** ✅ **확정.** 준비 기간에 경계 좌표 측량 → 경계 근처를 **가상 장애물로 주입** → 기존 회피 로직이 자동 처리.

## 🚨 신규 발견: ship_dock이 절대 실행되지 않음
- **발견 경위:** 7번 확인하려고 코드 전수 조사 중.
- **문제:** `ship_dock`은 `active_wp_mode = 9`를 기다리는데, **웨이포인트에 mode 9가 없음.** 도킹은 **mode 7**.
- **결과:** **도킹 미션(배점 15%)이 통째로 죽어 있었음.**
- **사용자:** 작년 기준으로 수정 진행.
- **최종:** ✅ **`active_wp_mode` 9 → 7**

# 🟡 LEVEL 2 — 안전

## 10. 소프트웨어 페일세이프
- **진단:** 센서/노드/통신 유실 시 **마지막 명령으로 계속 주행**. 유일한 안전장치는 사람의 RC 수동 전환.
- **사용자:** 알고리즘에 넣자. **단 "고장이 아닌데 고장으로 판단해 멈추는 참사"가 우려됨.**
- **검증:** 오탐지 정지 방지 4중 설계 후 시뮬 → **정상 상황 오탐지 정지 0회**, 진짜 고장에서만 정지.
- **최종:** ✅ **3단계 확정**
  - L1: 비전만 끊김 → 계속 주행 (미션 포기, 다음 구간)
  - L2: LiDAR/IMU 0.7초 무응답 → **감속 + 직진**
  - L3: 3초 무응답 → **정지** (= LiDAR 스캔 30회 연속 누락, 오탐지 거의 불가능)
  - 미션 타임아웃(전략) = 별개 층위. 다음 좌표로 이동.

## 🚨 신규 발견: 오탐지 정지 방지 필수 조건 3가지
- **① `time.time()`(벽시계) → `time.monotonic()`**
  전 노드(`ship_direction`/`turn`/`dock`/`gate`)가 벽시계 사용, monotonic **0회**. NTP 동기화로 시각이 점프하면 페일세이프가 오작동/지연.
- **② ARMED 플래그 (가장 위험한 함정)**
  타임스탬프 초기값을 `0.0`으로 두면 `age = now - 0` → 거대 → **경기 시작하자마자 배가 정지**. 첫 데이터를 받은 센서만 감시해야 함.
- **③ 히스테리시스 (연속 3회 확인) + 자동 복구**
  CPU 지터·순간 드롭아웃을 걸러냄. 시뮬에서 **스캔 20% 누락에도 정지 안 함** 확인.

## 11. 펌웨어 워치독
- **진단:** ROS가 죽어도 아두이노가 마지막 모터값을 무한 유지 → 폭주.
- **사용자 피드백:** 10번과 같은 거 아닌가? 중립 or 미션 종료 좌표로 이동?
- **답변:** **다른 층위입니다.** 10번은 **노트북**(ROS), 11번은 **아두이노**(펌웨어). **ROS가 통째로 죽으면 10번 코드도 같이 죽습니다.** 그때 멈출 수 있는 건 아두이노뿐.
- **"종료 좌표로 이동"은 불가능:** 워치독이 발동하는 상황이 곧 ROS가 죽은 때인데, **좌표를 계산할 주체가 그 ROS**입니다. 아두이노는 GPS도 좌표도 모릅니다.
- **최종:** ✅ **펌웨어 워치독 = 반드시 중립 정지.** (0.5초 무응답 → 1500/1500)

## 12. RC 두절 시 기본 오토파일럿
- **진단:** RC 신호가 없으면 `Auto_signal=0 < 1500` → 자동 자율. "RC 없음"과 "자율 선택"을 구분 못 함. 작년 참사(멀어져서 수동 전환 안 됨) 원인일 수 있음.
- **사용자 피드백:** 자율 미션은 자율로 시작해 자율로 끝남. RC는 이상 시 복귀용. **RC 끊겼다고 멈추면 경기가 끝남.** 건드리지 말 것.
- **최종:** ✅ **건드리지 않음.** 잔여 위험만 기록 — RC가 다시 잡혔을 때 수동 전환이 되는지 **실측 권장**. 안전망은 **무선 비상스위치 + geofence**.

## 13. iahrs GPS heading override
- **처음 진단:** GPS heading(COG)으로 IMU yaw를 덮어쓰는데, 한 번 유효하면 **NaN 리셋이 없어 stale값에 영구 고정**. COG는 저속에서 노이즈.
- **사용자 피드백 1:** "GPS 방향(목표) − IMU 방향(뱃머리)"이라 GPS가 필요한 것 아닌가?
- **답변:** **GPS의 두 용도를 구분해야 합니다.**
  - **(A) GPS 위치(fix) → 목표 방위 계산** = 말씀하신 그 로직. **필수, 유지** ✅
  - **(B) GPS heading(COG) → IMU yaw 덮어쓰기** = 13번 버그. **위험** ❌
- **사용자 피드백 2:** 뱃머리는 IMU가 전담. IMU 고장 때만 예외.
- **사용자 피드백 3:** IMU 모델 = **WT901C** → 이후 **RB-SDA-v1**로 정정.
- ⚠️ **정정:** WT901C라고 하셨을 때 "드라이버 프로토콜 불일치, 새로 작성 필요"라고 경고 → **RB-SDA-v1 = IntelliThings iAHRS**로 확인되어 **경고 철회.** 현재 드라이버가 바로 이 모델용이고 ASCII 프로토콜도 정확히 맞습니다. **9축 확인.**
- **최종:** ✅ **GPS heading override 삭제. IMU 전담.** (9축이라 지자기로 절대 방위 가능)

## 🚨 신규 발견: 부팅 0점화가 절대 기준을 파괴
```cpp
yaw_initial_offset = imu_yaw_cw;                  // 부팅 시 첫 값
yaw_corrected = imu_yaw_cw - yaw_initial_offset;  // 빼버림
```
- **문제:** 부팅할 때 향한 방향이 0도가 됨 → IMU yaw가 **상대 방위**. 그런데 `north_goal_angle`은 **진북 기준 절대 방위**를 계산. **기준이 완전히 다름.**
- **파급:** 배를 북쪽 보고 켰을 때만 우연히 맞음. **이게 GPS override를 넣은 진짜 이유로 보임** (원인은 놔두고 증상만 가림).
- **최종:** ✅ **부팅 0점화 제거 + 자북→진북 편차(한국 약 8°W) 보정.** 그러면 GPS override 없이 기준이 맞음.
- **주의:** 지자기는 자기 간섭에 취약 → **모터·배터리에서 멀리, 높게 장착** (하드웨어 파트 요청)

## 14. 미들 스러스터

- **최종:** ⏸️ **보류.** (현재는 `M_signal = 1500` 고정 권장)

# 🟢 LEVEL 3 — 성능 (시뮬 검증 완료)

> **핵심 원칙: 접촉 1회 = 30초. 주행이 140초니까 접촉 3회면 기록 65% 악화.**
> **속도보다 "안 부딪히는 것"이 압도적으로 중요.**

## 15·20. LiDAR 노이즈 붕괴 + 시간 필터
- **진단:** `rear_obstacle_ignore_margin` 로직 때문에 **물보라 0.3m 반사 1점**이 최근접으로 잡히면 **1.6m 앞 진짜 부표가 통째로 무시됨** (장애물 셀 17개 → 0개).
- **사용자 우려:** 시간 필터 3프레임이면 **3초**라 부딪힐 수 있고, 탐지거리 늘리면 **데이터가 기하급수적으로 늘어 컴퓨터가 퍼질 것**.
- ⚠️ **두 전제 모두 사실과 다릅니다 (실측 검증):**
  - **LiDAR는 1Hz가 아니라 10Hz** (`scan_frequency=10` 코드 확인) → **3프레임 = 0.3초**, 1.2m/s에서 0.36m 이동
  - **탐지거리를 늘려도 데이터는 안 늘어남.** LiDAR는 항상 같은 점 수(회전당 ~1600점)를 보냄. `detection_distance`는 **임계값**일 뿐 → **연산량 동일**
  - **실측: 1.8m/3.0m/5.0m 모두 0.15ms/스캔** = 100ms 예산의 **0.1%** (여유 660배)
- **최종:** ✅ **`rear_obstacle_ignore_margin` 제거 + 시간 필터(3프레임 중 2회)**

## 16. clearance
- **처음 진단:** 0.15m는 너무 작음. **0.3~0.5m로 올리라.**
- ⚠️ **정정 (시뮬 스윕):** 제 권고가 **틀렸습니다.** **0.45m는 오히려 807초로 폭주**합니다(통과 불가 판단 → 후진 반복).

| clearance | 접촉 | 기록 |
|---|---|---|
| 0.20 | 1.7회 | 196초 |
| **0.25** | **0.2회** | **151초** ✅ |
| 0.30 | 0.8회 | 171초 |
| 0.45 | 2.0회 | **807초** ❌ |

- **최종:** ✅ **0.25m** (배 폭 확정 후 재조정)

## 17. detection_distance
- **진단:** 1.8m는 반응시간 1.5초뿐. 시뮬에서 **8/8 전부 충돌**.
- **사용자:** LiDAR 스펙 확인 요청.
- **검증:** **RPLIDAR A3 = 최대 25m** (Sensitivity 모드). 1.8m는 성능의 **7%**. 3m에서 반경 0.2m 부표가 **34개 점**으로 찍힘. **완전히 여유.**
- **최종:** ✅ **구간별 적용 — 게이트 2.0m / 장애물밭 3.0m / 도킹 0.8m**
  (일괄 3.0m는 좁은 게이트에서 오히려 악화 → 접촉 6회)

## 18·19. 침식 / 팽창 최소셀
- **진단:** `suppress_spike_edges`가 작은 부표를 침식·삭제. 침식 후 3셀 미만이면 `dilate`(배 폭 팽창)도 안 붙어 **"탐지는 됐는데 여유 0"**.
- **사용자 질문:** 어느 노드? / 변수 늘면 하드웨어 퍼지나?
- **답변:** `ship_direction.py` — `smooth_spikes()` **336행**, `suppress_spike_edges()` **358행**, `dilate_obstacles()` **369행**, 파라미터 **47~57행**. **연산량은 오히려 줄어듭니다** (침식 루프 하나 제거).
- **최종:** ✅ **침식 제거 + `min_obstacle_cells` 3 → 1**

## 21. 제어 주기 0.5초
- **진단:** IMU는 100Hz인데 `ship_goal_angle`이 **2Hz**로만 갱신 → 병목.
- **사용자:** 하드웨어 과부하 고려 요청.
- **답변:** 이 노드는 **뺄셈 1번 + Float32 발행**이 전부. 20Hz여도 CPU **0.01%도 안 씀**.
- **최종:** ✅ **0.5초 → 0.05초**

## 22. 감속 로직
- **진단:** 최종본에서 장애물 거리 기반 감속이 **제거됨**. 순항 고정.
- **사용자:** 넣는 게 좋겠다.
- **검증 (시뮬 스윕):** **감속 시작 1.2m, 최저 속도 70%** 가 최적. (2.5m/45%는 시간만 늘어남)
- **최종:** ✅ **확정.** 주행시간 +5%지만 접촉이 사라져 총 기록 -34%

## 23. mode2_detection_distance 죽은 코드
- **진단:** `mode2 = base = 1.8`로 동일 → wp_mode==2 전환이 무효.
- **설명:** 도킹 때 탐지거리가 길면 **도크 자체를 장애물로 보고 피해버려** 접안 불가. 그래서 짧게(0.8m) 해야 함.
- **사용자:** 그 방식대로 해보고 데이터 쌓아서 판단.
- **최종:** ✅ **구간별 값 적용** (17번과 통합)

## 24. 신선도(timeout) 체크
- **최종:** ✅ **10번 페일세이프에 통합**

## 31·32. 카메라 OAK-1 W PoE 교체
- **처음 경고:** **OAK-1은 depth가 없습니다** (카메라 1개). 현재 코드는 depth로 거리를 잼.
- **사용자:** 거리는 LiDAR가 담당. 가능한지 판단 요청.
- **검증 ①:** 부표는 **완전히 가능** ✅ — LiDAR 각분해능 0.225° vs 카메라 오차 ±2°, 게이트 부표 2개가 3m에서 53° 벌어져 혼동 없음.
- **사용자 추가:** 팀에서 "도형 각도에 따라 인식 실패"한다는데, 거리 판별 때문 아닌가?
- **검증 ②:** **사용자 판단이 맞습니다.**
  - **가설 A (도형 각도) = 주원인 아님.** 원근 변환은 직선을 보존 → **꼭짓점 개수 보존**. 비스듬해도 사각형은 4개.
  - **가설 B (거리 판별) = 맞음.** 표식은 도크 **중앙**인데 LiDAR는 도크 **구조물 최근접점**을 맞음 → 비스듬하면 방위가 **최대 26° 어긋남** (매칭 윈도우 ±3° 초과).

| 거리 | 횡오프셋 | 방위 차이 |
|---|---|---|
| 3m | 0m (정면) | 0° ✅ |
| 3m | 1m | **18.4°** ❌ |
| 3m | 2m | **15.3°** ❌ |

- **최종 해법:** ✅ **도크는 표식-LiDAR 매칭을 아예 하지 않는다.**
  - ① 어느 도크인가 → **카메라** (표식 판별)
  - ② 어디로 갈까 → **카메라** (표식 방위)
  - ③ 얼마나 가까운가 → **LiDAR 전방 섹터 최소거리** (매칭 불필요!)
  - **+ 정면 접근 전략:** 도크 정면 3m standoff → 정렬 → 직진 접안 → 각도 문제 소멸
