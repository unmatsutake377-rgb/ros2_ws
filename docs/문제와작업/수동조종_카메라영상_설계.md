## 0. 한 줄 요약

**배 노트북의 D455 컬러 영상을 GStreamer 로 H.264 인코딩해 UDP/RTP 로 물가 노트북에 쏜다.**
ROS2 토픽을 네트워크로 넘기지 않는다(Tailscale 을 못 넘음). 제어 경로(조종기→수신기→Mega)는 손대지 않는다.

파일 7개:
| 파일 | 어디서 | 역할 |
|---|---|---|
| `tools/cam_stream.sh` | 배 노트북 | 송신. `v4l2`(수동, 카메라 직접) / `ros`(자율, 토픽 경유) 두 모드 |
| `tools/cam_stream_ros.py` | 배 노트북 | `ros` 모드 본체. `/camera/camera/color/image_raw` → appsrc |
| `tools/cam_stream_oak.py` | 배 노트북 | `oak` 모드. OAK-1 PoE 온보드 H.264 인코더 직접 (⚠️ 실물 미검증) |
| `tools/cam_view.sh` | 물가 노트북 | 수신. ROS 불필요, Ubuntu/Mac 공통 |
| `tools/cam_bench_tx.py` / `cam_bench_rx.py` | 양쪽 | 벤치. 프레임에 송신시각 바코드를 박아 지연·fps·유실을 **숫자로** 잰다 (인코더 체인은 본 스트림과 동일) |
| `tools/cam_bench_netsim.py` | 어디든 | UDP 프록시로 무선 링크(지연·지터·유실) 흉내 — 하드웨어 없이 사전 벤치 |

설치·벤치 절차: `docs/절차/카메라영상_설치와_벤치.md`

## 1. 왜 이 방식인가 — 대안 비교

| 대안 | 기각/채택 이유 |
|---|---|
| ROS2 토픽 그대로(`rqt_image_view`, `image_transport compressed`) | ❌ DDS 멀티캐스트가 Tailscale/서로 다른 랜을 못 넘는다(08-10 확정). 같은 랜에서도 discovery 지연·QoS 문제로 침묵 실패가 잦다 |
| WebRTC(브라우저) | △ 되지만 시그널링 서버·TURN 한 겹이 더 필요. 지연 이득 없음(병목은 카메라 캡처). 대회 전 의존을 늘리지 않는다 |
| MJPEG over UDP | △ 인코딩 지연은 더 짧지만 대역폭 10~20Mbps — LTE 에서 못 버틴다 |
| 아날로그 5.8GHz FPV | ❌ 국내 허용 출력(10mW급)으로는 ~30m. 대회 거리(최대 116m) 불가 |
| 디지털 FPV(DJI O4 등) | △ 성능은 최고지만 수십만 원 + 5.8GHz 가 우리 5GHz WiFi 상위 채널과 겹침. 노트북 하선이 필수일 때만 |
| **H.264 / RTP / UDP 유니캐스트 (채택)** | ✅ 추가 하드웨어 0, 유니캐스트라 VPN 을 넘는다, 1~3Mbps 로 LTE 도 됨, ROS 와 완전 분리 |

## 2. 구조

```
[배 노트북]                                           [물가 노트북]
D455 컬러 ─(v4l2 또는 ROS 토픽)─▶ clockoverlay ─▶ x264enc ─▶ RTP ─▶ UDP:5600 ══무선══▶ udpsrc ─▶ jitterbuffer ─▶ avdec ─▶ 화면
                                  (배 시각 각인)   zerolatency                                   30ms
```

- **단방향.** 물가에서 배로 들어가는 패킷은 없다. 조종 명령은 기존대로 조종기 전파.
- **배 시각을 영상에 박는다**(좌상단). 화면이 멈추면 시계도 멈춘다 → "묵은 프레임을 지금으로 읽는" 사고 차단. 저장소 원칙(모르면 입을 다문다)과 같은 취지. 수신 노트북 시각은 우하단 — 두 시계 차 ≈ 전송 지연(양쪽 NTP 동기 시).
- 송신·수신 모두 **끊기면 3초 후 자동 재시작** 루프. 조용히 죽지 않는다.
- `mtu=1200`: Tailscale(WireGuard) 헤더 몫을 빼서 IP 단편화 방지.

### 어느 모드로 띄우나

| 상황 | 모드 | 이유 |
|---|---|---|
| **수동 토너먼트** (자율 스택 안 띄움) | `v4l2` | realsense 노드가 없어 장치를 직접 열 수 있다. CPU 가장 싸다 |
| 자율 주행 중 모니터링 | `ros` | realsense 노드가 장치를 잡고 있어 v4l2 로 못 연다("Device busy"). 토픽 경유 |

⚠️ `v4l2` 모드에서 `camera.launch.py` 를 같이 띄우면 **둘 중 하나가 죽는다.** 동시에 쓰지 말 것.

### 🚨 카메라가 OAK-1 PoE 로 바뀌면 (구매 확정 09-15: OAK-1 PoE 고정초점 69°, RJ45, 2m Cat5e 동봉)

OAK 는 **이더넷(PoE) 장치**라 `/dev/video` 가 없다 → **`v4l2` 모드는 못 쓴다.** 나머지는 그대로다:

| 카메라 | 수동(카메라 노드 없음) | 자율(카메라 노드 있음) | 비고 |
|---|---|---|---|
| RealSense D455 | `v4l2` | `ros` | 지금 |
| OAK-1 PoE | `ros` (depthai 노드만 띄움) **또는** `oak` | `ros` + `CAM_TOPIC=/oak/rgb/image_raw` | 토픽 이름은 ⚠️ 도착일 `ros2 topic list` 로 확인 |

- `ros` 모드는 카메라를 가리지 않는다 — 토픽만 맞추면 D455/OAK 동일. **OAK 의 기본 경로.**
- `oak` 모드는 OAK 안의 인코더(Myriad X)를 써서 **노트북 CPU 0** 이지만, 이미 압축된 영상이라 **배 시각 각인을 못 한다**(프리즈 판별 불가). CPU 가 모자랄 때만.
- OAK 는 노트북 이더넷을 쓴다. 라우터도 이더넷이면 포트가 겹친다 — 라우터는 WiFi 로 붙거나 USB 이더넷 어댑터 하나 더(`oak_arrival_runbook.md` §2 의 기가비트 조건 동일).
- 광각(120~150°)이라 조종 화면으로는 D455 보다 오히려 좋다(좌우가 넓게 보임).

## 3. 설계 결정 — 펌웨어 설계문서와의 충돌

`펌웨어_설계문서.md` §"수동 토너먼트 = 노트북·센서 전부 하선 가능(경량화)" 은 **"가능"** 이지 "필수" 가 아니다.
카메라 영상을 쓰려면 수동 토너먼트에도 **노트북 + D455 + 라우터**를 싣는다. 대가는 무게(속도)다.

- 펌웨어는 여전히 노트북 없이 돈다. 노트북·스트림·라우터가 전부 죽어도 **RC 수동 조종은 영향 0.**
- 모드 전환은 조종기에만 둔다는 08-10 결정 무변경. 이 설계는 "보는 것" 만 추가한다.
- 영상이 끊기면? **조종기로 즉시 정지 → 시야 확보 → 재개.** 영상은 보조이지 조종의 전제가 아니다(체크리스트 5장에 넣을 것).

## 4. 네트워크 — 어느 IP 로 쏘나

`cam_stream.sh <물가노트북IP>` 의 IP 는 **물가 노트북의 Tailscale IP(100.x.y.z)** 를 기본으로 한다.

| 상황 | 경로 | 비고 |
|---|---|---|
| 같은 5GHz 랜(배 라우터에 둘 다 접속) | Tailscale 이 랜 직결 경로를 자동으로 잡는다 | IP 를 바꿀 필요 없음 |
| 배=LTE, 물가=다른 인터넷 | Tailscale 릴레이/직결 | CGNAT 무관(유니캐스트 UDP, 배→물가 방향) |

- Tailscale IP 는 고정이라 **스크립트 인자를 매번 바꿀 일이 없다.** 랜 사설 IP(DHCP)로 쏘면 그날그날 바뀐다.
- 수신측 방화벽: `sudo ufw allow 5600/udp` (ufw 사용 시). Mac 은 첫 실행 때 허용 팝업.
- ⚠️ **대역폭 상한 실측 필요.** 기본 1500kbps. 5GHz 랜이면 3000 까지 올려도 되고, LTE 상행이 약하면 800 으로 내린다. `cam_stream.sh <IP> v4l2 640 480 30 <kbps>`.

## 5. 설치 (한 번만)

배 노트북(Ubuntu 22.04):
```bash
sudo apt install gstreamer1.0-tools gstreamer1.0-plugins-base gstreamer1.0-plugins-good \
     gstreamer1.0-plugins-bad gstreamer1.0-plugins-ugly gstreamer1.0-libav gstreamer1.0-x \
     v4l-utils python3-gi gir1.2-gstreamer-1.0 gir1.2-gst-plugins-base-1.0
chmod +x tools/cam_stream.sh tools/cam_view.sh tools/cam_stream_ros.py
```
(`gstreamer1.0-x` 가 `clockoverlay` 를 담고 있다 — 이게 빠지면 "no element clockoverlay")

물가 노트북: Ubuntu 는 위와 같음(python3-gi·v4l-utils 불필요). Mac 은 `brew install gstreamer`.

### 7-B. 사전 벤치 (2026-09-14, 가상 링크) — 키프레임 0.5초로 확정한 근거

`cam_bench_netsim.py` 로 지연·유실을 넣고 돌린 결과(640x480@30, 1500kbps). 상세 표는 절차 문서 §1-B.

- 인코딩+전송+디코딩 자체는 **p50 3ms**. 지연의 몸통은 링크 편도지연과(실링크에선) 카메라 캡처다.
- 유실 1~2% 에서 **키프레임 1초 간격이면 p99 1.6s / max 3.2s** — 유실 뒤 다음 키프레임까지 화면 일부가 묵는다. **0.5초로 줄이면 p99 292 / max 594ms.** 그래서 `key-int-max=FPS/2`. 더 줄여도(0.17s) 이득 없음.
- 지터버퍼는 링크 지터의 1.5~2배. 과하게 키우면 대기만 는다(5GHz 에 60ms → p90 3배 악화).
- 유실 5% 구간은 p90 380ms — 조종 불가 영역. 절차상 **조종기로 정지**.

V2 가 200ms 를 크게 넘으면 순서대로: 지터버퍼 30→10ms(`CAM_JITTER_MS=10`) → 해상도 424x240 → 카메라 캡처 자체를 의심(USB 카메라 캡처 ~100ms 가 통상 병목).

## 9. 안 한 것 (의도)

- **양방향(물가→배 명령)**: 안 만든다. 모드 전환·조종은 조종기 전용(08-10 결정).
- **녹화**: 필요하면 수신 파이프라인에 `tee ! filesink` 한 줄. 지금은 뺐다(디스크·CPU 변수 추가 금지).
- **ssf_tools 패키지 편입**: `python3-gi` 의존을 패키지에 넣지 않는다(빌드 위험). `tools/` 독립 스크립트로 둔다.
- **VAAPI 하드웨어 인코딩**: V3 에서 CPU 가 부족할 때만. IdeaPad Slim 3 의 CPU 종류부터 확인(`lscpu`).
